Add your application's users to Permit.io so the policy decision point (PDP) can check their permissions. This page is for developers who connect their sign-up or sign-in flow to Permit. You can add users in the Permit dashboard, with the `users.sync` SDK function, or with the Permit API.

## Prerequisites

- A Permit.io project and environment ([Quickstart](/quickstart))
- For the SDK or API: your environment API key ([Get your API key](/overview/get-api-key))
- Optional: roles defined in the Policy Editor, so you can assign one to the user ([Policy basics](/how-to/build-policies/policy-basics))

## When to sync users \{#when-to-sync-your-users}

Sync a user during sign-up or sign-in, right after your authentication provider verifies the user's identity. At that point, translate the user's organizational role (for example Head of Marketing, Customer, Consultant, or Patient) and other JSON Web Token (JWT) claims into application-level roles, attributes, and relationships.

The user key you sync is the identifier you later pass to [`permit.check()`](/how-to/enforce-permissions/check). Use the same identifier your authentication provider gives the user, for example the JWT `sub` claim.

## Choose a sync method

| Method | Use it when |
|---|---|
| [Permit dashboard](#via-the-user-management-screen) | You add a few users by hand, for example for testing. |
| [SDK](#via-the-sdks) | Your backend syncs users in code, for example in the sign-in callback. |
| [API](#via-the-api) | You call Permit over HTTP from a language or tool without an SDK. |

## Add a user in the Permit dashboard \{#via-the-user-management-screen}

1. In Permit, open the [Directory](https://app.permit.io/user-management) screen from the navigation bar.

    ![Permit navigation bar with the Users item selected](/ui-videos/how-to/sync-users/1.png)

2. Select the tenant the user belongs to. Permit creates the user in the selected tenant. Each tenant has its own users, data, and permissions.

3. In the top right corner, click **Add user**.

    ![The Add user button](/ui-videos/how-to/sync-users/2.png)

4. Fill out the **Create a new user** form.

    ![Create a new user form with Key, Email, First Name, Last Name, Tenant, and Top Level Access fields](/ui-videos/how-to/sync-users/3.png)

    | Field | Description |
    |---|---|
    | **Key** | Required. The unique identifier of the user in the environment. When you use an authentication provider, this is usually the user's ID in that provider. |
    | **Email**, **First Name**, **Last Name** | Optional. Identify the user in the Permit dashboard. |
    | **Tenant** | The tenant to associate the user with. |
    | **Top Level Access** | Optional. The roles to assign to the user in that tenant. Define roles first in the [Policy Editor](/how-to/build-policies/policy-basics). |
    | Instance roles | Optional. Roles on specific resource instances, for relationship-based access control (ReBAC) policies. See [Build ReBAC policies](/how-to/build-policies/rebac/building-rebac-policies). |

5. Click **Save**. The user appears in the Directory list for that tenant.

## Sync a user with the SDK \{#via-the-sdks}

Call `users.sync` from your backend when a user signs up or signs in. The function creates the user if the key doesn't exist, and updates the user if it does. In the Node.js SDK, the call is `permit.api.users.sync(user)`. In the Python SDK, it is `await permit.api.users.sync(user)`. See the per-language reference, for example [syncUser for Node.js](/sdk/nodejs/user/sync-user), and the [SDKs overview](/sdk/sdks-overview) for other languages.

### User object fields \{#parameters}

`users.sync` takes one argument: a user object with these fields.

| Field | Required | Description |
|---|---|---|
| `key` | Yes | The unique ID Permit uses to identify the user in permission checks. You pass the same value to [`permit.check()`](/how-to/enforce-permissions/check). Use any value that is unique in your system, such as an email or a [UUID](https://en.wikipedia.org/wiki/Universally_unique_identifier). Allowed characters: letters, digits, and `\|`, `@`, `+`, `-`, `.`, `_`. |
| `email` | No | The user's email. A synced email is unique in the environment. |
| `first_name` | No | The user's first name. |
| `last_name` | No | The user's last name. |
| `attributes` | No | Key-value data for attribute-based access control (ABAC) policies. See [Defining attributes](/how-to/build-policies/abac/defining-attributes). |
| `role_assignments` | No | A list of `role` and `tenant` pairs to assign to the user. |

### Example user object \{#a-payload}

This is the shape of the user object for the Node.js SDK. Pass it to `permit.api.users.sync()`.

```
{
    key: "key",

    email: "email@example.com",

    first_name: "John",

    last_name: "Smith",

    attributes: {}
}
```

The field names are the same in every SDK. The call syntax depends on the SDK language.

### Change roles after the first sync

Use `users.sync` to create the user and keep the profile fields current. To change the roles of a user that already exists, call `permit.api.users.assignRole()` and `permit.api.users.unassignRole()` in the Node.js SDK (`assign_role` and `unassign_role` in Python). See [assignRole for Node.js](/sdk/nodejs/role/assign-role).

:::info users.sync compared with users.create
`users.create` creates a user and fails if the key already exists. `users.sync` creates or updates the user. A user without a role assignment can't perform any action, so assign a role in the same flow, either with `role_assignments` or with `assignRole`.
:::

## Create a user with the API \{#via-the-api}

Send a request to the [Create User](https://api.permit.io/v2/redoc#tag/Users/operation/create_user) endpoint:

`POST https://api.permit.io/v2/facts/{proj_id}/{env_id}/users`

Authenticate with your environment API key as a bearer token.

| Path parameter | Description |
|---|---|
| `proj_id` | The ID or the URL-friendly key (slug) of the project. |
| `env_id` | The ID or the URL-friendly key (slug) of the environment. |

The request body takes the same fields as the [SDK user object](#parameters): `key` (required, matching `^[A-Za-z0-9|@+\-\._]+$`), `email`, `first_name`, `last_name`, `attributes` (default `{}`), and `role_assignments`.

This is a sample request body:

```
{
  "key": "user|892179821739812389327",
  "email": "jane@coolcompany.com",
  "first_name": "Jane",
  "last_name": "Doe",
  "attributes": {
    "department": "marketing",
    "age": 30,
    "subscription": {
      "tier": "pro",
      "expired": false
    }
  }
}
```

The API returns the created user, or `409` when a user with the same key already exists. To create or update in one call, use `PUT https://api.permit.io/v2/facts/{proj_id}/{env_id}/users/{user_id}`, which is the endpoint `users.sync` calls.

:::note Assign a role to the user
A Create User request without `role_assignments` creates a user with no roles. Assign roles in the same request with `role_assignments`, or afterwards with the [Assign Role To User](https://api.permit.io/v2/redoc#tag/Users/operation/assign_role_to_user) endpoint. The [Users section of the API reference](https://api.permit.io/v2/redoc#tag/Users) lists every user endpoint.
:::

## Verify the user was synced

Open the [Directory](https://app.permit.io/user-management) screen and select **All Tenants**. The user appears in the list with its key, and with any roles you assigned under **Top Level Access**. Then run a [`permit.check()`](/how-to/enforce-permissions/check) with the user key to confirm the user's permissions.

## Users and members \{#users-vs-members}

Permit has two kinds of identities. Users are the identities you check permissions for. Members are your team in the Permit dashboard.

### Users

Users are the end users of your application: the people and automated identities whose access you control. Each user is authenticated by your application. A user can belong to more than one [tenant](/overview/glossary#tenant) and has roles and permissions in each tenant.

To let your end users manage access in your application, embed the [User Management element](/embeddable-uis/element/user-management). Through that element, users with the right role can invite other users and assign roles, within the limits you set. For other self-service interfaces, build them on the [Permit API](https://api.permit.io/v2/redoc). You can control access to those interfaces with Permit itself, for example in a separate environment.

### Members

Members are your team members who work in the Permit dashboard. Permit's own access control governs what members can do ([AuthZ for AuthZ](/overview/glossary#authz-for-authz-aka---meta-authorization)). By default, only members can access Permit and create or edit policies.
