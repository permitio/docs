View every permission decision your policy decision points (PDPs) make, filter the list to the decisions you care about, and read why each decision allowed or denied the request. This page is for developers and admins who debug permissions or review who accessed what.

## How Permit creates audit logs \{#automatic-log-generation}

Each `permit.check()` call that reaches a PDP creates an audit log entry. You don't add logging code. The entry combines the check (user, action, resource, tenant) with the policy that the PDP evaluated: resources, actions, roles, and user and tenant data.

The PDP uploads decision logs to Permit by default, for container PDPs and the Cloud PDP. To see decisions outside the Permit dashboard, use one of these options on a container PDP:

- Print each decision to the container output with `PDP_OPA_DECISION_LOG_CONSOLE`. See [Print decisions to the console](/overview/local-authorization-microservice#debug-mode).
- Send decision logs to Elasticsearch or stdout with the [logs forwarder](/how-to/use-audit-logs/logs-forwarder).

## Audit log types \{#types-of-audit-logs}

| Type | What it shows |
|---|---|
| Audit log | Who made the request, the action, the resource, the tenant, and whether the PDP allowed or denied it. |
| Decision log | The details of one decision, including a human-readable `reason` for the result. |

## View audit logs \{#viewing-your-audit-logs}

1. Sign in to the [Permit dashboard](https://app.permit.io) and select the environment your PDP uses.
2. Open the [Audit Log](https://app.permit.io/audit-log) screen.
3. Select an entry to open its decision log.

<video controls aria-label="Opening the Audit Log screen in the Permit dashboard and selecting a log entry">
  <source src={viewingAuditLogs} />
</video>

If the screen shows no entries, see [Troubleshoot missing audit logs](/how-to/use-audit-logs/troubleshooting).

:::note Audit log retention
Permit deletes old audit logs periodically. To access older logs or extend log retention for your account, contact Permit on [Slack](https://io.permit.io/slack) or at [help@permit.io](mailto:help@permit.io).
:::

## Filter audit logs \{#filtering}

On the **Audit Log** screen, filter entries by **user**, **date**, **decision**, and **tenant**.

<video controls aria-label="Filtering audit log entries by user, date, decision, and tenant in the Permit dashboard">
  <source src={filteringAuditLogs} />
</video>

To filter audit logs in code, call the [List audit logs](https://api.permit.io/v2/redoc#tag/Audit-Logs/operation/list_audit_logs) endpoint. It filters by users, decision, resources, tenant, action, PDP configuration, and a time range, and returns up to 100 results per page. To narrow a large result, shorten the time range or add filters.

## Decision logs

A decision log shows the input the PDP received and the result that Open Policy Agent (OPA), the policy engine inside the PDP, returned. The Permit policy that runs in OPA adds a human-readable `reason` that explains why the PDP allowed or denied the request.

![Decision log panel in the Audit Log screen showing the request input, the decision, and the reason](/ui-videos/how-to/audit-logs/decision-log.png)

This `reason` is from a denied check where no attribute-based access control (ABAC) rule grants the user the `delete` permission on a `task`:

```json
{
  "reason": "user 'c2fc4a07-7edf-48fb-8fd8-e4989e103a77' does not match any rule that grants him the 'delete' permission on the given resource of type 'task'"
}
```

The decision log includes the `reason` when [Debug Mode](/how-to/use-audit-logs/debug-mode) is on. Next to the `reason`, the decision log has a `code` that names the cause of a denial, and a `support_link` to the page that explains it.

### Denial codes in decision logs

| Code | Meaning |
|---|---|
| [`no_such_resource`](/how-to/use-audit-logs/errors/no_such_resource) | The resource type in the check doesn't exist. |
| [`no_such_action`](/how-to/use-audit-logs/errors/no_such_action) | The action isn't defined on the resource type. |
| [`no_such_tenant`](/how-to/use-audit-logs/errors/no_such_tenant) | The tenant in the check doesn't exist. |
| [`user_not_synced`](/how-to/use-audit-logs/errors/user_not_synced) | The user key doesn't match any user in Permit. |
| [`no_user_roles`](/how-to/use-audit-logs/errors/no_user_roles) | The user has no role in any tenant. |
| [`no_role_in_tenant`](/how-to/use-audit-logs/errors/no_role_in_tenant) | The user has roles in other tenants, but not in the checked tenant. |
| [`no_permission`](/how-to/use-audit-logs/errors/no_permission) | None of the user's roles grants the action. |
| [`no_matching_usersets`](/how-to/use-audit-logs/errors/no_matching_usersets) | The user matches no ABAC user set. |
| [`no_matching_resourcesets`](/how-to/use-audit-logs/errors/no_matching_resourcesets) | The resource matches no ABAC resource set. |
| [`no_matching_rules`](/how-to/use-audit-logs/errors/no_matching_rules) | No ABAC rule grants the action between the matched sets. |
| [`cloud_pdp_not_supporting_abac`](/how-to/use-audit-logs/errors/cloud_pdp_not_supporting_abac) | The check reached the Cloud PDP, and the environment uses ABAC. |
