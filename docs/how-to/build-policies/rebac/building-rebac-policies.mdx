Build a relationship-based access control (ReBAC) policy in the Permit.io dashboard and enforce it with `permit.check()`. This guide is for developers who know their application's resource hierarchy and want to model it in Permit. For the concepts (resource roles, role derivations, and relationship tuples), read the [ReBAC overview](/how-to/build-policies/rebac/overview) first.

## Before you start

- A Permit.io account with a project and an environment. See the [Quickstart](/quickstart).
- A map of your resources and the relationships between them. Draw each resource type as a node and each relationship as an edge, for example: a `Folder` is the parent of a `File`. Mark which relationships are hierarchies (parent and child) and which are groupings (members of a team).
- A list of the permissions each relationship grants, for example: the owner of a folder can edit every file in it.

:::tip Google Zanzibar and Permit
Permit's implementation of relationship-based access control (ReBAC) follows the tuple convention in the [Google Zanzibar paper](https://www.permit.io/blog/what-is-google-zanzibar).
Tuples describe resources, instances, and roles with notation such as `resource:instance`, `resource#role`, and `resource:instance#role`.

For example, the moderator role on the `general` chat room is written as:

`room:general#moderator`
:::

## Build the policy in the Policy Editor \{#using-the-policy-editor-to-create-rebac-enforcements}

Create the schema on the **Policy** screen in this order: resources, relations, resource roles, and role derivations. Then add instance data on the **Directory** screen.

### 1. Create resources \{#creating-resources}

A resource is a type of object users act on, such as a folder, a module, or a project. On the **Resources** tab of the Policy screen, create a resource for each type in your map, with the actions users can perform on it.

### 2. Create resource relations \{#create-resource-relations}

A relation defines how two resource types connect, such as `Folder` is parent of `File`. Add relations in the **ReBAC Options** of a resource. Later, you create relationships (also called relationship tuples) between specific instances based on these relations.

![Relations form with Folder is Parent of File and Project is Parent of Folder, and a diagram of the Folder to File relation](/ui-videos/rebac/resource-relationship.png)

:::info `parent` relation
A resource can't be the parent of itself. To relate a resource to itself, use another relation type, such as `owner` or `container`.
:::

### 3. Add roles to resources \{#adding-roles-to-resources}

A resource role, such as `Folder#Admin`, grants permissions on the instances of one resource. In the **ReBAC Options** of each resource, add the roles users can hold on its instances. Then grant each resource role its actions in the Policy Editor.

### 4. Define role derivations \{#defining-role-derivations}

A role derivation grants a user a role on an instance because of a role they hold on a related instance. For example, a user with `Folder#Admin` gets `File#Editor` on every file whose parent is that folder.

![Role derivation diagram where Folder#Admin derives File#Editor when a Folder is the parent of a File](/ui-videos/rebac/define-role-derivation.png)

### 5. Create resource instances and relationships \{#creating-a-resource-instance}

A resource instance is a specific object of a resource type. For example, `document` is a resource, and `Document A` is one of its instances.

#### Connect resource instances with a relationship \{#connecting-resource-instances-with-a-relationship}

A relationship (relationship tuple) connects two specific instances, based on a relation in the policy schema. For example, you place a specific `document` in a specific `folder`, or a specific `account` under a specific `company`.

1. Open the **Directory** screen and select the **Instances** tab.
2. Create or edit a resource instance.
3. Add a relationship between the instance and another instance. The other instance can be of a different resource type.

![Resource instance form with a relationship to another resource instance](/ui-videos/rebac/relationship-between-instances.png)

You can also create resource instances and relationship tuples with the Permit API and SDKs. See [Sync application data into Permit](/overview/sync-applications-data).

## Enforce the policy in your code \{#enforcing-your-policies-in-your-code}

In your application, call `permit.check()` with a resource instance. The policy decision point (PDP) evaluates the user's direct and derived roles on that instance.

![Diagram of Permit sending a policy update with the Folder to File role derivation to the authorization microservice, which answers a permit.check() call from your application](/ui-videos/rebac/enforcing-rebac.png)

The following check asks whether a user can perform the `assign` action on a specific member group. The code builds the instance key at runtime:

```javascript
await permit.check(userId, "edit", `file:${fileKey}`);
```

### permit.check() parameters \{#function-permitcheck}

`permit.check()` returns `true` when the user can perform the action on the resource, and `false` otherwise.

| Parameter | Value in the example | Description |
|---|---|---|
| User | `userId` | The key of the user whose permissions you check. |
| Action | `"assign"` | The action the user wants to perform, here assigning a member to a group. |
| Resource | `` `member_group:${group}` `` | The resource instance, in `resource_type:instance_key` format. The template string inserts the key of the group instance. |

### Other ways to pass the resource instance \{#variant-permitcheck-rebac-calls}

Pass a fixed instance key:
```javascript
await permit.check(userId, "edit", "file:readme");
```
Pass an object with the resource type, the instance key, and more data such as the tenant, as in role-based access control (RBAC) checks:
```javascript
await permit.check(userId, "edit", { type: "file", key: "readme", tenant: "default" });
```

### Verify the policy

Run a check for a user who has a derived role, and one for a user who doesn't:

- A user with a role on the parent instance gets `true` for an action that the derived role allows on the child instance.
- After you delete the relationship between the two instances, the same check returns `false`.

To see why a check was allowed or denied, open the **Audit Log** in the Permit dashboard. For more check options, see [Check permissions with permit.check()](/how-to/enforce-permissions/check).
