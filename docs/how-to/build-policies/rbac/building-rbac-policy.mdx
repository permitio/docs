Build a role-based access control (RBAC) policy in the Permit.io dashboard, assign a role to a user, and confirm the permission with a check. This tutorial is for developers building their first policy in Permit.

The tutorial builds this policy:

:::info Example policy
**An administrator in a company can perform all actions on documents.**
:::

## Prerequisites

- A Permit.io account with a project and an environment. See the [Quickstart](/quickstart).
- To run the check at the end: your environment API key ([Get your API key](/overview/get-api-key)) and a Permit SDK connected to a policy decision point (PDP). See [Check permissions with permit.check()](/how-to/enforce-permissions/check).

For the definitions of roles, resources, and actions, see [RBAC components](/how-to/build-policies/rbac/components).

## 1. Create the admin and customer roles \{#creating-roles-top-level-in-the-ui}

Create two top-level roles, `Admin` and `Customer`. A top-level role applies to a user across a whole tenant.

1. In the Permit dashboard, open **Policy** and select the **Roles** tab.
2. Create a role with the name `Admin`. The key is the identifier you use in your code.
3. Click **Save**.
4. Repeat for a role named `Customer`.

### Create the Admin role \{#creating-the-admin-role-top-level-within-the-ui}

![New Role panel on the Roles tab with the name Admin, the key Admin, and an optional description](/img/updated/rbac/rbac-1.png)

### Create the Customer role \{#creating-the-customer-role-within-the-ui}

![New Role panel on the Roles tab for the Customer role](/img/updated/rbac/rbac-2.png)

## 2. Create the document resource \{#adding-a-resource}

Every resource you create is available to every role in the environment. Until you create a resource, the Policy Editor has no permissions to show.

![Policy Editor with no resources, prompting you to create a resource](/img/updated/rbac/rbac-3.png)

1. Select the **Resources** tab and create a resource.
2. Enter the name `document`.
3. Add the actions `read`, `create`, `update`, and `delete`. Press Enter after each action.
4. Click **Save**.

### Create a resource in the dashboard \{#creating-a-resource-within-the-ui}

![New Resource panel with the name document, the key document, and the read, create, update, and delete actions](/img/updated/rbac/rbac-4.png)

After you save the resource, the Policy Editor lists the `document` actions under each role:

![Policy Editor block view with the Admin and Customer roles, each listing the create, delete, read, and update actions of the document resource](/img/updated/rbac/rbac-5.png)

## 3. Grant permissions to the roles \{#assigning-permissions-to-actions}

1. Select the **Policy Editor** tab.
2. Under the `Admin` role, select `create`, `delete`, `read`, and `update` for `document`.
3. Under the `Customer` role, select the actions customers need, such as `read`.
4. Save your changes.

### Roles with selected permissions \{#roles-with-specific-selected-permissions}

![Policy Editor with create, delete, read, and update selected on document for both the Admin and Customer roles](/img/updated/rbac/rbac-6.png)

## 4. Create a user and assign the Admin role \{#creating-a-user--assigning-a-role}

### Open the Directory screen \{#the-users}

Select **Directory** in the dashboard navigation. The screenshot shows an earlier version of the dashboard, where the same screen is labeled **Users**.

![Dashboard navigation with the Users item selected](/img/updated/rbac/rbac-7.png)

### Assign a role to the user \{#assigning-a-role-to-a-user}

1. Click **Add user**.
2. Enter a key, such as `john@permit.io`. You use the key to identify the user in `permit.check()`.
3. Optionally, enter an email, first name, and last name.
4. Select a tenant, such as **Default Tenant**.
5. Under **Top Level Access**, add the `Admin` role.
6. Click **Save**.

![Create a new user panel with a key, email, first and last name, Default Tenant selected, and the Admin role under Top Level Access](/img/updated/rbac/rbac-8.png)

### Confirm the role assignment \{#a-user-with-the-admin-role}

The Directory screen lists the user with the `Admin` role in the **Top Level Access** column.

![Directory screen for Default Tenant listing John Smith with the Admin role under Top Level Access](/img/updated/rbac/rbac-9.png)

## 5. Check the permission

From your application, call `permit.check()` with the user key, an action, and the resource key. For example, `permit.check("john@permit.io", "delete", "document")` returns `true`, because the `Admin` role can delete documents. For a user without a role that allows the action, the check returns `false`.

For SDK setup and full examples, see [Check permissions with permit.check()](/how-to/enforce-permissions/check).

## Multi-tenancy RBAC in Permit \{#multi-tenancy-rbac-in-permit}

Top-level roles and their permissions are defined per environment and shared by every tenant in the environment. Role assignments are per tenant: you can assign a user the `Admin` role in one tenant and the `Customer` role in another. The user then has admin permissions only in the first tenant.

To learn more, see [Multi-tenant authorization](/concepts/multi-tenant-authorization).

## Role attributes \{#role-attributes}

Role attributes are metadata on roles, such as a tier or a region. Use them to tag roles and filter roles through the API, for example to separate the roles that belong to each tenant. To define role attributes, see [Define role attributes](/how-to/build-policies/abac/defining-attributes#define-role-attributes). To filter roles by attribute, see [List tenant roles filtered by role attributes](/api/examples/filter-role-associations#list-tenant-roles-filter-by-role-attributes).
