Add your identity provider's JSON Web Key Set (JWKS) to a Permit environment. Permit uses the public keys in the JWKS to verify the JSON Web Tokens (JWTs) that your frontend sends to Permit, for example when users sign in to [Permit Elements](/embeddable-uis/embedding-elements) with your own identity provider. This page is for developers who set up frontend authentication to Permit.

## Prerequisites

- A Permit.io account with access to the environment you configure
- The JWKS object or the JWKS URL of your identity provider ([Fetch a JWKS from your identity provider](/how-to/enforce-permissions/url-mapping/fetching-jwks))

A JWKS belongs to one environment. Repeat these steps for each environment your frontend uses.

## 1. Open Settings in the Permit dashboard \{#1-navigate-to-the-settings-from-the-left-hand-navigation-panel-in-the-permit-dashboard}

In the [Permit dashboard](https://app.permit.io), click **Settings** in the left navigation panel.

![Settings item in the left navigation panel of the Permit dashboard](/img/url-mapping/settings.png)

## 2. Open JWKS Config \{#2-click-on-the-jwks-config}

Click **JWKS Config**.

![JWKS Config tab on the Settings page of the Permit dashboard](/img/url-mapping/jwks-config.png)

## 3. Select the environment \{#3-select-the-environment-you-want-to-configure-and-add-your-jwks}

Select the environment to configure.

![Environment selector on the JWKS Config page](/img/url-mapping/select-env.png)

## 4. Add the JWKS object or the JWKS URL \{#paste-your-whole-jwks-object-inside-the-json-editor}

Add the JWKS in one of two ways:

- **JWKS object.** Paste the whole JWKS object into the JSON editor. The root of the object is the `keys` array.
- **JWKS URL.** Enter an `https` URL that returns a valid JWKS object with `keys` at the root. Use a URL when your identity provider rotates signing keys, so Permit fetches the current keys instead of a copy that goes stale.

Then click **Save**.

![JSON editor on the JWKS Config page, with a pasted JWKS object](/img/url-mapping/json-editor.png)

Each key in `keys` describes one public key. The `kid` value is the unique identifier of the key and matches the `kid` in the header of the JWTs the key signs. The following example shows the fields of an RS256 key, with the key values masked:

```json
{
    "keys": [
        {
            "alg": "RS256",
            "kty": "RSA",
            "use": "sig",
            "n": "****",
            "e": "****",
            "kid": "****",
            "x5t": "****",
            "x5c": [
                "****"
            ]
        }
    ]
}
```

## Verify the JWKS configuration

To confirm that Permit stored the JWKS, request the environment with `GET /v2/projects/{proj_id}/envs/{env_id}` and check the `jwks` field of the response. To test a JWKS URL, call `POST /v2/projects/{proj_id}/envs/{env_id}/test_jwks` with the URL in the `url` query parameter.

To confirm that the JWKS contains the key for your tokens, compare the `kid` in the header of one of your JWTs with the `kid` values in `keys`.

## Configure a JWKS with the Permit API

To configure a JWKS without the dashboard, update the environment with `PATCH /v2/projects/{proj_id}/envs/{env_id}` and set the `jwks` field. The `jwks` field accepts a `jwks` object with a `keys` array, or a `url`, and an optional `ttl`: the time in seconds Permit caches the JWKS (default `600`). See the [Environments API reference](https://api.permit.io/v2/redoc#tag/Environments).

## Set the user key claim \{#user-key-claim}

When a user logs in to Permit Elements with `LoginMethod.frontendOnly`, or approves an Elements invite with their JWT, Permit reads the user's Permit key from one claim of the JWT. That claim is `sub` unless you set another one on the environment. If your identity provider puts the user key in a different claim, set `user_key_claim` in the `jwks` field:

```bash
curl -X PATCH 'https://api.permit.io/v2/projects/{proj_id}/envs/{env_id}' \
-H 'authorization: Bearer API_SECRET_KEY' \
-H 'Content-Type: application/json' \
-d '{"jwks": {"url": "<YOUR_JWKS_URL>", "user_key_claim": "<CLAIM_NAME>"}}'
```

- **Name only a claim your identity provider sets.** Permit refuses claims that the user or the client can set, such as an OIDC `nonce`, `name` or `aud`. A custom claim filled from profile data the user can edit is just as unsafe.
- **The value must be a non-empty string or an integer.** Permit reads an integer as its decimal string.
- **`email` needs a verified email.** Permit accepts the `email` claim only from a token whose `email_verified` claim is the JSON boolean `true`. Tokens without `email_verified`, such as Entra ID's, or with the string `"true"` can't use it. A user keyed by email changes key when their email changes at the identity provider.
- **On a shared identity provider, also set `issuer` and `audience`.** For a JWKS URL on Entra ID, Google, Apple, Salesforce, LinkedIn or Facebook, a request that sets or changes `user_key_claim` needs `issuer` and `audience` in the same configuration.
- **Changing the claim changes which user each token logs in as.** Users whose Permit key matches the old claim's value don't match the new one.

To go back to `sub`, send `"user_key_claim": null`. Removing the whole configuration with `"jwks": null` removes it as well.

`permit.elements.login()` and the invite approval request also accept a `userKeyClaim` (`user_key_claim`) parameter. Set the claim on the environment instead. If you pass the parameter, it must be `sub` or the environment's `user_key_claim`. When the environment sets `user_key_claim`, Permit rejects any other value.
