# Workflows & Rules

Egress policy is organized into **API workflows**. A workflow is a named unit of access — a bundle of the domains an agent may reach and the rules that govern them. Every agent token is bound to exactly **one** workflow, so an agent can only ever make the outbound calls that workflow allows.

The proxy is **deny-by-default**: if a request doesn't match a domain and rule in the token's workflow, it is denied — before any credential is injected or any connection is made. You grant access by adding domains and rules to a workflow.

:::note Where you author workflows
Workflows are created and edited in the [dashboard](https://app.agent.security) under **Proxy → Workflows**. There is no CLI command for authoring workflows yet — the `asg` CLI handles everything around them (enabling the proxy, storing credentials, minting workflow-bound tokens).
:::

## How a workflow is structured

A workflow has three levels:

```text
Workflow  "ship_pr"
├── Domain  *.github.com
│   ├── Rule  read_repo      GET/HEAD   → low trust
│   └── Rule  push_commit    POST/PUT   → medium trust   (injects credential "github")
└── Domain  api.slack.com
    └── Rule  post_message   POST       → medium trust   (injects credential "slack")
```

- **Workflow** — the top-level unit an agent token binds to. Give it a clear name (e.g. *"Ship a PR"*) and slug.
- **Domain** — a hostname or glob the workflow allows (`api.stripe.com`, `*.github.com`). A request's target host must match one of the workflow's domains, or it's denied.
- **Rule** — inside a domain, a rule narrows *which* requests to that domain are allowed and at what trust level.

## What a rule matches

Each rule matches a request on these dimensions:

| Field | Matches | Example |
| --- | --- | --- |
| **Path** | The request path (glob). Optional — leave blank to match all paths on the domain. | `/v1/customers/*` |
| **Method** | One or more HTTP method **classes**: `read`, `write`, `delete`, or `all`. | `read`, `write` |
| **Protocol** | `http` (default), `websocket`, or `any`. | `http` |

The **method class** groups HTTP verbs by risk so you don't enumerate them: `read` covers safe methods like `GET` and `HEAD`, `write` covers `POST`/`PUT`/`PATCH`, `delete` covers `DELETE`, and `all` matches any method. A rule can select several classes at once.

## What a rule grants

Rules are **allow-only**: a matching request is authorized when the caller's trust level is **at least** the rule's required trust. There is no separate "block" or "require-approval" action — you control access by choosing which domains and rules exist and what trust each one demands.

Each rule carries:

| Field | Purpose |
| --- | --- |
| **Required trust** | The minimum trust the caller must hold for this rule to authorize the request — `low`, `medium`, or `high`. Choose **Auto** to derive it from the method class: `read → low`, `write → medium`, `delete`/`all → high`. |
| **Credential** | An optional stored [credential](./credentials) to inject into matched requests, so the agent never holds the secret. |
| **TLS mode** | For HTTPS, whether the connection is `passthrough` (host-level only) or `intercept` (decrypt and apply the rule in full). See below. |

Because trust is required per rule, a single workflow can grant an agent broad read access while gating writes and deletes behind a higher trust level that only a human's consent can supply. See [Authorization & Trust](./authorization) for how trust is granted and capped.

## HTTPS handling per rule

For HTTPS targets, each rule's **TLS mode** decides how deeply the proxy inspects the encrypted connection:

- **`passthrough`** (default) — the request is authorized at the domain level, then the encrypted tunnel is forwarded without decryption. No path matching, credential injection, or response scrubbing happens inside it.
- **`intercept`** — the proxy decrypts the connection (using a certificate authority issued for your host) and applies the rule in full, including path matching, credential injection, and response scrubbing.

See [Connecting Agents → HTTPS interception](./connecting-agents#https-interception) for how to enable intercept and trust the CA.

## Building a workflow

In **Proxy → Workflows**, create a workflow, add one or more domains, and add rules to each domain:

1. **Create the workflow** — name it for the job the agent does (*"Ship a PR"*, *"Reconcile invoices"*).
2. **Add a domain** — the hostname or glob the agent may reach.
3. **Add rules** — for each domain, add rules that pin the paths, methods, and required trust. Attach a credential where the proxy should inject a secret.
4. **Bind an agent** — mint a token for the workflow with [`asg proxy token create --workflow <slug>`](./cli), or have a human delegate it with [`asg proxy authorize --workflow <slug>`](./authorization#human-consent).

:::tip Start tight, then widen
Begin with the exact domains and paths your agents need at the lowest trust that works, and let deny-by-default handle everything else. Widening later as real traffic requires it is far easier than starting open and trying to lock down after the fact.
:::

## Human-in-the-loop on egress

For high-risk egress, the gateway can route a request to a human for approval before it's forwarded — the same [Human-in-the-Loop](/permit-mcp-gateway/human-in-the-loop) machinery it uses for MCP tool calls. This is an optional, per-host capability rather than a rule setting; [contact us](mailto:support@permit.io) to enable it for your account. When an approval is required, the request pauses at the proxy, your reviewers are notified (email / Slack), and it proceeds only if a reviewer approves — otherwise it's denied (fail-closed). When an agent is driven by the CLI, approval outcomes are reported distinctly so automation can tell *"a human said no"* from *"blocked by policy"* from *"the request timed out."*
