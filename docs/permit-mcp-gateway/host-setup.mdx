This guide is for the admin who deploys Permit MCP Gateway for an organization. You create a host, import the MCP servers your team uses, give people access, connect MCP clients to the gateway, and plan how to roll the gateway out to more people and environments.

The examples use the organization Acme Corp, the host `acme-zesty-magenta-11.agent.security`, and the DeepWiki MCP server at `https://mcp.deepwiki.com/mcp`.

## What is a host?

A **host** is an instance of Permit MCP Gateway. Each host gets its own subdomain (for example, `acme-zesty-magenta-11.agent.security`) and is isolated from other hosts:

| A host has its own | What that means |
| --- | --- |
| Subdomain | A unique gateway URL that MCP clients connect to. |
| Permit environment | Policies, roles, and resource definitions are scoped to the host. |
| Users and sessions | Sign-in, consent, and audit trails are isolated per host. |
| MCP servers | The host has its own imported upstream servers, each with its own tools, trust levels, and intent. |
| Settings | Authentication methods, Dynamic MCP Connections, Agent Identity, and the other sections of **Settings** apply to one host. |

Each host uses one Permit environment, and each environment can be used by only one host. You can't change a host's environment after you create the host. To use a different environment, delete the host and create a new one.

## Prerequisites

- A [Permit.io](https://app.permit.io) account. You sign in to the admin dashboard with it.
- The URL of each upstream MCP server your team uses (for example, `https://mcp.deepwiki.com/mcp`), and an account with that provider if the server requires sign-in.
- The email addresses of the first people you want to give access.

## Set up a host step by step \{#step-by-step-host-setup}

### 1. Sign in to the admin dashboard \{#1-sign-into-the-platform}

Go to [app.agent.security](https://app.agent.security) and click **Sign in with Permit.io**. There is no separate sign-up and no API key to paste. The organizations you see come from your Permit account.

### 2. Create or select an organization \{#2-connect-your-permitio-organization}

The organization switcher at the top of the sidebar shows the current organization. To use another organization you belong to, open the switcher and select it.

To create a new organization:

1. Open the organization switcher and click **+** (**Add organization**). The **Organizations** page opens.
2. Click **Create Another Organization**. If your account has no organizations yet, the page shows the form right away.
3. Enter an **Organization name**, such as `Acme Corp`, and an **Organization key** of lowercase letters, numbers, and dashes, such as `acme-corp`.
4. Click **Create**. If your account had no organizations, the button is **Create Organization**.

The admin dashboard creates the organization in Permit. For the layout of the dashboard, see the [Admin dashboard reference](/permit-mcp-gateway/platform).

### 3. Create a host

1. Open **Hosts** in the sidebar and click **Create Host**. You can also use **Add host** in the host chip menu in the top bar.
2. Fill in the fields:

   | Field | What to enter |
   | --- | --- |
   | **Subdomain** | A prefix that identifies the host's purpose, such as `acme`, `acme-staging`, or `engineering`. The dashboard adds a generated suffix, such as `-zesty-magenta-11.agent.security`, so the subdomain is unique. You can't change the suffix. |
   | **Project** | The Permit project that contains the environment you want to use, such as **Default Project**. |
   | **Environment** | **+ Create new environment** (the default), or one of the **Existing environments**. For a new environment, enter an **Environment Name**, such as `Acme Gateway`, and an **Environment Key**, such as `acme-gateway`. The key must start with a letter. |
   | **Allow Dynamic MCP Connections** | On by default. When on, people can connect to any MCP server URL, not only the servers you import. See the warning below. |

   ![Create Host form with the acme prefix, Default Project, a new Acme Gateway environment, and Allow Dynamic MCP Connections on](/img/agent-security/platform/create-host-filled.png)

3. Click **Create Host**. The **Confirm Host Creation** dialog shows the full subdomain and the environment, marked **(will be created)** for a new one.
4. Click **Create Host** in the dialog.

![Confirm Host Creation dialog with the subdomain acme-zesty-magenta-11.agent.security and the Acme Gateway environment](/img/agent-security/platform/create-host-confirm.png)

The environment is permanent. The dialog warns that "The environment attached to a host cannot be changed after creation." If you pick an environment another host already uses, the dashboard refuses it: "Each environment can only be used by one host."

:::warning
**Allow Dynamic MCP Connections** is one-way. After a host allows dynamic connections, you can't turn the setting off. To keep the host limited to the MCP servers you import, switch it off before you click **Create Host**.
:::

The new host becomes the current host, and the **Hosts** page shows its card with a **Current** badge. Each MCP server you import gets its own URL on the host, in the form `https://<subdomain>.agent.security/mcp/<server_key>`.

### 4. Import MCP servers

Import each upstream MCP server your team needs:

1. Open **MCP Servers** and click **Create Server**. The **Import MCP Server** page opens on the **Connect** step.
2. Enter the upstream MCP server URL, such as `https://mcp.deepwiki.com/mcp`, and click **Connect**. The gateway probes the server to discover its tools.

   ![Import MCP Server on the Connect step with the DeepWiki URL](/img/agent-security/platform/import-connect.png)

3. If the upstream server requires a sign-in, the wizard shows **Authorization Required**. Click **Sign in to MCP Server**, sign in on the provider's authorization page, and grant access. The browser returns to the wizard to finish the import. Click **Change Server** to go back and enter another URL.

   ![Authorization Required step for an MCP server that needs a sign-in, with Change Server and Sign in to MCP Server](/img/agent-security/platform/import-auth-required.png)

   If the provider doesn't support automatic client registration, the wizard shows **Manual OAuth Configuration Required** instead. Register an OAuth app with the provider using the redirect URI the wizard shows, then enter its **Client ID** and, if it has one, its **Client Secret**.

4. On the **Review & Configure** step, fill in the **Server Configuration** card:

   | Field | What to enter |
   | --- | --- |
   | **Server Key** | A unique identifier of lowercase letters, underscores, and numbers, such as `deepwiki`. The key is part of the server's MCP URL. |
   | **Display Name** | The name people see, such as `DeepWiki`. |
   | **Description (optional)** | What the server provides. |
   | **Workflow intent (optional)** | Up to 500 characters. The Guardian grades each tool call against this intent when the Guardian is on. See [Write a workflow intent](#write-a-workflow-intent). |

5. In **Tools to Import**, choose the tools to import with their checkboxes, or use **Select All** and **Deselect All**. For each tool you can:
   - Change its trust level in the trust select. A level you change shows **(custom)**.
   - Turn on its **HITL** switch to require an admin's approval before each call. See [Human-in-the-loop approvals](/permit-mcp-gateway/human-in-the-loop).

   The gateway classifies each tool into a trust level by keywords in the tool name:

   | Trust level | Classification | Examples |
   | ----------- | -------------- | -------- |
   | **Low** | Read-only (default) | `get_issues`, `list_repos`, `read_wiki_contents` |
   | **Medium** | Write operations | `create_issue`, `update_record`, `send_message` |
   | **High** | Destructive operations | `delete_repo`, `remove_member`, `destroy_environment` |

   The [trust level classification reference](/permit-mcp-gateway/platform#tool-auto-discovery-and-trust-level-classification) lists every keyword.

   ![Review and Configure step for DeepWiki with the server key, display name, description, workflow intent, and three tools, one set to Medium](/img/agent-security/platform/import-review.png)

6. Click **Import Server & N Tools**, where N is the number of selected tools.

The wizard shows **Import Successful** with the **Server Key**, the number of **Tools Imported**, and how many **Need Approval**. A **Server Created Successfully** dialog offers to give people access right away: select a person, set **Max trust**, and click **Grant Access**, or click **Skip for Now**. Then click **View Server** to open the server's page, or **Import Another** for the next server.

![Server Created Successfully dialog over the Import Successful step for DeepWiki](/img/agent-security/platform/import-add-users.png)

Repeat these steps for each MCP server. To change a server after import, see [Manage an MCP server after import](#manage-an-mcp-server-after-import).

### 5. Review the host settings \{#5-configure-authentication-methods}

Open **Settings** in the sidebar. Settings apply to the current host. Check these sections before you invite people:

- **Authentication Methods**: how people sign in during the consent flow. **Email / Password** is on by default. You can add **Email OTP**, **Passkeys**, **Google**, **GitHub**, **Microsoft**, **Enterprise OIDC**, or **Enterprise SAML**, and a **Global Email Domain Restriction**. See the [Authentication methods reference](/permit-mcp-gateway/authentication-methods).
- **Dynamic MCP Connections**: whether people can connect to MCP server URLs you haven't imported. The setting is one-way.
- **Agent Identity**: semantic identity, agent intent, and the Guardian, three layers that check every agent call. See [Check agent identity and intent](/permit-mcp-gateway/advanced-features).
- **Sign-in check for people's approvals** and **Expiring consent grants**: timing for people's approvals and for grant expiry warnings.
- **Upstream Authentication (JWT)**: the JWKS URL your upstream MCP servers can use to verify that a request came through the gateway.

![Authentication Methods section in Settings with Email / Password and Global Email Domain Restriction](/img/agent-security/platform/settings-auth-methods.png)

For enterprise teams, configure **Enterprise SAML** or **Enterprise OIDC** and add a domain restriction so only addresses such as `@acme.com` can sign in. The [Authentication methods reference](/permit-mcp-gateway/authentication-methods) covers each method, identity provider setup for Okta, Microsoft Entra ID, and Google Workspace, callback URLs, domain restrictions, and forced SSO domains. For every section of Settings, see [Settings](/permit-mcp-gateway/platform#settings).

### 6. Grant users access to MCP servers

People have **no access** to any MCP server until you grant it. Each grant sets a **max trust level**: the highest level the person can grant an agent during consent.

To grant access from the MCP server's page:

1. Open **MCP Servers** and select the server.
2. In **Authorized Humans**, click **Grant Access**.
3. In the **Grant Human Access** dialog, pick the person on the **Existing User** tab, or enter an email address on the **Invite by Email** tab for someone who hasn't signed up yet.
4. Set **Max trust**. The default is **Low**.
5. Click **Grant Access**.

You can also grant access from the person's page on **Humans**. For the full procedure and how the max trust level combines with the person's consent, see [Grant access to an MCP server](/permit-mcp-gateway/managing-humans-and-agents#granting-access-to-an-mcp-server).

:::warning
If a person connects before you grant access, the consent screen says "No MCP servers available. Contact your administrator to grant you access to MCP servers." On a host that allows dynamic MCP connections, the person can still enter a custom MCP server URL. Grant access before you share the MCP URL.
:::

### 7. Share the MCP URL with your team \{#7-share-the-host-url-with-your-team}

Each MCP server's page has an **MCP URL** card with the server's gateway URL and a snippet for each client:

1. Open **MCP Servers** and select the server.
2. Copy the URL from the **MCP URL** card, such as `https://acme-zesty-magenta-11.agent.security/mcp/deepwiki`.
3. Pick the client tab, **Cursor / VS Code**, **Claude Desktop**, or **Claude Code**, and share its snippet.

![MCP URL card for DeepWiki with the server URL and the Cursor / VS Code snippet](/img/agent-security/platform/server-mcp-url.png)

The clients take the URL directly. In each example, replace `acme-zesty-magenta-11` with your host's subdomain and `deepwiki` with your server key.

**Cursor:** add the snippet to `.cursor/mcp.json`.

```json
{
  "mcpServers": {
    "deepwiki": {
      "url": "https://acme-zesty-magenta-11.agent.security/mcp/deepwiki"
    }
  }
}
```

**VS Code:** the dashboard shows one snippet for Cursor and VS Code. `.vscode/mcp.json` takes a top-level `servers` key instead of `mcpServers`, so rename the key when you paste the snippet into VS Code.

**Claude Desktop:** add the same `mcpServers` snippet to the Claude Desktop config file, `~/Library/Application Support/Claude/claude_desktop_config.json` on macOS or `%APPDATA%\Claude\claude_desktop_config.json` on Windows.

**Claude Code:** run this command.

```bash
claude mcp add deepwiki --transport http "https://acme-zesty-magenta-11.agent.security/mcp/deepwiki"
```

When the host requires agent identity, the **MCP URL** card also shows an **Agent Identity Verification** snippet. Ask your team to paste it into `CLAUDE.md` (Claude), `.cursorrules` (Cursor), or `.github/copilot-instructions.md` (Copilot). See [Check agent identity and intent](/permit-mcp-gateway/advanced-features).

#### Server URLs and the host-level URL \{#pre-selected-mcp-server-urls}

A host accepts two kinds of MCP URL:

| URL | What the person sees during consent |
| --- | --- |
| `https://<subdomain>.agent.security/mcp/<server_key>` | The consent flow connects to that server without a server list. If the person has no access to it, the consent screen says `MCP server "<server_key>" is not available or you don't have access to it.` |
| `https://<subdomain>.agent.security/mcp` | The consent screen lists the servers the person has access to, and the person picks one. |

Give each team the URLs of the servers it uses, for example `https://acme-zesty-magenta-11.agent.security/mcp/deepwiki` for the Acme web team.

The host-level URL also accepts an `upstream_mcp` query parameter with an upstream server URL, such as `https://acme-zesty-magenta-11.agent.security/mcp?upstream_mcp=https://mcp.deepwiki.com/mcp`. If the URL matches an imported server the person has access to, the consent screen selects it. If it doesn't match, a host that allows dynamic MCP connections connects to it as a dynamic server, and a host that doesn't shows "This host does not allow connecting to dynamic MCP servers. Contact your administrator."

### 8. Verify the host works

1. Connect an MCP client with one of the snippets in step 7, for example the DeepWiki URL.
2. Sign in on the host and complete the [consent flow](/permit-mcp-gateway/consent-service) at **Low** trust.
3. In the admin dashboard, open **Agents**. The person appears with the MCP client under them, such as **Acme Research Agent**, and its sessions.
4. Ask the agent to call a read-only tool, such as `read_wiki_structure`. The call succeeds.
5. Ask the agent to call a tool above its trust level, such as `ask_wiki_question` set to Medium. The gateway refuses the call: "Permission denied: tool 'ask_wiki_question' is not allowed at your current trust level."
6. Check both calls in the Dashboard's **Live activity** feed, or on the agent's **Audit Logs** tab. See [Audit logs](/permit-mcp-gateway/audit-logs).

## Manage an MCP server after import

Open **MCP Servers** and select a server. The **Overview** tab has a card for each part of the server.

### Write a workflow intent

The **Intent** card shows what the Guardian grades calls to this server against, and whether the Guardian is on for the host. To change the intent, click **Edit intent**, edit the **Workflow intent** (up to 500 characters), and click **Save intent**. Without an intent, the Guardian grades each call against the person's task when the person set one, and otherwise against the agent's semantic identity, the 12 words it registered.

![Intent card in edit mode with the Workflow intent box and Save intent](/img/agent-security/platform/server-intent-edit.png)

Describe what the server is and what agents do with it, not only the rule. For example, an intent that says only "Read-only research on public GitHub repositories" can make the Guardian refuse legitimate DeepWiki calls, because DeepWiki isn't named. This wording lets those calls pass:

```text
DeepWiki hosts generated documentation for public GitHub repositories. Agents read those wiki pages and ask questions about how open-source codebases such as React and Next.js work. Read-only; no writes.
```

Test a new intent with [Dry Run](#test-a-call-with-dry-run) before people rely on it.

### Change tools

The **Tools** card lists every tool. For each tool you can:

- Change its trust level in the trust select. Changing a tool's level needs the admin or write access level in your Permit organization.
- Turn its **HITL** switch on to require an admin's approval before each call.
- Click **Dry Run** to open the **Dry Run** tab with the tool selected.
- Delete it with the trash button, then confirm in the **Delete tool** dialog.

**Re-sync Tools** reads the tool list from the upstream server again and reports the result, such as "Sync complete: 1 added, 0 removed, 2 unchanged." If the upstream server needs a new sign-in, the card shows **Authenticate & Re-sync**. **Add Tool** adds a tool by hand with a **Key**, **Name**, **Description**, and **Trust Level**.

![Tools card for DeepWiki with three tools, each with Dry Run, a HITL switch, and a trust select](/img/agent-security/platform/server-tools.png)

### Change the name, description, or upstream URL

The **Configuration** card edits the server's **Name**, **Description**, and **Upstream URL**. Click **Save Changes**. You can't change the server key, because it is part of the server's MCP URL.

When you change the upstream URL, a **Confirm URL Change** dialog explains the effects: existing sessions keep the old URL until they reconnect, new connections use the new URL, and the gateway tries to sync the tools. Click **Confirm Change**. You don't need to delete and import the server again.

![Configuration card with the DeepWiki name, description, and upstream URL](/img/agent-security/platform/server-configuration.png)

### Delete a server

In **Danger Zone**, click **Delete Server**, type the server key to confirm, and click **Delete Server**. Deleting a server removes its tools and permissions, and can't be undone.

## Test a call with Dry Run

The **Dry Run** tab tries a tool call the way an agent would make it. Nothing reaches the upstream server and no audit row is written. Only admins see the tab, and only on static servers. A host gets 10 dry runs a minute, shared by its admins.

1. On the server's page, open the **Dry Run** tab.
2. Pick the **Tool** and enter its **Arguments** as a JSON object, for example `{"repoName": "facebook/react", "question": "How does useEffect clean up between renders?"}`.
3. Under **Grade against**, pick **Server intent**, or **Server intent and a person's task** to add the task a person set at consent.
4. Optionally set **Person asks before writes**, the level the **Agent approved at** (**The tool's level**, **Low**, **Medium**, or **High**), and the **Agent's task sentence (checked only when enforced)**.
5. Click **Start Dry Run**.

The **What would happen** card shows each gate (**Trust ceiling**, **Approval rules**, **Ask before writes**, and **Judge**), the verdict, such as **Runs**, the judge's **Alignment** and **Confidence** scores with its reasoning, and the text the call was **Graded against**. When the Guardian is off for the host, the judge still grades the call, but its verdict doesn't count.

![Dry Run result for ask_wiki_question: every gate passes, alignment 0.85 and confidence 0.90](/img/agent-security/platform/server-dry-run.png)

## Static and dynamic MCP servers

The **MCP Servers** page has two tabs:

- **Static** servers are the servers an admin imports. You control their tools, trust levels, intent, approval rules, and who can access them.
- **Dynamic** servers appear when a person connects to an MCP server by URL during consent, on a host that allows dynamic MCP connections. A dynamic server's page has no **Intent**, **Configuration**, or **Danger Zone** card and no **Dry Run** tab. You can still change its tools' trust levels and the person's max trust.

For the full comparison, see [Dynamic servers](/permit-mcp-gateway/platform#dynamic-servers).

## Multi-host patterns

Each host has its own subdomain, Permit environment, users, and policies, so you can use separate hosts to separate environments or teams.

### Staging and production hosts \{#staging-vs-production}

Create separate hosts for staging and production to test configuration changes before they reach your team:

| Host | Subdomain | Permit environment | Purpose |
| ---- | --------- | ------------------ | ------- |
| Staging | `acme-staging-...` | `staging` | Test MCP server imports, trust levels, intents, and authentication settings before rollout. |
| Production | `acme-prod-...` | `production` | The live gateway for your team. |

In the staging host, you can:

- Import MCP servers and check trust level classifications.
- Write workflow intents and test them with Dry Run.
- Test authentication changes, such as adding SSO.
- Give a small group of people access for testing.

### Team-based hosts

Create a host per team when groups need different MCP servers, trust policies, or authentication methods:

| Host | Subdomain | Teams | MCP servers |
| ---- | --------- | ----- | ----------- |
| Engineering | `acme-eng-...` | Backend, Frontend, DevOps | GitHub, Linear, Sentry |
| Marketing | `acme-mktg-...` | Content, Analytics | HubSpot, Google Analytics |
| Security | `acme-sec-...` | InfoSec, Compliance | AWS, Datadog, PagerDuty |

Each host has its own:

- Imported MCP servers.
- Trust levels per tool.
- Authentication methods (for example, SSO for employees and email and password for contractors).
- Domain restrictions.

### Single host for small teams

A small organization can use one host with all MCP servers and all people. You can add hosts later.

## Onboard users at scale \{#user-onboarding-at-scale}

### Pre-grant access to all users \{#pre-granting-access-to-all-users}

Invite people by email before they sign up. On first connection, each person sees the MCP servers you granted and can finish the consent flow without waiting for you.

To onboard a team:

1. Collect email addresses, for example from your HR system or team roster.
2. For each MCP server, open its page, click **Grant Access** in **Authorized Humans**, and use the **Invite by Email** tab to add each person with a **Max trust**. Invited people appear on the **Humans** page under **Pending Invites** until they sign up.
3. Share the MCP URLs.

See [Grant access to an MCP server](/permit-mcp-gateway/managing-humans-and-agents#granting-access-to-an-mcp-server).

### Filter users with domain restrictions \{#domain-restrictions-for-automatic-user-filtering}

A domain restriction limits which email addresses can sign in. For example, set `acme.com` in **Global Email Domain Restriction**. People with `@acme.com` addresses can sign in, and the host rejects other addresses.

You can set domain restrictions:

- **Globally:** **Global Email Domain Restriction** applies to every authentication method on the host.
- **Per method:** **Email Domain Restriction** on one method. For example, with `acme.com` and `partner.com` in the global list, set `partner.com` on email and password so only `@partner.com` people sign in with a password.

A person must pass both the global list and the method's list. A list applies only when it isn't empty. Domains match exactly, so `acme.com` doesn't cover `contractor.acme.com`: list each subdomain you allow.

With enterprise SSO, add the domain to **Force SSO for Domains**. When a person types an `@acme.com` address on the sign-in screen, the host sends them straight to your identity provider. See [Domain restrictions](/permit-mcp-gateway/authentication-methods#domain-restrictions) for how global and per-method restrictions combine.

### Migrate from direct MCP server access \{#migrating-from-direct-mcp-server-access}

If your team connects MCP clients directly to upstream MCP servers (for example, `https://mcp.deepwiki.com/mcp`), move them to the gateway:

1. **Create a host** and import the MCP servers your team uses.
2. **Review trust levels.** Check that the classified trust levels match your security requirements, and change the ones that don't.
3. **Pre-grant access** to all current users with the right max trust levels.
4. **Share the server URLs.** Give each person the gateway URL of each server they use, in the form `https://<subdomain>.agent.security/mcp/<server_key>`.
5. **Update MCP client configurations.** Replace the upstream URL with the gateway URL in each person's client config.
6. **Have people complete the consent flow.** On first connection, each person signs in, selects a trust level, and approves the agent.

After the migration, every tool call goes through the gateway, which authenticates the person, authorizes the call, and writes an audit log entry.

:::tip
Migrate a small pilot group first and confirm the setup works before you move the full team. Direct MCP access can keep running in parallel during the transition.
:::

## Plan a phased rollout \{#rollout-guidance}

A phased rollout lets you find trust level and authentication problems with a few people before they affect the whole organization. The durations below are suggestions.

### Phase 1: Pilot (1 to 2 weeks) \{#phase-1-pilot-12-weeks}

**Goal:** Confirm that the gateway works with your MCP servers and clients, and that the setup meets your security requirements.

1. **Create one pilot host** linked to a non-production Permit environment.
2. **Import 1 or 2 MCP servers** your team already uses, such as GitHub or Linear.
3. **Grant access to 2 or 3 pilot users** with a **Low** (read-only) max trust level.
4. **Have pilot users connect their MCP clients** through the gateway and complete the consent flow.
5. **Review the audit logs.** Check that tool calls are logged and that allowed and denied decisions match your expectations.
6. **Test trust level enforcement.** Confirm that write and destructive tools are denied at Low trust, and that Medium trust allows write tools.

Questions to answer during the pilot:

- Did the import discover every tool you expected?
- Do the trust level classifications match your security expectations? Change the ones that don't.
- Does the consent flow work with your authentication method (SSO, OAuth, or email)?
- Do the audit log entries give you the information you need?

### Phase 2: Controlled expansion (2 to 4 weeks) \{#phase-2-controlled-expansion-24-weeks}

**Goal:** Add people and servers while keeping risk limited.

1. **Raise max trust levels for pilot users** based on Phase 1 results, for example from Low to Medium. Each person revokes their agent on **Your MCP agents**, then reconnects it from the MCP client and picks the higher level on the consent screen. Reconnecting while the grant is active doesn't show the consent screen. See [Give a user a higher trust level](/permit-mcp-gateway/managing-humans-and-agents#a-user-needs-higher-trust-than-i-originally-set).
2. **Import more MCP servers** as needed, each with a workflow intent tested in Dry Run.
3. **Onboard a larger group of people.** Pre-authorize them by email and share the MCP URLs.
4. **Restrict destructive tools.** Grant High trust only to the people who need it, and consider [human-in-the-loop approvals](/permit-mcp-gateway/human-in-the-loop) for sensitive tools.
5. **Review audit logs regularly** for access patterns, unexpected denials, and tools that need a different trust level.

### Phase 3: Production rollout \{#phase-3-production-rollout}

**Goal:** Move the whole team to the gateway with established security policies.

1. **Create a production host** linked to a production Permit environment, if the pilot used a staging environment.
2. **Move people** by pointing their MCP client configurations at the production gateway URLs.
3. **Remove direct MCP server connections** so all MCP traffic goes through the gateway.
4. **Configure SSO** (SAML or OIDC) and **domain restrictions**.
5. **Set up monitoring.** Decide who watches the Dashboard and reviews audit logs, and how your team responds to unexpected access patterns.

### Rollout principles

- **Start restrictive, then expand.** Begin with Low trust and raise it based on observed behavior.
- **Pilot before production.** Test configuration changes on a separate staging host.
- **Review before you broaden access.** Read the audit logs after each phase before you add people or servers.
- **Record trust level decisions.** Write down why each tool has its trust level, especially manual changes.
- **Remove direct access.** An MCP client that still connects directly to an upstream MCP server bypasses the gateway, so its tool calls aren't authorized or logged by the gateway.

:::tip Enterprise deployment
To run the gateway inside your own network for data residency, private MCP servers, or compliance, see [Enterprise deployment](/permit-mcp-gateway/enterprise-deployment). You can evaluate with the hosted gateway first.
:::
