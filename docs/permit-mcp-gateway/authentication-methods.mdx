Configure how people sign in to a Permit MCP Gateway host during the [consent flow](/permit-mcp-gateway/consent-service), and how recently they must have signed in to decide their agents' approvals. This reference is for host admins who turn on sign-in methods, connect an identity provider (IdP), or limit sign-in to company email domains.

Each host has its own authentication configuration. Different hosts can use different methods, credentials, and domain restrictions.

## Configure authentication for a host

1. In the [Permit MCP Gateway dashboard](https://app.agent.security), select the host in the host selector at the top of the page.
2. In the sidebar, click **Settings**, and scroll to **Authentication Methods**.
3. Click **Add method** and pick a method. The menu groups the methods under **Standard**, **Social Providers**, and **Enterprise**.
4. Expand the method's row and enter the values the method needs. The [available methods](#available-methods) table lists them. The row also shows the callback URL to register with the provider.
5. Click **Save Configuration**. The dashboard checks the [configuration rules](#configuration-rules) on save. Saving needs the admin role in the organization.
6. Connect an MCP client to the host. The sign-in page of the consent flow shows the method you added.

![Authentication Methods section of host Settings with Global Email Domain Restriction, Email / Password under Standard, Add method, and Save Configuration](/img/agent-security/platform/settings-auth-methods.png)

A host starts with **Email / Password** on and all other methods off. To remove a method, click the **X** on its row and confirm **Remove**. **Reset to Defaults** returns a host with a saved configuration to Email / Password only.

## Available methods

| Method | Listed in **Add method** as | Configuration required | Callback URL |
| --- | --- | --- | --- |
| [Email / Password](#email--password) | **Email / Password** | None | None |
| [Email OTP](#email-otp) | **Email OTP** | None | None |
| [Passkeys](#passkeys-webauthn) | **Passkeys** | None | None |
| [Google OAuth](#google-oauth) | **Google** | Client ID and client secret | `https://{subdomain}.agent.security/api/auth/callback/google` |
| [GitHub OAuth](#github-oauth) | **GitHub** | Client ID and client secret | `https://{subdomain}.agent.security/api/auth/callback/github` |
| [Microsoft OAuth](#microsoft-oauth) | **Microsoft** | Client ID, client secret, optional tenant ID | `https://{subdomain}.agent.security/api/auth/callback/microsoft` |
| [SAML 2.0 SSO](#saml-20-sso) | **Enterprise SAML** | IdP entry point URL, IdP entity ID, X.509 certificate in PEM format | ACS URL: `https://{subdomain}.agent.security/api/auth/sso/saml2/callback/sso-{subdomain}` |
| [OIDC SSO](#oidc-sso) | **Enterprise OIDC** | Issuer URL, client ID, client secret | `https://{subdomain}.agent.security/api/auth/oauth2/callback/sso-{subdomain}` |

In every URL, replace `{subdomain}` with the host's full subdomain, for example `acme-zesty-magenta-11`. Each method's row in **Settings** shows the exact URLs for the host.

### Email / Password \{#email--password}

People create an account with **Create Account** (name, email address, and a password of at least 8 characters), then sign in with **Email** and **Password**. **Forgot password?** sends a reset link. Email / Password needs no configuration and is on by default.

On hosted gateway hosts, a new account verifies its email address before it signs in: the **Check your email** page asks the person to open the verification link.

If a host has no saved authentication configuration, the host uses Email / Password only.

### Email OTP

Email one-time passcode (OTP) sign-in is passwordless. Under "Sign in with email code", the person enters an email address and clicks **Send Code**, receives a 6-digit code by email, and enters the code within 5 minutes.

Email OTP needs no configuration; the host sends the code with its built-in email delivery. You can turn on Email OTP next to Email / Password, and the sign-in page shows both.

### Passkeys (WebAuthn)

Passkeys use the FIDO2 Web Authentication (WebAuthn) standard. A person signs in with **Sign in with Passkey** and a biometric or a security key instead of a password.

- **Configuration required:** none.
- **Browser support:** the person's browser must support the [Web Authentication API](https://developer.mozilla.org/en-US/docs/Web/API/Web_Authentication_API).
- **Where people add a passkey:** on the host's **Your passkeys** page (`/passkeys`), from the account menu. The page offers passkeys only when the host has **Passkeys** on and the person's email domain is allowed for the method. Adding a passkey needs a recent sign-in (**Sign in again**), then a confirmation: an emailed code for the first passkey, or a tap of an existing passkey after that.
- **Tied to one host:** a passkey signs in only on the host where the person registered it. On another host, the person registers another passkey.
- **Approvals switch to the passkey:** after a person adds their first passkey on a host, every approval decision of theirs on that host is confirmed with a passkey, instead of a recent sign-in or an emailed code. The page shows "Approvals: confirmed with a passkey" until an admin resets it. The admin resets it on the person's page under **Humans**, in **Approval verification**, with **Reset to sign-in**, which removes the person's passkeys on that host. See [Manage humans and agents](/permit-mcp-gateway/managing-humans-and-agents).
- **Keep another method on:** a person without a passkey can't sign in with one, so keep another method on next to Passkeys.

### Google OAuth

People sign in with a Google account through **Continue with Google**. Google OAuth needs a Google OAuth client ID and client secret.

#### Set up Google OAuth \{#setup-steps}

1. Go to the [Google Cloud Console](https://console.cloud.google.com/).
2. Go to **APIs & Services > Credentials**.
3. Click **Create Credentials > OAuth client ID**.
4. Select **Web application** as the application type.
5. Under **Authorized redirect URIs**, add the Google callback URL:
   ```text
   https://{subdomain}.agent.security/api/auth/callback/google
   ```
   Replace `{subdomain}` with your host's full subdomain, for example `acme-zesty-magenta-11`.
6. Copy the **Client ID** and **Client Secret**.
7. In the Permit MCP Gateway dashboard, go to **Settings** > **Authentication Methods**, click **Add method**, and select **Google**.
8. Paste the client ID and client secret, and click **Save Configuration**.

:::info One OAuth app per host
The callback URL contains the host's subdomain, so each host needs its own OAuth app registration. For several hosts, create a separate Google OAuth app for each host, with that host's callback URL.
:::

### GitHub OAuth

People sign in with a GitHub account through **Continue with GitHub**. GitHub OAuth needs a GitHub OAuth client ID and client secret.

#### Set up GitHub OAuth \{#setup-steps-1}

1. Go to [GitHub Developer Settings > OAuth Apps](https://github.com/settings/developers).
2. Click **New OAuth App**.
3. Fill in the app details:
   - **Application name:** for example, "Permit MCP Gateway (acme)".
   - **Homepage URL:** `https://{subdomain}.agent.security`
   - **Authorization callback URL:**
     ```text
     https://{subdomain}.agent.security/api/auth/callback/github
     ```
4. Click **Register application**.
5. Copy the **Client ID**, then generate and copy a **Client Secret**.
6. In the Permit MCP Gateway dashboard, go to **Settings** > **Authentication Methods**, click **Add method**, and select **GitHub**.
7. Paste the client ID and client secret, and click **Save Configuration**.

A GitHub sign-in never counts as recent for the [sign-in check for approvals](#sign-in-check-for-approvals), so people who sign in with GitHub confirm approvals with an emailed code or a passkey.

### Microsoft OAuth

People sign in with a Microsoft account through Microsoft Entra ID (formerly Azure AD), through **Continue with Microsoft**. Microsoft OAuth supports single-tenant and multi-tenant apps. It needs a Microsoft OAuth client ID and client secret, and optionally a tenant ID.

#### Set up Microsoft OAuth \{#setup-steps-2}

1. Go to [Azure Portal > App registrations](https://portal.azure.com/#view/Microsoft_AAD_RegisteredApps/ApplicationsListBlade).
2. Click **New registration**.
3. Fill in the registration:
   - **Name:** for example, "Permit MCP Gateway (acme)".
   - **Supported account types:**
     - *Single tenant:* only users in your Microsoft Entra directory.
     - *Multitenant:* users in any Microsoft Entra directory.
     - *Multitenant and personal Microsoft accounts:* users in any Microsoft Entra directory and personal Microsoft accounts.
   - **Redirect URI:** select **Web** and enter the Microsoft callback URL:
     ```text
     https://{subdomain}.agent.security/api/auth/callback/microsoft
     ```
4. Click **Register**.
5. Copy the **Application (client) ID**.
6. Go to **Certificates & secrets > New client secret**, create a secret, and copy its **Value**.
7. In the Permit MCP Gateway dashboard, go to **Settings** > **Authentication Methods**, click **Add method**, and select **Microsoft**.
8. Paste the client ID and client secret.
9. Optional: set **Tenant ID** to limit sign-in to one Microsoft Entra directory. See [Tenant ID values](#tenant-id-values).
10. Click **Save Configuration**.

#### Tenant ID values

| Value | Who can sign in |
| --- | --- |
| Empty | Same as `common`. |
| `common` | Any Microsoft Entra account or personal Microsoft account. |
| `organizations` | Any Microsoft Entra account. No personal accounts. |
| `consumers` | Personal Microsoft accounts only. |
| A directory UUID | Only users in that Microsoft Entra directory. |

### SAML 2.0 SSO

Security Assertion Markup Language (SAML) 2.0 single sign-on (SSO) connects the host to your company IdP, such as Okta, Microsoft Entra ID, or Google Workspace. Permit MCP Gateway is the service provider (SP), and your IdP is the identity provider. In **Add method**, SAML SSO is **Enterprise SAML**, and the sign-in page shows **Sign in with Enterprise SSO (SAML)**.

SAML SSO needs the IdP entry point URL, the IdP entity ID, and the IdP's X.509 signing certificate in PEM format. The method's fields are **IdP SSO URL (Entry Point)**, **IdP Entity ID**, and **IdP X.509 Certificate (PEM)**.

#### Service provider details

Enter these values in your IdP when you create the SAML app. The **Enterprise SAML** row in **Settings** shows the same values for the host.

| Field | Value |
| --- | --- |
| **SP Entity ID / Audience URI** | `https://{subdomain}.agent.security/api/auth/sso/saml2/sp/metadata` |
| **ACS (Assertion Consumer Service) URL** | `https://{subdomain}.agent.security/api/auth/sso/saml2/callback/sso-{subdomain}` |
| **SP Metadata URL** | `https://{subdomain}.agent.security/api/auth/sso/saml2/sp/metadata?providerId=sso-{subdomain}` |

#### Attribute mapping

Configure your IdP to send these SAML attributes:

| Attribute | SAML claim URI |
| --- | --- |
| **Email** | `http://schemas.xmlsoap.org/ws/2005/05/identity/claims/emailaddress` |
| **Name** | `http://schemas.xmlsoap.org/ws/2005/05/identity/claims/name` |

#### SAML security settings \{#security-posture}

| Setting | Behavior |
| --- | --- |
| **SP-initiated SSO only** | The host rejects IdP-initiated SSO. People start sign-in from the gateway's sign-in page, not from the IdP's app dashboard. |
| **InResponseTo validation** | Each SAML response must reference the authentication request the host sent. |
| **Certificate format** | The IdP certificate must be PEM: it starts with `-----BEGIN CERTIFICATE-----` and ends with `-----END CERTIFICATE-----`. |

A SAML sign-in never counts as recent for the [sign-in check for approvals](#sign-in-check-for-approvals), so people who sign in with SAML confirm approvals with an emailed code or a passkey.

:::note Identity provider consoles change
The Okta, Microsoft Entra ID, and Google Workspace steps below use the console labels those vendors show at the time of writing. If a label differs in your console, match the field by purpose: ACS URL, SP entity ID, name ID format, and the email and name attributes.
:::

#### Okta setup

1. In the Okta Admin Console, go to **Applications > Create App Integration**.
2. Select **SAML 2.0** and click **Next**.
3. Set **App name**, for example "Permit MCP Gateway".
4. Configure the SAML settings:
   - **Single sign-on URL (ACS URL):** `https://{subdomain}.agent.security/api/auth/sso/saml2/callback/sso-{subdomain}`
   - **Audience URI (SP Entity ID):** `https://{subdomain}.agent.security/api/auth/sso/saml2/sp/metadata`
   - **Name ID format:** EmailAddress
   - **Application username:** Email
5. Add attribute statements:
   - `email` to `user.email` (URI: `http://schemas.xmlsoap.org/ws/2005/05/identity/claims/emailaddress`)
   - `name` to `user.displayName` (URI: `http://schemas.xmlsoap.org/ws/2005/05/identity/claims/name`)
6. Click **Next**, then **Finish**.
7. On the app's **Sign On** tab, copy the **IdP SSO URL** (entry point) and the **IdP Entity ID** (issuer), and download the **X.509 Certificate**.
8. In the Permit MCP Gateway dashboard, go to **Settings** > **Authentication Methods**, click **Add method**, and select **Enterprise SAML**.
9. Paste the entry point URL, entity ID, and PEM certificate, and click **Save Configuration**.

#### Microsoft Entra ID setup \{#azure-ad-entra-id-setup}

1. In the [Azure Portal](https://portal.azure.com), go to **Enterprise Applications > New Application > Create your own application**.
2. Select **Integrate any other application you don't find in the gallery (Non-gallery)**.
3. Name the application, for example "Permit MCP Gateway", and click **Create**.
4. Go to **Single sign-on > SAML**.
5. In **Basic SAML Configuration**, set:
   - **Identifier (Entity ID):** `https://{subdomain}.agent.security/api/auth/sso/saml2/sp/metadata`
   - **Reply URL (ACS URL):** `https://{subdomain}.agent.security/api/auth/sso/saml2/callback/sso-{subdomain}`
6. In **Attributes & Claims**, check these mappings:
   - `emailaddress` to `user.mail`
   - `name` to `user.displayname`
7. In **SAML Certificates**, download **Certificate (Base64)**. The Base64 certificate is in PEM format.
8. In the **Set up** section for your application, copy the **Login URL** (entry point) and the Microsoft Entra identifier (entity ID). Older portal versions label the identifier **Azure AD Identifier**.
9. In the Permit MCP Gateway dashboard, go to **Settings** > **Authentication Methods**, click **Add method**, and select **Enterprise SAML**.
10. Paste the entry point URL, entity ID, and certificate, and click **Save Configuration**.

#### Google Workspace setup

1. In the [Google Admin Console](https://admin.google.com), go to **Apps > Web and mobile apps > Add app > Add custom SAML app**.
2. Name the app, for example "Permit MCP Gateway", and click **Continue**.
3. On the **Google Identity Provider details** page, copy the **SSO URL** (entry point) and the **Entity ID**, and download the **Certificate**.
4. Click **Continue**.
5. Fill in **Service provider details**:
   - **ACS URL:** `https://{subdomain}.agent.security/api/auth/sso/saml2/callback/sso-{subdomain}`
   - **Entity ID:** `https://{subdomain}.agent.security/api/auth/sso/saml2/sp/metadata`
   - **Name ID format:** EMAIL
   - **Name ID:** Basic Information > Primary email
6. Add attribute mappings:
   - `email` to Basic Information > Primary email
   - `name` to Basic Information > First name and Last name
7. Click **Finish**, then turn the app **ON** for the organizational units that use the gateway.
8. In the Permit MCP Gateway dashboard, go to **Settings** > **Authentication Methods**, click **Add method**, and select **Enterprise SAML**.
9. Paste the entry point URL, entity ID, and certificate, and click **Save Configuration**.

### OIDC SSO

OpenID Connect (OIDC) SSO connects the host to any IdP that supports OIDC discovery. In **Add method**, OIDC SSO is **Enterprise OIDC**, and the sign-in page shows **Sign in with Enterprise SSO**. OIDC SSO needs the issuer URL, a client ID, and a client secret (the **Issuer URL**, **Client ID**, and **Client Secret** fields). The host requests the `openid`, `profile`, and `email` scopes.

#### How OIDC discovery works \{#how-it-works}

Permit MCP Gateway reads your IdP's endpoints from the standard OpenID Connect discovery URL:

```text
{issuerUrl}/.well-known/openid-configuration
```

You enter the issuer URL. The gateway reads the authorization, token, and key endpoints from the discovery document.

#### Set up OIDC SSO \{#setup-steps-3}

1. In your IdP, register a web application (sometimes called an OIDC app).
2. Set the redirect URI (callback URL). Copy the exact value from **Redirect URI (Callback URL)** on the **Enterprise OIDC** row in **Settings**:
   ```text
   https://{subdomain}.agent.security/api/auth/oauth2/callback/sso-{subdomain}
   ```
3. Note the **Issuer URL**, for example `https://accounts.google.com`, `https://login.microsoftonline.com/{tenant}/v2.0`, or `https://{domain}.okta.com`.
4. Copy the **Client ID** and **Client Secret**.
5. In the Permit MCP Gateway dashboard, go to **Settings** > **Authentication Methods**, click **Add method**, and select **Enterprise OIDC**.
6. Paste the issuer URL, client ID, and client secret, and click **Save Configuration**.

:::note One SSO method per host
A host can use SAML 2.0 SSO or OIDC SSO, not both. While one SSO method is on, **Add method** doesn't offer the other. To switch, remove the current SSO method before you add the other one.
:::

## Account linking

People's accounts are shared across gateway hosts and identified by email address. When a person signs in with a new method, whether the gateway links it to an existing account with the same email depends on the method:

| Method | Links to an existing account with the same email |
| --- | --- |
| Google, GitHub, Microsoft | Yes, when the provider reports the email as verified and the existing account's email is verified. |
| SAML 2.0 SSO, OIDC SSO | Never. Your IdP controls what it asserts, so the gateway doesn't trust its email claims for other accounts. |

What this means for a host with SSO:

- A person who already has an account with the same email address, for example from Email / Password on this or another host, can't sign in through the host's SSO. They keep signing in the way they signed up.
- Accounts that SSO creates aren't linked from Google, GitHub, or Microsoft either.

Turn on SSO before people create Email / Password accounts with their company addresses, so that employees sign in through SSO from the start.

## Domain restrictions

Domain restrictions limit which email domains can sign in with each method. Set them in **Settings** > **Authentication Methods**:

- **Global Email Domain Restriction**, at the top of the section: "If set, only emails from these domains can use any auth method."
- **Email Domain Restriction**, inside each method's row: "Restrict this method to specific email domains."

### Global and per-method restrictions \{#global-vs-per-method}

| Restriction | Scope |
| --- | --- |
| **Global** | All authentication methods on the host. |
| **Per-method** | One authentication method. |

An empty list means no restriction at that level.

### How global and per-method restrictions combine \{#intersection-semantics}

When both lists are set, an email domain must be in the global list **and** in the per-method list. A per-method list narrows the global list. A per-method list can't add a domain that the global list blocks.

| Global allows | Per-method allows | `user@acme.com` | `user@partner.io` | `user@outsider.com` |
| --- | --- | --- | --- | --- |
| `acme.com`, `partner.io` | Not set | Allowed | Allowed | Blocked |
| Not set | `acme.com` | Allowed | Blocked | Blocked |
| `acme.com`, `partner.io` | `acme.com` | Allowed | **Blocked** (not in per-method) | Blocked |
| `acme.com` | `acme.com`, `outsider.com` | Allowed | Blocked | **Blocked** (not in global) |

:::warning Per-method lists don't bypass the global list
If the global list allows only `acme.com` and a per-method list adds `outsider.com`, people with `@outsider.com` addresses still can't sign in with that method. Add a domain to the global list before you add it to a per-method list.
:::

### Domain restriction examples \{#examples}

| Scenario | Global allowed domains | Per-method allowed domains | Result |
| --- | --- | --- | --- |
| One organization | `acme.com` | Not set | All methods accept only `@acme.com` addresses. |
| Employees on SSO, contractors on Email / Password | `acme.com`, `contractor.acme.com` | SSO: `acme.com` | Employees use SSO. People with `@contractor.acme.com` addresses can use Email / Password but not SSO. |
| Partner organizations | `acme.com`, `partner1.com`, `partner2.com` | Optional: SSO limited to `acme.com` | All three domains can use any enabled method, except where a per-method list narrows them. |

### Force-redirect domains

For SAML or OIDC SSO, you can set force-redirect domains (**Force SSO for Domains** on the SSO method's row: "Users with these email domains will be auto-redirected to SSO."). When a person enters an email address with a matching domain, the sign-in page sends the person to the SSO provider without showing the other methods.

1. The person enters an email address on the sign-in page.
2. If the domain matches a force-redirect domain, the browser redirects to the SSO provider.
3. After SSO authentication, the person returns to the consent flow.

If the SSO sign-in fails, for example because the IdP is unavailable or the person cancels, the person returns to the sign-in page with the message *"SSO sign-in was unsuccessful. Please try another method or contact your administrator."* The person can then sign in with any other method allowed for their domain.

## Enable multiple methods \{#multi-method-configuration}

### Combine methods on one host \{#enabling-multiple-methods}

You can turn on any combination of methods, with one limit: a host can use only one SSO type, SAML 2.0 or OIDC.

### What people see on the sign-in page \{#what-users-see}

The **Sign In** page shows only the methods that are on. When domain restrictions are set, the person enters an email address first, and the page shows only the methods allowed for that domain.

![Sign In page of a gateway host with Email / Password only](/img/agent-security/consent/login.png)

Methods appear in this order:

1. Passkeys (**Sign in with Passkey**)
2. Social sign-in buttons (**Continue with Google**, **Continue with GitHub**, **Continue with Microsoft**)
3. SSO button (**Sign in with Enterprise SSO**, or **Sign in with Enterprise SSO (SAML)**)
4. Email / Password form
5. Email OTP form ("Sign in with email code")

The **Create Account** button appears only when Email / Password or Email OTP is on.

A browser sign-in on a host lasts 7 days, and the gateway extends it when the person uses it after a day.

### Recommended configurations

| Organization type | Methods | Notes |
| --- | --- | --- |
| **Small team** | Email / Password | No external setup. |
| **Developer team** | GitHub OAuth and Email / Password | GitHub for daily sign-in, Email / Password as a fallback. GitHub sign-ins confirm approvals with an emailed code or a passkey. |
| **Google Workspace organization** | Google OAuth and Email / Password | Limit Google OAuth to your domain with a per-method restriction. |
| **Microsoft 365 organization** | Microsoft OAuth or OIDC SSO | Set the tenant ID to limit sign-in to your directory. |
| **Enterprise with an IdP** | SAML 2.0 or OIDC SSO, and Email / Password | SSO for employees, Email / Password for exceptions. Add force-redirect domains so employees go straight to SSO. Turn on SSO first: SSO doesn't link to existing accounts. See [Account linking](#account-linking). |
| **Organization with contractors** | SSO and Email / Password, with domain restrictions | SSO limited to the employee domain, Email / Password for the contractor domain. |

## Sign-in check for approvals \{#sign-in-check-for-approvals}

Some actions on the consent pages need a recent sign-in, so that the person, and not an agent with access to their browser, makes the decision:

- Approving or rejecting a call their agent asked about (when they turned on **Ask me before this agent changes or deletes anything**).
- Turning that switch off on a server.
- Editing a task they set on **Your MCP agents**.
- Adding or removing a passkey.

Set the window in **Settings** > **Sign-in check for people's approvals**. **Sign-in must be within** offers **5 min**, **15 min** (default), **1 hour**, **8 hours**, and **Custom** (1 to 1440 minutes).

![Sign-in check for people's approvals with Sign-in must be within set to 15 min](/img/agent-security/platform/settings-sign-in-check.png)

When the person's sign-in is older than the window:

- The person enters a code the gateway emails for that action. The code works once, for 5 minutes, with 5 tries.
- Or the person clicks **Sign in again instead**. The **Sign in again** page ("Confirm it's you. Then you go back to where you were.") signs them in and returns them to the action. For Google, Microsoft, and OIDC SSO, the gateway asks the provider to sign the person in again.

A person with a passkey on the host confirms every decision with the passkey instead.

Which sign-ins count as recent:

| Sign-in | Counts as recent |
| --- | --- |
| Email / Password, Email OTP | Yes, from the sign-in time. |
| Passkey registered on this host | Yes, from the sign-in time. |
| Google, Microsoft, OIDC SSO | Yes, when the provider reports that the person signed in at the provider during this sign-in. A sign-in the provider completes from its own older session doesn't count. |
| GitHub, SAML 2.0 SSO | Never. These people use the emailed code or a passkey. |

## Configuration rules

The dashboard enforces these rules when you save authentication settings:

| Rule | Description |
| --- | --- |
| **At least one method** | At least one authentication method must be on. You can't turn off all methods. |
| **One SSO type per host** | A host can use SAML 2.0 SSO or OIDC SSO, not both. |
| **SAML requires all fields** | SAML needs the entry point URL, the entity ID, and the X.509 certificate. |
| **OIDC requires all fields** | OIDC needs the issuer URL, the client ID, and the client secret. |
| **Social providers require credentials** | Google, GitHub, and Microsoft OAuth each need a client ID and a client secret. |
| **PEM format** | The dashboard rejects a SAML certificate that doesn't start with `-----BEGIN CERTIFICATE-----` and end with `-----END CERTIFICATE-----`. |
