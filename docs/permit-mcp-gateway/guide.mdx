**Short answer:** Permit MCP Gateway signs in the people behind AI agents, authorizes each MCP tool call against the trust level the person approved and the maximum an admin set, and logs every decision. Use it when an admin must control which people reach which MCP servers and tools from Cursor, Claude Code, VS Code, or Claude Desktop. Don't use it when you need to enforce permissions inside an MCP server you own.

| Fact | Value |
|---|---|
| Trust levels | Low (read tools), medium (adds write tools), and high (adds destructive tools). A higher level includes every lower level. An admin can change the level of any tool. |
| Agents | One agent per person per MCP client. Two people who connect the same client get two agents, each with its own trust level. |
| Supported MCP clients | Cursor, VS Code, Claude Desktop, and Claude Code. Each MCP server's page shows its gateway URL and a configuration snippet for each client. |
| Deployment modes | Hosted (SaaS) on `*.agent.security`, customer-controlled, and fully on-premises. The last two are available on Enterprise plans. See [Enterprise deployment](/permit-mcp-gateway/enterprise-deployment). |
| Authorization model | A relationship-based access control (ReBAC) trust ceiling on standard Permit objects. Gateway policies can also use RBAC and ABAC. |
| Optional controls | Admin approval per tool or per server, agent identity checks, and the Guardian, an LLM judge that grades each call against the server's intent. |
| Sign-in methods | Email and password (on by default), email one-time passcode, passkeys, Google, GitHub, and Microsoft OAuth, and SAML 2.0 or OIDC single sign-on. See [Authentication methods](/permit-mcp-gateway/authentication-methods). |
| Audit | Each allowed or denied tool call is logged with the person, the agent, the tool, the MCP server, and the reason, on the **Audit Logs** tabs in the admin dashboard and in the Permit **Audit Log** screen. |
| SDK or code change | None. You point the MCP client at the gateway URL instead of the MCP server URL. Agent identity checks, if you turn them on, need an instruction snippet in the agent's rules file. |
| Free tier | Community plan, labeled "Free forever" on the [Permit MCP Gateway pricing](https://www.permit.io/mcp-gateway/pricing) page: "Up to 1,000 MAU (human + agentic identities)", Tenants 10, Environments 1, Audit log retention 7 days. The main [Permit.io pricing](https://www.permit.io/pricing) page lists different Community limits for Permit.io authorization outside the gateway. |
| Open-source components | The Permit PDP and [OPAL](https://github.com/permitio/opal) that Permit uses are open source. The Access Request MCP server ([permitio/permit-mcp](https://github.com/permitio/permit-mcp)) is a separate open-source project and is not the gateway. |

Set up a Permit MCP Gateway host for your team, from your first sign-in to an allowed tool call, a denied tool call, and their audit log entries, then add admin approvals, agent identity, and the Guardian. This guide is for the admin or AI agent builder who sets up the gateway and gives other people access to Model Context Protocol (MCP) servers through it.

Permit MCP Gateway is a proxy between MCP clients (Cursor, Claude Desktop, VS Code, Claude Code) and upstream MCP servers. The gateway signs people in, checks each tool call against policy in Permit.io, and logs each decision. For the shortest path to one connected client, see the [Permit MCP Gateway quickstart](/permit-mcp-gateway/quickstart).

When you finish this guide, you have:

- A host with one imported MCP server, a trust level on each tool, and a workflow intent.
- People with access to that server, each with a maximum trust level.
- An MCP client connected through the gateway, with an agent the person approved.
- One allowed tool call, one denied tool call, and audit log entries for both.
- Optionally, a tool that waits for admin approval, and agent identity checks and the Guardian turned on.

The examples use the organization **Acme Corp**, the host `acme-zesty-magenta-11.agent.security`, the DeepWiki MCP server (`https://mcp.deepwiki.com/mcp`), the person **Check TheDog**, and an MCP client named **Acme Research Agent**.

## Prerequisites

- A [Permit.io](https://app.permit.io) account. You sign in to the gateway admin dashboard at [app.agent.security](https://app.agent.security) with it.
- An MCP client installed: Cursor, VS Code, Claude Desktop, or Claude Code.
- The URL of a remote MCP server to secure, such as `https://mcp.deepwiki.com/mcp`.

## 1. Sign in and choose an organization \{#1-sign-up-and-connect-your-organization}

1. Go to [app.agent.security](https://app.agent.security) and click **Sign in with Permit.io**. The admin dashboard has no separate sign-up and no API key step. Your organizations come from your Permit.io membership.
2. Check the organization switcher at the top of the sidebar. It shows the current organization. Open it to search your organizations or switch between them.
3. To create an organization, click **+** in the organization switcher. On the **Organizations** page, click **Create Another Organization**, enter an **Organization name** and an **Organization key** (lowercase letters, numbers, and dashes only), and click **Create**. If your account has no organization yet, click **Manage Organizations** on the welcome page. The **Organizations** page shows the same fields with a **Create Organization** button.

![Organization switcher open in the sidebar with a search box and the add organization button](/img/agent-security/platform/org-switcher.png)

The sidebar lists the admin pages: **Dashboard**, **Hosts**, **MCP Servers**, **Approvals**, **Agents**, **Humans**, **Consent Grants**, and **Settings**. For every page, see the [Platform reference](/permit-mcp-gateway/platform).

## 2. Create a host

A **host** is one gateway tenant with its own subdomain, its own sign-in page and accounts for the people who connect agents, its own MCP servers, and one Permit environment that stores its policies.

1. Go to **Hosts** and click **Create Host**. You can also open the host chip in the top bar and click **Add host**.
2. Fill in the host fields:

   | Field | Value |
   | --- | --- |
   | **Subdomain** | A prefix such as `acme`: lowercase letters, numbers, and hyphens, not starting or ending with a hyphen. The platform adds a suffix such as `-zesty-magenta-11.agent.security` that you can't change. |
   | **Project** | The Permit project for the host's environment. |
   | **Environment** | **+ Create new environment** (the default), with an **Environment Name** and an **Environment Key** that starts with a letter, or an existing environment. You can't change the environment after you create the host. |
   | **Allow Dynamic MCP Connections** | On by default. Lets people connect to any MCP server URL, not only servers you import. |

   ![Create Host form with the subdomain prefix acme, a new Acme Gateway environment, and Allow Dynamic MCP Connections on](/img/agent-security/platform/create-host-filled.png)

3. Click **Create Host**. The **Confirm Host Creation** dialog repeats that the environment can't change and shows the subdomain and the environment. Click **Create Host** to confirm.

   ![Confirm Host Creation dialog showing the subdomain and the environment that will be created](/img/agent-security/platform/create-host-confirm.png)

:::warning Decide on dynamic MCP connections before you create the host
With **Allow Dynamic MCP Connections** on, people can connect their agents to any MCP server URL, including servers an admin never reviewed. Tool calls on those servers are still authorized and logged. You can turn the setting on later in **Settings**, but after it is on you can't turn it off. To limit people to imported servers, turn the switch off now.
:::

**Expected result:** the host card on the **Hosts** page is marked **Current**, and the host chip in the top bar shows `acme-zesty-magenta-11.agent.security`. The host's settings, including sign-in methods and agent identity, are under **Settings** in the sidebar. The host has no imported MCP servers and no access grants yet. With **Allow Dynamic MCP Connections** on, a person who signs in can still connect an agent to any MCP server URL from the consent screen.

## 3. Import MCP servers \{#3-import-mcp-servers}

Importing an MCP server connects the platform to the upstream server, discovers its tools, and creates the matching resource and actions in the host's Permit environment.

1. Go to **MCP Servers** and click **Create Server**. Only organization admins can import servers.
2. On the **Connect** step, enter the upstream MCP server URL, such as `https://mcp.deepwiki.com/mcp`, and click **Connect**.

   ![Import MCP Server Connect step with the DeepWiki URL](/img/agent-security/platform/import-connect.png)

   - If the upstream server requires authentication, the page shows **Authorization Required**. Click **Sign in to MCP Server**, sign in with the provider, and you return to the import.
   - If the upstream provider doesn't support automatic OAuth client registration, the page asks for a **Client ID** and **Client Secret**. Register an OAuth app with the provider using the redirect URI the page shows, then enter its credentials.

3. On the **Review & Configure** step, set the server fields:

   | Field | Value |
   | --- | --- |
   | **Server Key** | A unique key with lowercase letters, underscores, and numbers, such as `deepwiki`. The key is part of the server's gateway URL, `https://<subdomain>.agent.security/mcp/<server_key>`. |
   | **Display Name** | The name people see on the consent screen, such as `DeepWiki`. |
   | **Description (optional)** | What the server does. |
   | **Workflow intent (optional)** | Up to 500 characters on what the server is for. The Guardian grades tool calls against it, and the consent screen shows it as **Purpose, set by your admin**. |

4. Under **Tools to Import**, choose the tools to import. Each tool shows the trust level the gateway picked from the tool name (see the [trust level reference](#trust-level-reference)). Change a level with the select next to the tool; a changed level shows **(custom)**. Turn on a tool's **HITL** switch to require admin approval for every call to it. For this guide, set `ask_wiki_question` to **Medium**.

   ![Review and Configure step for DeepWiki with the server key, workflow intent, and three tools with HITL switches and trust levels](/img/agent-security/platform/import-review.png)

5. Click **Import Server & N Tools**, where N is the number of selected tools.
6. In the **Server Created Successfully** dialog, add people who already signed in to the host, or click **Skip for Now**. Then click **View Server**.

:::tip Write the workflow intent as what the server is and does
The Guardian compares each call with the intent. An intent such as "Read-only research on public GitHub repositories" can make the Guardian refuse a legitimate read from DeepWiki, because DeepWiki isn't GitHub. An intent that describes the server works better: "DeepWiki hosts generated documentation for public GitHub repositories. Agents read those wiki pages and ask questions about how open-source codebases such as React and Next.js work. Read-only; no writes." Test an intent with the server's **Dry Run** tab (see [step 10](#10-turn-on-agent-identity-and-the-guardian-optional)).
:::

**Expected result:** the server appears on the **MCP Servers** page. Its page has **Overview**, **Audit Logs**, and **Dry Run** tabs. The **Overview** tab holds the **Intent** card, the **MCP URL** card, **Authorized Humans**, **Server Approval Policy**, **Trusted Agent Bypass**, **Tools**, and **Configuration**. Nobody can use the server yet.

To change a tool's trust level or approval switch later, use the server's **Tools** card. **Re-sync Tools** reads the upstream tool list again, and **Add Tool** adds one tool. See the [Platform reference](/permit-mcp-gateway/platform).

## 4. Grant people access to MCP servers \{#4-grant-user-access-to-mcp-servers}

A person can't use an imported MCP server until an admin grants access. Each grant sets **Max trust**: the highest trust level the person can approve for any of their agents on that server. The agent's effective trust level is the lower of the level the person approves at consent and this maximum.

Grant access in one of two places:

- **Server page, for anyone.** On the server's **Authorized Humans** card, click **Grant Access**. In the **Grant Human Access** dialog, pick a person on the **Existing User** tab, or enter an email address on the **Invite by Email** tab for someone who hasn't signed up yet. Set **Max trust** and click **Grant Access**. An invite activates when the person signs up on the host with that email.
- **Humans page, for people who signed in.** Go to **Humans** and open the person. On the **MCP Server Access** card, click **Grant Access**, pick the **MCP Server**, set **Max trust** (the default is **Low**), and click **Grant Access**.

![MCP Server Access card for Check TheDog with DeepWiki at high trust and Cloudflare Docs at medium trust](/img/agent-security/platform/human-mcp-access.png)

People appear on the **Humans** page after their first sign-in to the host. **Invite by Email** on the **Humans** page pre-authorizes a person by email; grant the invite server access from the server's **Authorized Humans** card.

For this guide, grant the person access to DeepWiki with **Max trust** set to **High**.

:::warning Grant access before people connect
If a person connects before you grant access, the consent screen says "No MCP servers available. Contact your administrator to grant you access to MCP servers." Grant access, then ask the person to click **Refresh list** on the consent screen.
:::

**Expected result:** the person appears on the server's **Authorized Humans** card, and the consent screen lists the server for that person.

To change a maximum or revoke access later, use the **Trust level** select or **Revoke access** on the person's **MCP Server Access** card. See [Managing humans and agents](/permit-mcp-gateway/managing-humans-and-agents).

## 5. Connect MCP clients \{#6-share-with-your-users}

Each MCP server's page has an **MCP URL** card with the server's gateway URL and tabs for **Cursor / VS Code**, **Claude Desktop**, and **Claude Code**. Share the URL or the snippet with each person.

![MCP URL card for DeepWiki with the Claude Code tab open](/img/agent-security/platform/server-mcp-url-claude-code.png)

:::warning Remove direct connections to the same MCP server
If an MCP client has the same server configured through the gateway and as a direct connection, the agent can use the direct connection and skip the gateway. Calls on the direct connection aren't authorized or logged.
:::

### Cursor \{#cursor--vs-code}

Add the server to `.cursor/mcp.json`:

```json
{
  "mcpServers": {
    "deepwiki": {
      "url": "https://acme-zesty-magenta-11.agent.security/mcp/deepwiki"
    }
  }
}
```

VS Code reads MCP servers from `.vscode/mcp.json`, which uses a top-level `servers` key instead of `mcpServers`. See the [VS Code MCP server documentation](https://code.visualstudio.com/docs/copilot/customization/mcp-servers) for the file format.

### Claude Desktop

The **Claude Desktop** tab shows the same JSON and the location of the config file:

- **macOS**: `~/Library/Application Support/Claude/claude_desktop_config.json`
- **Windows**: `%APPDATA%\Claude\claude_desktop_config.json`

### Claude Code

Run this command:

```bash
claude mcp add deepwiki --transport http "https://acme-zesty-magenta-11.agent.security/mcp/deepwiki"
```

### Choose which gateway URL to share \{#pre-selected-mcp-server}

| URL | What the person sees at consent |
| --- | --- |
| `https://<subdomain>.agent.security/mcp/<server_key>` | The consent screen opens with that server selected. If the person has no access to it, the screen says `MCP server "<server_key>" is not available or you don't have access to it.` |
| `https://<subdomain>.agent.security/mcp` | The consent screen lists every server the person has access to, and the person picks one. |
| `https://<subdomain>.agent.security/mcp?upstream_mcp=<url>` | For a server nobody imported. Works only when the host allows dynamic MCP connections. Otherwise the screen says "This host does not allow connecting to dynamic MCP servers. Contact your administrator." |

When the host allows dynamic MCP connections, the consent screen also has an **or enter a custom URL** field. Servers that people connect this way appear on the **Dynamic** tab of the **MCP Servers** page.

## 6. Complete the consent flow \{#7-user-consent-flow}

The first time a person connects an MCP client, the gateway answers that sign-in is required. The client registers itself with the host by OAuth dynamic client registration and opens a browser window on the host. For every screen and what the gateway does behind it, see [Consent service](/permit-mcp-gateway/consent-service).

1. **Sign in:** the person signs in on the host, or clicks **Create Account** and enters a **Name**, **Email**, **Password**, and **Confirm Password**. Host accounts are separate from Permit.io accounts. On the hosted gateway, a new account verifies its email address first: a **Check your email** page asks the person to open the link in the email.

   ![Host sign-in page with email, password, and Create Account](/img/agent-security/consent/login.png)

2. **Choose an MCP server:** with the host URL, the **Connect MCP Server** screen lists the servers the person can access, each with its trust badge and tools. The person selects a server and clicks **Select**. With a server URL, this step is skipped.

   ![Connect MCP Server screen listing Cloudflare Docs and DeepWiki, with Refresh list and a custom URL field](/img/agent-security/consent/select-server.png)

3. **Review the request:** the review screen shows, from top to bottom:
   - **Target Server** and **Purpose, set by your admin**, the server's workflow intent.
   - **Name this agent (optional):** a name admins see instead of the app's name. It applies only the first time this app connects.
   - **Trust Level:** a Low, Medium, High slider that stops at **Max**, the person's maximum for this server. For this guide, pick **Low**.
   - **Task and expiry:** by default, the summary says the client reports its own task when it connects and that access never expires. Under **Advanced**, **Who states the agent's task** offers **I set the task** (the person writes the task, up to 500 characters, and the agent can't change it) or **Agent reports its task** (the default). **Access ends** offers **1 hour**, **1 day**, **7 days**, **Custom**, and **Forever**. **I set the task** defaults to 7 days, and **Agent reports its task** defaults to **Forever**.
   - **Available Tools:** each tool shows **Allowed** or **Denied** at the chosen level, with the level an admin set. The **Ask me before this agent changes or deletes anything** switch makes changes wait for the person's approval by email; reads run without asking. See [Human-in-the-loop approvals](/permit-mcp-gateway/human-in-the-loop).
   - The redirect address, then **Deny** and **Accept**.

   ![Task and expiry section with I set the task selected, a task for the agent, and access ending in 7 days](/img/agent-security/consent/task-expiry-person-sets.png)

4. **Accept:** the gateway saves a consent grant for this person, agent, and server, and the browser returns to the MCP client.

Each grant lasts until its end date, until the person or an admin revokes it, or until it goes unused for 90 days. While a grant is active, reconnecting the client doesn't show the consent screen again. People manage their own grants on the host's **Your MCP agents** page, `https://<subdomain>.agent.security/my-mcp-agents`: edit a task they set, read the history, or **Revoke** an agent.

![Your MCP agents page listing an approved agent with its trust level, task, end date, and Revoke](/img/agent-security/consent/my-mcp-agents.png)

## 7. Test an allowed and a denied tool call \{#8-runtime-authorization}

The gateway checks each tool call, resource read, and prompt request, in this order:

1. **Agent identity**, on a host that requires it: the agent must have a current registration.
2. **Two Permit checks:** the agent's, as `agent|<client_id>|<subject>`, and on imported servers the person's, as `human|<subject>`. Both must allow the call.
3. **The grant's trust ceiling:** the tool's trust level must be at or below the level the person approved.
4. **Approval rules:** a tool or server that requires admin approval.
5. **The Guardian**, when it is on.
6. **One approval**, when a rule, an unsure Guardian, or the person's **Ask me before this agent changes or deletes anything** switch asks for one.

An allowed call goes to the upstream server unchanged. The gateway writes one decision to the audit log for every call.

Test both outcomes with the **Low** trust level from step 6:

1. Ask your agent to read documentation through DeepWiki, such as "Use DeepWiki to read the documentation for facebook/react." The `read_wiki_structure` or `read_wiki_contents` call succeeds.
2. Ask your agent to call `ask_wiki_question`, the tool you set to **Medium**. The agent gets this error:

   ```text
   Permission denied: tool 'ask_wiki_question' is not allowed at your current trust level. To use this tool, an administrator needs to enable it or increase your trust level in the Agent Security Gateway.
   ```

:::note Agents can list tools they can't call
The gateway returns every tool in `tools/list` responses, whatever the agent's trust level, and adds `gateway_register_session` on hosts that require agent identity. The gateway enforces the trust level when the agent calls a tool, so an agent can see a tool and still be denied when it calls the tool.
:::

## 9. Require admin approval for a tool (optional)

Hold calls to a sensitive tool until an admin approves them.

1. On the server page, find the tool on the **Tools** card and turn on its **HITL** switch. To hold every tool on the server, turn on **Require approval for all tools** on the **Server Approval Policy** card.

   ![Tools card for DeepWiki with the HITL switch on for read_wiki_contents](/img/agent-security/platform/server-tools-approval.png)

2. Ask your agent to call the tool. The call waits, and a card appears on the **Pending** tab of **Approvals**. The card names the agent, the tool, the server, and the person, and shows the agent and person IDs, the arguments, a 5-minute countdown, and why the call is waiting, such as "A policy rule asks an admin to approve this tool." with **Details**.

   ![Pending approval card with the agent and person IDs, a countdown, Approve and Reject buttons, and the reason the call is waiting](/img/agent-security/platform/approval-card.png)

3. Click **Approve** to run the call, or **Reject** with a preset or custom reason. A rejected call returns the reason to the agent, such as "Tool 'read_wiki_contents' was rejected by admin: 'Use the Next.js docs for this task; React internals are out of scope.'. Contact your admin if you believe this is an error."

To email or post to Slack when an approval is waiting, add recipients and a Slack incoming webhook on the **Notifications** tab of **Approvals**. For timeouts, trusted agent bypass, and the person's own approvals, see [Human-in-the-loop approvals](/permit-mcp-gateway/human-in-the-loop).

## 10. Turn on agent identity and the Guardian (optional)

**Settings** > **Agent Identity** has three layers that check every agent call in order. A new host has all three off. Layers 2 and 3 need layer 1.

| Layer | What it checks |
| --- | --- |
| **Semantic identity** | Is this the same agent? The agent registers 12 words about its task, and the gateway stops an agent whose words drift, which can mean a prompt injection. |
| **Agent intent** | Does the agent mean to do what the person asked? At registration, the agent's task sentence is checked against the task the person set at consent. |
| **Guardian** | Does this call fit the task? An LLM judge grades each call against the server's workflow intent and refuses it or holds it for an admin. |

1. Turn on **Require Agent Identity**. Copy the snippet from the **Agent Identity Verification** alert into the agent's rules file: `CLAUDE.md` for Claude, `.cursorrules` for Cursor, or `.github/copilot-instructions.md` for Copilot. The server's tool list then includes `gateway_register_session`, which the agent calls with 12 words and a one-line task before it uses other tools. A registration lasts for the **Identity Token TTL**, 60 seconds by default.
2. Turn on **Enable Guardian Agent (LLM Intent Evaluator)**. Under **If the Guardian is unsure**, choose **Deny the call** or **Ask a human** (the default), which holds the call in **Approvals** for up to 5 minutes. Under **Where the Guardian's reason shows**, choose **Platform**, **Slack**, or **Email**.

   ![Guardian layer turned on, with the unsure action and the channels for the Guardian's reason](/img/agent-security/platform/settings-guardian.png)

3. On each server page, check the **Intent** card. Click **Edit intent** to change the workflow intent, then **Save intent**. Without an intent, the Guardian grades calls against the person's task when the person set one, and otherwise against the agent's 12 registered words.
4. Test the intent on the server's **Dry Run** tab. Pick a tool, enter JSON **Arguments**, and click **Start Dry Run**. The result shows the gates the call passes, the judge's **Alignment** and **Confidence** scores, and its reasoning. A dry run never reaches the upstream server and writes no audit row.

   ![Dry Run result with the gates, the judge's alignment and confidence scores, and its reasoning](/img/agent-security/platform/server-dry-run.png)

When the Guardian refuses a call, the agent gets "This call was refused by the security check." The agent's **Audit Logs** tab shows the Guardian's verdict and reasoning. For drift thresholds, rotating identity questions, and the task check, see [Check agent identity and intent](/permit-mcp-gateway/advanced-features).

## Configure how people sign in \{#authentication-methods}

Each host has its own sign-in methods for the consent flow. Email and password is on by default. To change them, open **Settings** for the host and go to **Authentication Methods**: add a method with **Add method**, set a **Global Email Domain Restriction**, and click **Save Configuration**.

![Authentication Methods section with Email / Password, the Global Email Domain Restriction field, and Add method](/img/agent-security/platform/settings-auth-methods.png)

The available methods are email and password, email one-time passcode (OTP), passkeys, Google, GitHub, and Microsoft OAuth, and Enterprise OIDC or Enterprise SAML single sign-on (SSO). You can also limit sign-in to specific email domains and send people with matching domains straight to your SSO provider.

:::warning Domain restrictions apply at two levels
The global domain list and a method's own domain list both apply, each only when it isn't empty. A person can sign in with a method only if their email domain is on every list that is set. Domains match exactly, so `acme.com` doesn't cover `contractor.acme.com`. Adding `partner.com` to the Google list alone doesn't let `partner.com` people sign in when the global list contains only `acme.com`.
:::

For setup steps, SAML service provider values, and callback URLs, see [Authentication methods](/permit-mcp-gateway/authentication-methods).

## Trust level reference

During import, the gateway assigns each tool a trust level by matching keywords anywhere in the tool name, ignoring case. You can change the level for any tool.

| Trust level | Includes | Naming patterns | Examples |
| ----------- | -------- | --------------- | -------- |
| **Low** | Read-only operations (default) | Default for tools not matching medium or high patterns | `get_user`, `list_issues`, `search_files` |
| **Medium** | Low + write operations | Tools containing: `create`, `write`, `update`, `set`, `modify`, `edit`, `put`, `post`, `insert`, `add`, `send`, `execute`, `run`, `invoke`, `submit`, `push`, `publish`, `deploy`, `apply`, `patch` | `create_issue`, `update_record`, `send_message` |
| **High** | Low + medium + destructive operations | Tools containing: `delete`, `remove`, `destroy`, `drop`, `purge`, `erase`, `truncate`, `terminate`, `kill`, `revoke` | `delete_repo`, `remove_member`, `destroy_environment` |

Trust levels are hierarchical: **high** includes all medium and low permissions, and **medium** includes all low permissions. A tool that matches no medium or high keyword gets **low** trust. A tool named `bulk_delete_users` gets **high** trust because its name contains `delete`.

## Troubleshooting

| Symptom | Likely cause | Fix |
| ------- | ------------ | --- |
| Agent performs actions that should be denied | The same MCP server is configured both through the gateway and directly in the MCP client, and the agent uses the direct connection. | Remove the direct MCP server entry from the client configuration so only the gateway URL remains. |
| MCP client gets HTTP `404` with `host_not_found` ("The requested host is not configured") | The gateway URL is wrong, or the host doesn't exist. | Copy the URL from the server's **MCP URL** card, and check the host on the **Hosts** page. |
| Consent screen says "No MCP servers available. Contact your administrator to grant you access to MCP servers." | No admin granted the person access to any server. | Grant access (see [step 4](#4-grant-user-access-to-mcp-servers)), then click **Refresh list** on the consent screen. |
| Consent screen says `MCP server "<server_key>" is not available or you don't have access to it.` | The person has no access to that server, or the server key in the URL is wrong. | Grant access to the server, or copy the URL again from the server's **MCP URL** card. |
| Consent screen says "This host does not allow connecting to dynamic MCP servers. Contact your administrator." | The URL uses `?upstream_mcp=` for a server nobody imported, and the host doesn't allow dynamic MCP connections. | Import the server and share its `/mcp/<server_key>` URL. |
| "Permission denied: tool '...' is not allowed at your current trust level" | The tool's trust level is above the level the person approved. | The person revokes the agent on **Your MCP agents**, then reconnects it from the MCP client and picks a higher level on the consent screen, up to their max trust. Reconnecting while the grant is active doesn't show the consent screen. Admins can lower an agent's trust level but can't raise it. |
| Consent doesn't offer a higher trust level | The person's **Max trust** for the server is too low. | Raise the person's **Trust level** on the **MCP Server Access** card of the **Humans** page. Then the person revokes the agent on **Your MCP agents**, reconnects it from the MCP client, and picks the higher level on the consent screen. |
| "Grant not found - complete consent flow first" | The person has no active grant for this server: it ended, was revoked, or was never approved. | Reconnect the MCP client to run the [consent flow](#7-user-consent-flow) again. |
| "Session not registered or expired. Call `gateway_register_session` ..." | The host requires agent identity, and the agent's registration expired, for example while a call waited for approval. | The agent calls `gateway_register_session` again. To give registrations longer, raise **Identity Token TTL** in **Settings** > **Agent Identity**. |
| "This call was refused by the security check." | The Guardian found that the call doesn't fit the intent. | Read the Guardian's reasoning on the agent's **Audit Logs** tab. If the call was legitimate, reword the server's workflow intent and test it with **Dry Run**. |
| Import asks for a **Client ID** and **Client Secret** | The upstream provider doesn't support automatic OAuth client registration. | Register an OAuth app with the provider using the redirect URI the page shows, then enter its credentials. |
| A tool is missing from the server page | You deselected the tool at import, or the upstream server added it later. | Click **Re-sync Tools** or **Add Tool** on the server's **Tools** card. |
| Can't find audit logs | Only one location was checked. | Check the **Audit Logs** tab of the agent, the person, or the server in [app.agent.security](https://app.agent.security), and **Audit Log** in the linked environment in [app.permit.io](https://app.permit.io). See [check activity and audit logs](#9-audit-logs). |

## Frequently asked questions \{#faq}

### How do trust levels work in Permit MCP Gateway?

During import, the gateway assigns each tool a trust level from its name: low for read tools, medium for tools such as `create` or `update`, and high for tools such as `delete`. Trust levels are hierarchical, so a high-trust agent can call medium and low tools. An admin can change any tool's level. See the [trust level reference](#trust-level-reference).

### Who decides how much access an agent gets?

Both the admin and the person. The admin sets the highest trust level each person can approve on each server, and the person picks a level up to that maximum on the consent screen. The agent's effective level is the lower of the two. An admin can lower an agent's level or revoke it. Only the person can raise it: the person revokes the agent on **Your MCP agents**, then reconnects it from the MCP client and picks a higher level on the consent screen, up to their max trust.

### What is an agent in Permit MCP Gateway?

One person using one MCP client. When two people connect the same client, the gateway creates two agents, `agent|<client_id>|<subject>` for each person, each with its own trust level, sessions, and audit log.

### How do I test that the gateway denies a tool call?

Complete [step 7](#8-runtime-authorization): call a tool at your approved trust level, then call a tool above it. The gateway returns a permission error for the second call, and the audit log shows both decisions.

### Where do I find the audit log?

On the **Audit Logs** tab of each agent, person, and MCP server page in [app.agent.security](https://app.agent.security), and on the **Audit Log** screen of the linked environment in [app.permit.io](https://app.permit.io). The **Dashboard** shows totals and a live feed.

### What does Allow Dynamic MCP Connections do?

It lets people connect to any MCP server URL, including servers an admin never imported. Tool calls are still authorized and logged. The setting is on by default when you create a host, and after it is on you can't turn it off.
