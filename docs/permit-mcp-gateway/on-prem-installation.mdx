Install Permit MCP Gateway with Helm in your own Kubernetes cluster, connected to your self-hosted Permit Platform for authentication and authorization. This page is for platform operators who run a fully on-premises deployment. When you finish, the gateway, the consent service, and the admin dashboard run in your cluster, and you can sign in to the admin dashboard on your own domain.

:::info Enterprise plans
On-premises deployment is available on **Enterprise plans**. To compare deployment models before you install, see [Enterprise deployment](/permit-mcp-gateway/enterprise-deployment).
:::

## Prerequisites

| Requirement | Details |
| --- | --- |
| **Permit Platform deployed** | Install the Permit Platform first, with the [Permit Platform installation guide](/how-to/deploy/on-prem/installation). The Permit Platform provides Keycloak (authentication) and the Permit backend (authorization). |
| **Kubernetes cluster** (1.25+) | With an NGINX ingress controller installed, with ingress class `nginx`. Check the `README.md` in your installer package for the supported versions of your release. |
| **Helm 3.x** and **kubectl** | Configured for your cluster. |
| **Docker** | Installed on the machine where you load images and push them to your registry. |
| **Private container registry** | Hosts the MCP Gateway images, such as Google Artifact Registry, Amazon ECR, or Harbor. |
| **TLS certificate** | For your MCP Gateway domain. The sign-in flow requires HTTPS. |
| **DNS** | You can create DNS records for your MCP Gateway domain: a wildcard record and a record for the admin dashboard. |
| **DNS resolution inside the cluster** | Your Permit Platform URL and your MCP Gateway domain resolve from inside the cluster. Pods call these URLs server-side, for example when the admin dashboard exchanges OIDC tokens with Keycloak. |

### Information you'll need \{#information-youll-need}

The installation uses three values:

| Item | Example | Used for |
| --- | --- | --- |
| **Permit Platform URL** | `https://permit.yourcompany.com` | Permit API URL and OpenID Connect (OIDC) discovery URL |
| **MCP Gateway domain** | `mcp.yourcompany.com` | Base domain for host subdomains, and the admin dashboard host (`app.mcp.yourcompany.com`) |
| **Keycloak admin password** | Retrieved from a Kubernetes secret | Automatic creation of the OIDC client in Keycloak |

Retrieve the Keycloak admin password from your Permit Platform cluster. Replace `<permit-platform-namespace>` with the namespace where the Permit Platform runs:

```bash
kubectl get secret global-infrastructure-secret \
  -n <permit-platform-namespace> \
  -o jsonpath='{.data.KEYCLOAK_ADMIN_PASSWORD}' | base64 -d
```

## Network egress requirements \{#egress-requirements}

The gateway runs fully on-premises. This table lists each outbound connection the gateway components can make:

| Destination | Required | Purpose |
| --- | --- | --- |
| Your Permit Platform URL | **Required** | Permit API for authorization, and Keycloak for OIDC |
| Your PDP URL (set per host in the admin dashboard) | **Required** | Policy decision point (PDP) for tool-level authorization |
| Your container registry | Install time only | Image pulls during deployment |
| Your identity provider (IdP) or OIDC discovery URL | **Required** | Admin dashboard sign-in (server-side token exchange) |
| Upstream MCP servers that you configure | **Required** | The gateway proxies tool calls to upstream MCP servers. The consent service and the admin dashboard also connect to them to list their tools and run their OAuth flow. |
| Your SMTP relay | Only if you [configure email](#email-notifications) | Sign-in, invite, and approval emails |
| A Slack incoming webhook URL | Only if an admin sets one in **Approvals** > **Notifications** | The gateway posts approval notifications to Slack |
| Amazon Bedrock | Only if you turn on the Guardian | The Guardian LLM judge grades tool calls. The Guardian is off in the on-premises values template. |

Normal operation doesn't require a connection to `api.permit.io`, `app.permit.io`, or any other external cloud service. The on-premises values template turns off the Datadog and Segment integrations, and the chart refuses the `mailgun` email provider in on-premises mode.

## Install the gateway \{#installation}

### 1. Extract the installer package \{#step-1--extract-the-installer-package}

Your Permit team sends you a `.tar.gz` installer package. Extract the package:

```bash
tar -xzf agent-security-on-prem-installer-*.tar.gz
cd agent-security-on-prem-installer-*
```

The package contains:

```text
agent-security-on-prem-installer-*/
├── charts/agent-security/     # Helm chart
├── images/all-images.tar.gz   # Docker images (bundled for air-gapped use)
├── scripts/
│   ├── load-images.sh         # Push images to your registry
│   └── setup-keycloak.sh      # Manual Keycloak setup (for debugging)
├── values.yaml                # On-prem values template
└── README.md                  # Quick reference
```

### 2. Push the images to your registry \{#step-2--push-images-to-your-registry}

Authenticate to your container registry, then run the image loader. Replace `<your-registry>` with your registry path:

```bash
# Authenticate (example for GCP)
gcloud auth configure-docker us-central1-docker.pkg.dev

# Push all images and update values.yaml with your registry paths
./scripts/load-images.sh --registry <your-registry>

# See all options
./scripts/load-images.sh --help
```

Examples for common registries:

```bash
# Google Artifact Registry
./scripts/load-images.sh --registry us-central1-docker.pkg.dev/my-project/mcp-gateway

# AWS ECR
aws ecr get-login-password --region us-east-1 | docker login --username AWS --password-stdin 123456789.dkr.ecr.us-east-1.amazonaws.com
./scripts/load-images.sh --registry 123456789.dkr.ecr.us-east-1.amazonaws.com/mcp-gateway

# Harbor
./scripts/load-images.sh --registry harbor.company.com/mcp-gateway
```

The `load-images.sh` script:

1. Loads the images from the bundled tarball into your local Docker.
2. Retags each image with your registry prefix.
3. Pushes the images to your registry.
4. Replaces the `REGISTRY` placeholder in `values.yaml` with your registry.

### 3. Choose how to pass the Keycloak admin password \{#step-3--configure-keycloak-oidc-integration}

During installation, a Helm post-install Job creates the Keycloak OIDC client for the admin dashboard. You don't set up Keycloak by hand. The Job:

- Creates a confidential OIDC client, `agent-security-platform`, in the `permit-platform` Keycloak realm.
- Adds the `permit-backend-audience` mapper, which the Permit API needs to accept the admin dashboard's tokens.
- Configures the `offline_access` scope and role.
- Stores the generated client secret in a Kubernetes secret that the admin dashboard reads.

The Job needs the Keycloak admin password from [Information you'll need](#information-youll-need). You set one of these two options in `my-values.yaml` in [step 6](#step-6--configure-values). The on-premises values template ships with Option A.

**Option A: reference the existing secret (recommended)**

```yaml
permitPlatform:
  namespace: "<permit-platform-namespace>"
  keycloakAdminPasswordSecret: "global-infrastructure-secret"
  keycloakAdminPasswordSecretKey: "KEYCLOAK_ADMIN_PASSWORD"
```

With Option A, the Job reads the secret through the Kubernetes API of the cluster you install into, from the `permitPlatform.namespace` namespace. If the Permit Platform runs in a different cluster, use Option B.

**Option B: plaintext value**

:::warning Plaintext passwords in values files
With Option B, the Keycloak admin password is stored in plain text in `my-values.yaml`. Anyone who can read that file can sign in to Keycloak as an admin. Use Option A, or keep `my-values.yaml` out of version control.
:::

```yaml
permitPlatform:
  namespace: "<permit-platform-namespace>"
  keycloakAdminPassword: "<password>"
```

With Option B, Helm also stores the password in the release secret in your cluster.

If your Permit Platform's Keycloak uses a realm other than `permit-platform`, set `permitPlatform.realm` to that realm, and use the same realm in `platform.oidc.discoveryUrl` in [step 6](#step-6--configure-values).

The Keycloak setup Job is idempotent, so it runs safely on each `helm upgrade`. The Job never recreates an existing OIDC client.

:::note Admin dashboard pod waits for the Keycloak setup Job
Until the Keycloak setup Job creates the OIDC secret, the admin dashboard (platform) pod shows `CreateContainerConfigError`. This lasts about 30 to 60 seconds, and the pod recovers without action.
:::

#### Manual Keycloak setup (for debugging only) \{#manual-alternative-for-debugging-only}

If the Helm Job can't reach Keycloak, for example because network policies block traffic between namespaces, run the standalone setup script instead. Run the script only if the Helm Job fails, and don't run both.

```bash
./scripts/setup-keycloak.sh --agent-security-domain mcp.yourcompany.com
./scripts/setup-keycloak.sh --help    # See all options
```

### 4. Deploy a PDP \{#step-4--deploy-a-pdp}

The gateway sends each authorization check to a [policy decision point (PDP)](/how-to/deploy/on-prem/pdp-deployment). If you don't have a PDP deployed, install one with the Permit PDP Helm chart:

```bash
helm repo add pdp https://permitio.github.io/pdp-helm
helm repo update

helm install pdp pdp/pdp \
  --set pdp.ApiKey="<YOUR_PERMIT_API_KEY>" \
  --set "pdp.pdpEnvs[0].name=PDP_CONTROL_PLANE" \
  --set "pdp.pdpEnvs[0].value=<PERMIT_BACKEND_INTERNAL_URL>" \
  --namespace <permit-platform-namespace>
```

Replace these placeholders:

| Placeholder | Replace with |
| --- | --- |
| `<YOUR_PERMIT_API_KEY>` | The environment API key from your Permit Platform dashboard. See [Get your API key](/overview/get-api-key). |
| `<PERMIT_BACKEND_INTERNAL_URL>` | The Permit backend service URL inside your cluster, such as `http://permit-backend-v2.<namespace>.svc.cluster.local:8000` |
| `<permit-platform-namespace>` | The namespace where the Permit Platform runs |

Note the PDP service URL. You enter it in the **PDP URL** field when you [create a host](/permit-mcp-gateway/host-setup) in the admin dashboard.

#### PDP URL is set per host in the admin dashboard \{#pdp-url--configured-per-host-in-the-platform-ui}

The Helm values don't set a global PDP URL. In on-premises mode, each host has its own PDP URL: the **PDP URL** field on the **Create Host** form, and the **Policy Decision Point (PDP)** section of the host's **Settings** page. Different hosts can use different PDPs.

The PDP must use the API key of the Permit environment that the host uses. If the keys don't match, the admin dashboard reports that the PDP rejected the API key.

| Option | URL | When to use |
| --- | --- | --- |
| **Internal Kubernetes DNS** | `http://permitio-pdp.<namespace>.svc.cluster.local:7766` | The PDP and the gateway run in the same cluster (recommended) |
| **External URL** | `https://pdp.yourcompany.com` | The PDP is exposed through an ingress or runs in a different cluster |

The PDP Helm chart names its service `permitio-pdp` and listens on port `7766` by default.

:::tip One PDP per environment or tenant
You can deploy several PDPs, such as one per environment or per tenant, and give each host a different PDP URL. Each host uses its own PDP.
:::

### 5. Create the TLS secret \{#step-5--create-tls-secret}

The sign-in flow requires HTTPS because its cookies are set with `secure: true`. Create a TLS secret from your certificate and key files:

```bash
kubectl create secret tls agent-security-tls \
  --cert=path/to/tls.crt \
  --key=path/to/tls.key \
  -n agent-security --create-namespace
```

To manage certificates automatically instead, use [cert-manager](https://cert-manager.io/) with annotations on your ingresses.

### 6. Configure values \{#step-6--configure-values}

`values.yaml` already has your registry paths from [step 2](#step-2--push-images-to-your-registry). Copy `values.yaml` to a file for your settings:

```bash
cp values.yaml my-values.yaml
```

Open `my-values.yaml` and set the required values:

```yaml
global:
  # Your MCP Gateway domain: tenants will be at <name>.mcp.yourcompany.com
  baseDomain: "mcp.yourcompany.com"
  permit:
    # Your Permit Platform URL
    apiUrl: "https://permit.yourcompany.com"
    # PDP URL is set per-host in the Platform UI (not here)

# Keycloak integration (the Helm Job creates the OIDC client)
permitPlatform:
  namespace: "<permit-platform-namespace>"
  keycloakAdminPasswordSecret: "global-infrastructure-secret"
  keycloakAdminPasswordSecretKey: "KEYCLOAK_ADMIN_PASSWORD"

# OpenResty reverse proxy (required for on-prem)
nginx:
  enabled: true

# Platform UI
platform:
  ingress:
    host: "app.mcp.yourcompany.com"
  oidc:
    providerId: "keycloak"
    providerName: "Keycloak"
    discoveryUrl: "https://permit.yourcompany.com/auth/realms/permit-platform/.well-known/openid-configuration"
    clientId: "agent-security-platform"
    existingSecret: "agent-security-oidc-secret"
    existingSecretKey: "OIDC_CLIENT_SECRET"
```

Set these values for your installation:

| Key | Set to |
| --- | --- |
| `global.baseDomain` | Your MCP Gateway domain. Hosts get subdomains of this domain. |
| `global.permit.apiUrl` | Your Permit Platform URL. |
| `permitPlatform` | The namespace of your Permit Platform, and the Keycloak password option you chose in [step 3](#step-3--configure-keycloak-oidc-integration). The template ships with Option A. For Option B, replace the `keycloakAdminPasswordSecret` and `keycloakAdminPasswordSecretKey` lines with a `keycloakAdminPassword` line. |
| `platform.ingress.host` | `app.` followed by your MCP Gateway domain. |
| `platform.oidc.discoveryUrl` | Your Permit Platform URL followed by `/auth/realms/permit-platform/.well-known/openid-configuration`. |

Keep `nginx.enabled: true`. The gateway ingress routes traffic through the bundled OpenResty reverse proxy.

The chart sets these values for you:

- **Keycloak OIDC client:** created by the Helm Job during installation.
- **Database passwords:** generated, and kept across upgrades.
- **Redis password:** generated.
- **Admin tokens and session secrets:** generated.
- **Email verification for new accounts:** off. In on-premises mode, the chart turns it off whatever `email.requireVerification` is set to. To send sign-in, invite, and approval emails, see [Email notifications](#email-notifications).

### 7. Install the Helm chart \{#step-7--install}

```bash
helm install agent-security ./charts/agent-security \
  -f my-values.yaml \
  -n agent-security \
  --create-namespace --wait --timeout=10m
```

The command returns when all resources are ready, or fails after 10 minutes. If it fails, see [Install failed](#install-failed).

### 8. Configure DNS \{#step-8--configure-dns}

Get the external IP address of your ingress:

```bash
# Get the ingress controller IP
kubectl get ingress -n agent-security
```

Add these DNS records with your DNS provider, using the IP address from the `ADDRESS` column:

| Record | Type | Value |
| --- | --- | --- |
| `*.mcp.yourcompany.com` | A | `<ingress-ip>` |
| `app.mcp.yourcompany.com` | A | `<ingress-ip>` |

:::note Add an explicit record for the admin dashboard
With some DNS providers, the wildcard record doesn't resolve `app.mcp.yourcompany.com`. If host subdomains work but the admin dashboard is unreachable, check that the explicit `app.mcp.yourcompany.com` record exists.
:::

### 9. Attach the TLS secret to the ingresses \{#step-9--patch-ingresses-for-tls}

If you don't use cert-manager, attach the TLS secret from [step 5](#step-5--create-tls-secret) to both ingresses. Replace `mcp.yourcompany.com` with your MCP Gateway domain:

```bash
kubectl patch ingress agent-security-platform -n agent-security --type=json \
  -p='[{"op":"add","path":"/spec/tls","value":[{"hosts":["app.mcp.yourcompany.com"],"secretName":"agent-security-tls"}]}]'

kubectl patch ingress agent-security-gateway -n agent-security --type=json \
  -p='[{"op":"add","path":"/spec/tls","value":[{"hosts":["*.mcp.yourcompany.com"],"secretName":"agent-security-tls"}]}]'
```

Without TLS on the ingresses, admin dashboard sign-in fails and returns you to the sign-in page.

## Verify the installation \{#step-10--verify}

1. Check that the pods are running:

   ```bash
   kubectl get pods -n agent-security
   ```

   With the replica counts in the default on-premises values template, you see 10 pods, each `1/1 Running`:

   | Component | Pods | What it does |
   | --- | --- | --- |
   | Gateway | 2 | MCP proxy that enforces authentication and authorization |
   | Consent service | 2 | OAuth 2.1 authorization server |
   | Platform | 2 | Admin dashboard |
   | NGINX (OpenResty) | 2 | Reverse proxy that routes requests |
   | PostgreSQL | 1 | User and session storage |
   | Redis | 1 | Gateway state |

   If you changed replica counts in `my-values.yaml`, or use an external database, the pod count differs. On the first deploy, gateway pods can show 1 or 2 restarts while Redis starts. The gateway reconnects without action.

2. Check the ingresses:

   ```bash
   kubectl get ingress -n agent-security
   ```

   You see two ingresses:

   | Name | Host | Purpose |
   | --- | --- | --- |
   | `agent-security-gateway` | `*.mcp.yourcompany.com` | Traffic to gateway hosts |
   | `agent-security-platform` | `app.mcp.yourcompany.com` | Admin dashboard |

3. Check the admin dashboard health endpoint:

   ```bash
   curl -s https://app.mcp.yourcompany.com/api/health
   # Expected: {"status":"healthy"}
   ```

   The response is `{"status":"healthy"}`.

4. Open `https://app.mcp.yourcompany.com` in your browser. The admin dashboard sign-in page shows a **Sign in with Keycloak** button.

## Configuration options

### Use an external PostgreSQL and Redis \{#external-database}

To use your own PostgreSQL and Redis instead of the bundled ones, add these values to `my-values.yaml`. Each `existingSecret` names a Kubernetes secret in the `agent-security` namespace, and `existingSecretKey` names the key that holds the connection URL:

```yaml
postgres:
  enabled: false
externalDatabase:
  consent:
    existingSecret: "my-postgres-secret"
    existingSecretKey: "DATABASE_URL"
  platform:
    existingSecret: "my-postgres-secret"
    existingSecretKey: "DATABASE_URL"

redis:
  enabled: false
externalRedis:
  enabled: true
  host: "redis.yourcompany.com"
  port: 6379
  existingSecret: "my-redis-secret"
  existingSecretKey: "REDIS_URL"
```

Only the gateway connects to Redis. How the gateway connects depends on whether you set `externalRedis.existingSecret`:

- **With `existingSecret`:** the gateway uses the full URL in the secret, and the chart ignores `host`, `port`, and `tls`. Use a `rediss://` URL for a Redis that requires TLS, and a `redis://` URL for one that doesn't.
- **Without `existingSecret`:** the chart builds the URL from `host`, `port`, and `tls`. `tls` defaults to `true`, which gives a `rediss://` URL. For a Redis without TLS, set `tls: false`.

The chart refuses to install when both the bundled Redis (`redis.enabled: true`) and an external Redis are set. The same applies to PostgreSQL.

### Storage

To set the storage class and volume size for the bundled PostgreSQL and Redis:

```yaml
postgres:
  persistence:
    storageClass: "your-storage-class"
    size: 20Gi
redis:
  persistence:
    storageClass: "your-storage-class"
    size: 2Gi
```

### Email notifications

The consent service and the admin dashboard send email through an SMTP relay. Without one, these emails aren't delivered:

| Sent by | Email |
| --- | --- |
| Consent service | Password reset links and sign-in codes, when those sign-in methods are on for the host |
| Consent service | Invites that an admin sends from **Humans** > **Invite by Email** |
| Consent service | Approval requests to a person who turned on **Ask me before this agent changes or deletes anything** on the consent screen |
| Consent service | Emailed confirmation codes, when a person confirms an approval decision or a change to their agent with a code |
| Consent service | Notices when a person adds or removes a passkey |
| Admin dashboard | Approval notifications to the email recipients set in **Approvals** > **Notifications** |

The chart's `email` values set the provider and the sender address. Set the relay's host and port as environment variables on both services:

```yaml
email:
  provider: "smtp"
  from: "MCP Gateway <noreply@yourcompany.com>"

consentService:
  env:
    SMTP_HOST: "smtp.yourcompany.com"
    SMTP_PORT: "25"

platform:
  env:
    SMTP_HOST: "smtp.yourcompany.com"
    SMTP_PORT: "25"
```

The SMTP client connects without a username or password, and without implicit TLS (port 465). Use a relay that accepts mail from the cluster without authentication.

:::note SMTP only in on-premises mode
The `mailgun` email provider isn't available in on-premises mode, so email can't be sent through an external cloud service by mistake.
:::

### Permit Platform in a different cluster \{#cross-cluster-deployment}

If the Permit Platform runs in a different cluster, the Keycloak setup Job can't find Keycloak through Kubernetes DNS. Set the Keycloak URL, and pass the password with Option B from [step 3](#step-3--configure-keycloak-oidc-integration), because Option A reads the secret from the cluster you install into:

```yaml
permitPlatform:
  keycloakUrl: "https://permit.yourcompany.com/auth"
  keycloakAdminPassword: "<password>"
```

When `keycloakUrl` is empty, the Job uses `http://keycloak.<permit-platform-namespace>.svc.cluster.local:8080`.

### Keep secrets out of ingress controller logs \{#ingress-controller-logs}

The default access log formats of NGINX ingress controllers record each request's full URL, including the query string. For the gateway, the query string can hold secrets: OAuth authorization codes and `state` on sign-in callbacks, and MCP server URLs that carry upstream credentials. A password reset link also carries its token in the path (`/api/auth/reset-password/<token>`). What to set depends on your controller.

**Community ingress-nginx (`kubernetes/ingress-nginx`)**

- **Gateway host (`*.mcp.yourcompany.com`):** the chart sets `nginx.ingress.kubernetes.io/enable-access-log: "false"` on the gateway ingress. The bundled OpenResty behind it logs each request without its query string and with the reset token masked. Keep the controller's access log off for this host.
- **Admin dashboard host (`app.mcp.yourcompany.com`):** requests go from your controller straight to the admin dashboard, so the controller's log is the only access log. Set `log-format-upstream` to a format that logs the path without the query string, in the ingress-nginx Helm values or the same key in the `ingress-nginx-controller` ConfigMap:

```yaml
controller:
  config:
    log-format-upstream: '$remote_addr - - [$time_local] "$request_method $uri $server_protocol" $status $body_bytes_sent "-" "$http_user_agent" $request_length $request_time [$proxy_upstream_name] [$proxy_alternative_upstream_name] $upstream_addr $upstream_response_length $upstream_response_time $upstream_status $req_id'
```

This format keeps the default fields except the query string, the Referer, and `$remote_user`, and applies to every ingress the controller serves.

**F5 NGINX Ingress Controller (`nginx/kubernetes-ingress`)**

This controller ignores `nginx.ingress.kubernetes.io/*` annotations, so it logs the gateway host as well. Set a format that logs the path without the query string and with the reset token masked, in the controller's Helm values or the same keys in its ConfigMap:

```yaml
controller:
  config:
    entries:
      http-snippets: |
        map $request_uri $redacted_path {
          ~^(?<redacted_path_reset>[^?#]*/reset-password/)[^/?#]+ "${redacted_path_reset}[redacted]";
          ~^(?<redacted_path_plain>[^?#]+) $redacted_path_plain;
          default "-";
        }
      log-format: '$remote_addr - - [$time_local] "$request_method $redacted_path $server_protocol" $status $body_bytes_sent "-" "$http_user_agent" "$http_x_forwarded_for"'
```

**Error logs**

No setting keeps the query string out of an NGINX error log. When a request fails, for example because an upstream refuses the connection or a rate limit rejects the request, the error line quotes the full request line, the upstream URL, the `Host` header, and the Referer. This applies to the error log of the bundled OpenResty (stderr of the `agent-security-nginx` pods) and to your controller's error log. If you ship pod logs to a log collector, mask these fields there: the query string in the `request:`, `upstream:`, and `referrer:` fields, a `user:password@` part in the `host:` and `referrer:` fields, and the path segment after `/reset-password/`. The `log_processing_rules` in `charts/agent-security/templates/nginx/deployment.yaml` in your installer package are a tested set of patterns (RE2 syntax) to start from.

## Upgrade the gateway \{#upgrading}

Run `helm upgrade` with the same values file:

```bash
helm upgrade agent-security ./charts/agent-security \
  -f my-values.yaml \
  -n agent-security \
  --wait --timeout=10m
```

Upgrades keep the generated secrets and the data in PostgreSQL and Redis. Run the [verification checks](#step-10--verify) after each upgrade.

If an upgrade fails and pods are unhealthy, roll back to the previous release:

```bash
helm rollback agent-security -n agent-security --wait --timeout=10m
```

## Troubleshooting

| Symptom | Cause | Fix |
| --- | --- | --- |
| `helm install` fails | A pod or Job failed to start | See [Install failed](#install-failed) |
| Gateway pods restart on first deploy | Redis is still starting | No action. The gateway reconnects after 1 or 2 restarts. |
| Admin dashboard sign-in returns to the sign-in page | No TLS on the ingresses, so the browser drops the secure cookies | [Attach the TLS secret](#step-9--patch-ingresses-for-tls) |
| "Invalid credentials" when creating an organization | The Keycloak OIDC client is missing the audience mapper | See [Invalid credentials when creating an organization](#invalid-credentials-when-creating-an-organization) |
| Pods stuck in `CreateContainerConfigError` | The Keycloak setup Job hasn't created the OIDC secret yet | Wait 30 to 60 seconds. If the state persists, [check the logs](#checking-logs) of the Keycloak setup Job. |
| Admin dashboard pod fails with an OIDC error | The OIDC client, its secret, or the URLs the pod calls are wrong | See [Admin dashboard fails with an OIDC error](#admin-dashboard-fails-with-an-oidc-error) |
| Consent service or platform pods fail to start with migration errors | PostgreSQL isn't ready yet | See [Database migration errors](#database-migration-errors) |

### Install failed

If `helm install` fails, find the failed pod or Job, fix the cause, then uninstall and install again. Uninstalling keeps the persistent volume claims (PVCs), so your data stays.

```bash
# Check what failed
kubectl get pods -n agent-security
kubectl get jobs -n agent-security

# Uninstall (PVCs are retained, your data is safe)
helm uninstall agent-security -n agent-security

# Re-run install after fixing the issue
helm install agent-security ./charts/agent-security \
  -f my-values.yaml -n agent-security \
  --create-namespace --wait --timeout=10m
```

### Gateway pods restarting

On the first deploy, Redis takes a few seconds to start. The gateway reconnects after 1 or 2 restarts, and no action is needed.

### Platform login redirects back to login page \{#platform-login-redirects-back-to-login-page}

The ingresses have no TLS. The sign-in flow sets secure cookies, and the browser sends secure cookies only over HTTPS. [Attach the TLS secret to the ingresses](#step-9--patch-ingresses-for-tls).

### "Invalid credentials" when creating an organization \{#invalid-credentials-when-creating-an-organization}

The Keycloak OIDC client might be missing the required audience mapper. Check the logs of the Keycloak setup Job. Helm deletes the Job when it succeeds, so this command returns logs only while the Job runs or after it fails:

```bash
kubectl logs -n agent-security -l app.kubernetes.io/component=keycloak-setup
```

If the Job failed, run `helm upgrade` with the same values to run the Job again.

### Pods stuck in CreateContainerConfigError

The OIDC secret doesn't exist yet. The Keycloak setup Job runs after the main resources deploy. The platform pod recovers when the Job completes, usually within 30 to 60 seconds.

### Admin dashboard fails with an OIDC error

Check each of these:

- The Keycloak setup Job didn't fail. Helm deletes the Job when it succeeds, so `kubectl get jobs -n agent-security | grep keycloak` returns nothing after a success, and lists the Job while it runs or after it fails.
- The Keycloak client `agent-security-platform` exists, with the `permit-backend-audience` mapper and the `offline_access` scope.
- The `agent-security-oidc-secret` secret holds the client's current secret.
- The Keycloak admin password in your `permitPlatform` values is correct.
- The Permit Platform URL resolves from inside the admin dashboard pod.
- The TLS certificate is valid. The admin dashboard exchanges OIDC tokens server-side over HTTPS.

### Database migration errors

Consent service or platform pods fail to start if PostgreSQL isn't ready yet. The migration init containers retry on their own. To check the migration logs:

```bash
kubectl logs -n agent-security deployment/agent-security-consent-service -c db-migration
kubectl logs -n agent-security deployment/agent-security-platform -c db-migration
```

### Checking logs

To read recent logs for each component:

```bash
# Gateway
kubectl logs -n agent-security deployment/agent-security-gateway --tail=20

# Consent Service
kubectl logs -n agent-security deployment/agent-security-consent-service --tail=20

# Platform
kubectl logs -n agent-security deployment/agent-security-platform --tail=20

# Keycloak setup Job (only while it runs or after it fails; Helm deletes it on success)
kubectl logs -n agent-security -l app.kubernetes.io/component=keycloak-setup
```
