Show or hide UI components in a Next.js app based on the signed-in user's role and attributes. This worked example is for frontend developers who want to toggle features per user: it models each UI tile as a Permit.io resource, checks permissions in bulk from a backend route, and renders only the tiles the user is allowed to view.

Use this pattern to limit a feature to a group of test users, or to change the app for paying users based on their plan or location.

## What you build \{#what-well-build}

The demo app is a dashboard that loads four tiles: **Products**, **Product Configurators**, **Project Builder**, and **Topics for you**. For each tile, the app asks Permit whether the signed-in user can `view` it, and renders the tile only when the answer is `true`.

The example uses attribute-based access control (ABAC), which bases decisions on attributes of the user and the resource, on top of role-based access control (RBAC), which bases decisions on the user's role. Each user carries a `country` and a `channel` attribute. To learn how ABAC policies work, see [ABAC overview](/how-to/build-policies/abac/overview).

:::note Attributes from your identity provider
The `country` and `channel` values don't have to be stored in Permit. Your app reads them from the identity provider and passes them in each permission check as just-in-time (JIT) attributes. The policy decision point (PDP) evaluates the policy with the values in the request. The user and the user's role assignment must still exist in Permit. See [Pass just-in-time (JIT) attributes](/how-to/enforce-permissions/check#just-in-time-jit-attributes).
:::

The flow has three parts:

| Part | Where it runs | What it does |
|---|---|---|
| Permission check route | Your backend (Next.js API route) | Receives a list of actions and resources, calls `permit.check()` for each one against the PDP, and returns the list of results. |
| `AbilityLoader` | Your frontend (React) | Uses `permit-fe-sdk` to call the permission check route once for all tiles, and stores the results. |
| Conditional rendering | Your frontend (React) | Calls `permitState.check()` for each tile and renders the tile when the stored result is `true`. |

## Prerequisites

- A Permit.io account and an environment API key. See [Get your API key](/overview/get-api-key).
- A running PDP that your backend can reach at `http://localhost:7766`. See [Run the PDP](/overview/run-pdp).
- A Next.js (React) app to render the dashboard in.
- The `permitio` package installed in your backend, and the `permit-fe-sdk` and `@casl/ability` packages installed in your frontend.
- An authentication provider that stores user metadata. This example uses [Clerk](https://clerk.com/). Any provider works if your app can read the user's ID and attributes after sign-in.
- The signed-in users synced to Permit with the `Viewer` role assigned. See [Sync users](/how-to/sync-users).

## 1. Model the attributes and resources in Permit \{#modeling-basic-roles-and-resources}

Define the attributes, the resources, and the role that the dashboard checks.

1. In your authentication provider, store the attributes on each user. In Clerk, the example stores `country` and `channel` in the user's public metadata.

   ![Clerk user metadata editor with country and channel values in the public metadata](/ui-videos/modeling/custom-ui-demo/clerk-attributes.png)

2. In Permit, define the same attributes with their names and data types. Both `country` and `channel` are of type `String`.

   ![Permit ABAC Options form with a country attribute and a channel attribute, both of type String](/ui-videos/modeling/custom-ui-demo/attributes.png)

3. On the **Policy** screen, open the **Resources** tab and create one resource for each UI component you want to toggle. Start with the Product Configurators resource.

   ![New Resource form with the name Product Configurators, the key Product_Configurators, and a view action](/ui-videos/modeling/custom-ui-demo/new-resource.png)

4. Create the other three resources, so the environment has all four: `Products`, `Product_Configurators`, `Project_Builder`, and `Topics_for_you`. Each resource has a `view` action.

   ![Permit Resources tab listing the Products, Product Configurators, Project Builder, and Topics for you resources](/ui-videos/modeling/custom-ui-demo/all-resources.png)

5. Add the `country` and `channel` attributes to each resource. The permission check route passes resource attributes along with the resource and action.

   ![Permit Resources tab showing the four tile resources, each with country: string and channel: string attributes](/ui-videos/modeling/custom-ui-demo/resources-with-attributes.png)

## 2. Create the Viewer role and its policy \{#rendering-the-ui-based-on-permissions}

Create a `Viewer` role on the **Roles** tab. The policy for the `Viewer` role decides which tiles a viewer sees.

![Permit Roles tab with the Viewer role](/ui-videos/modeling/custom-ui-demo/viewer-role.png)

In the **Policy Editor**, check `view` for each resource the `Viewer` role may see. A user with the `view` permission on a resource sees the matching tile. In the following policy, viewers see only the **Topics for you** tile:

![Policy Editor where the Viewer role has view checked only on Topics for you](/ui-videos/modeling/custom-ui-demo/viewer-role-policy-limited.png)

Check `view` on all four resources to show every tile:

![Policy Editor where the Viewer role has view checked on all four tile resources](/ui-videos/modeling/custom-ui-demo/viewer-role-policy.png)

To make a tile depend on `country` or `channel` instead of the role alone, create user sets or resource sets with conditions on those attributes in the **ABAC Rules** tab, and grant `view` to those sets. See [Build ABAC policies](/how-to/build-policies/abac/building-abac-policy).

## 3. Create the permission check route \{#creating-an-api-endpoint-to-handle-permission-checks}

`permit-fe-sdk` doesn't call Permit directly. The frontend sends its checks to a route in your backend, and the route calls the PDP. When the frontend loads permissions in bulk, `permit-fe-sdk` sends a `POST` request to the route with the user ID in the `user` query parameter and a `resourcesAndActions` array in the body. The route must return a `permittedList` array with one boolean per item, in the same order.

The following route handles that request. The example serves it at `/api/something`; use any path, and pass the same path as `backendUrl` in the `AbilityLoader`.

```js
import { Permit } from "permitio";

const permit = new Permit({
  token: "YOUR_PERMIT_API_KEY",
  pdp: "http://localhost:7766",
});

export default async function handler(req, res) {
  try {
    const { resourcesAndActions } = req.body;
    const { user: userId } = req.query;

    if (!userId) {
      return res.status(400).json({ error: "No userId provided." });
    }

    const checkPermissions = async (resourceAndAction) => {
      const { resource, action, userAttributes, resourceAttributes } = resourceAndAction;

      const allowed = permit.check(
        {
          key: userId,
          attributes: userAttributes,
        },
        action,
        {
          type: resource,
          attributes: resourceAttributes,
          tenant: "default",
        }
      );

      return allowed;
    };

    const permittedList = await Promise.all(resourcesAndActions.map(checkPermissions));

    console.log(permittedList); // Printing the result of the checks

    return res.status(200).json({ permittedList });
  } catch (error) {
    console.error(error);
    return res.status(500).json({ error: "Internal Server Error" });
  }
}
```

Replace `YOUR_PERMIT_API_KEY` with your environment API key, loaded from an environment variable in production. Anyone with the environment API key can change that environment's policy through the Permit API, so keep the key on the server and don't commit it. The `pdp` value is the address of your PDP container. See [Get your API key](/overview/get-api-key) and [Run the PDP](/overview/run-pdp).

## 4. Load the user's permissions with the AbilityLoader \{#creating-the-abilityloader}

The `AbilityLoader` component runs after the user signs in. It reads the user ID from Clerk, initializes `permit-fe-sdk` with the route from the previous step as `backendUrl`, and calls `loadLocalStateBulk()` once with every action and resource the dashboard checks. `permit-fe-sdk` stores the results so later checks don't call the backend. The component also converts the results into CASL rules and shares them through a React context. To learn more about CASL with Permit, see [CASL](/integrations/feature-flagging/casl).

The user ID must match the user key synced to Permit. Any authentication provider works if it gives you that ID.

```js
import React, { createContext, useEffect, useState } from "react";
import { useUser } from "@clerk/nextjs";
import { Ability } from "@casl/ability";
import { Permit, permitState } from "permit-fe-sdk";

// Create Context
export const AbilityContext = createContext();

export const AbilityLoader = ({ children }) => {
  const { isSignedIn, user } = useUser();
  const [ability, setAbility] = useState(undefined);

  useEffect(() => {
    const getAbility = async (loggedInUser) => {
      const permit = Permit({
        loggedInUser: loggedInUser,
        backendUrl: "/api/something",
      });

      await permit.loadLocalStateBulk([
        {
          action: "view",
          resource: "Products",
          userAttributes: {
            country: "PL",
            channel: "ABC",
          },
        },
        {
          action: "view",
          resource: "Product_Configurators",
          userAttributes: {
            country: "UK",
            channel: "ABC",
          },
        },
        {
          action: "view",
          resource: "Project_Builder",
          userAttributes: {
            country: "FR",
            channel: "DEF",
          },
        },
        {
          action: "view",
          resource: "Topics_for_you",
          userAttributes: {
            country: "ES",
            channel: "DEF",
          },
        },
      ]);

      const caslConfig = permitState.getCaslJson();

      return caslConfig && caslConfig.length ? new Ability(caslConfig) : undefined;
    };

    if (isSignedIn) {
      getAbility(user.id).then((caslAbility) => {
        setAbility(caslAbility);
      });
    }
  }, [isSignedIn, user]);

  return <AbilityContext.Provider value={ability}>{children}</AbilityContext.Provider>;
};
```

The `userAttributes` in each item are sent to the permission check route and passed to `permit.check()`. The sample hardcodes a different `country` and `channel` for each tile to show the format. In your app, pass the signed-in user's values, such as `user.publicMetadata.country`.

Wrap the dashboard in `AbilityLoader` so the permissions load before the tiles render.

## 5. Render tiles based on the stored permissions \{#conditionally-rendering-the-ui}

In the file that renders the dashboard, import `permitState`:

```js
import { permitState } from "permit-fe-sdk";
```

Call `permitState.check()` for each tile. `permitState.check()` reads the result stored by `loadLocalStateBulk()` and doesn't call the backend. When no stored result matches, `permitState.check()` returns `false` by default, and the tile stays hidden.

```js
<div className="flex h-full">
  <div className="flex flex-col flex-grow">
    {permitState?.check("view", "Products", {
      country: user.publicMetadata.country,
      channel: user.publicMetadata.channel,
    }) && <div className="bg-white m-4 p-4 h-[250px]">Products</div>}

    {permitState?.check("view", "Product_Configurators", {
      country: user.publicMetadata.country,
      channel: user.publicMetadata.channel,
    }) && <div className="bg-white m-4 p-4 h-[200px]">Product Configurators</div>}

    {permitState?.check("view", "Project_Builder", {
      country: user.publicMetadata.country,
      channel: user.publicMetadata.channel,
    }) && <div className="bg-white m-4 p-4 h-[200px]">Project Builder</div>}

    {permitState?.check("view", "Topics_for_you", {
      country: user.publicMetadata.country,
      channel: user.publicMetadata.channel,
    }) && <div className="bg-white m-4 p-4 h-[100px]">Topics for you</div>}
  </div>
</div>
```

:::warning Stored results must match the render check
`permitState.check()` finds a stored result only when the action, the resource, and the attributes object match an item that `loadLocalStateBulk()` loaded. The `permit-fe-sdk` implementation matches the third argument of `permitState.check()` as resource attributes. If the render check passes attributes that the bulk load didn't, no stored result matches, and every tile stays hidden.
:::
