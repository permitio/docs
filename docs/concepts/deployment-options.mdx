This page is for teams that have [completed the Quickstart](/quickstart), connected an application to Permit,
and are now evaluating whether they need an on-premise deployment instead of the default hybrid model.

## Why would you need to deploy Permit.io on-premise? {#why-would-you-need-to-deploy-permitio-on-premise}

Most teams don't. In the default [hybrid](/concepts/control-plane-and-data-plane) deployment, policy decision points (PDPs) run in your network
and your data can stay there, while Permit runs the control plane.
You need an on-premise deployment when your network is air-gapped (no internet connection at all), or when your
security or compliance policy requires every component to run on-premise. Permit supports both on-premise options below for those cases.

## On-premise deployment types

There are two types of on-premise deployment:

### Full on-prem

In a full on-premise deployment, you run the entire Permit.io stack shown in the diagram below, delivered as Kubernetes Helm charts.
It is the option with the most DevOps and IT work.

![Full-on-prem diagram](/img/diagrams/full_on_prem.svg)

### Light on-prem

In a light (partial) on-premise deployment, you keep using the Permit management interfaces in the cloud and run only the
administration components, primarily the OPAL server, in your network.
You sync the policy state from your cloud Git repository (which you own) to a local Git repository, and the local OPAL server tracks it.
Because every change passes through your own repository, you can filter, test, benchmark, and review configuration and policy before it reaches your on-premise PDPs.
Light on-prem takes less work than full on-prem, and sits between full on-prem and hybrid.

![Full-on-prem diagram](/img/diagrams/partial_on_prem.svg)
