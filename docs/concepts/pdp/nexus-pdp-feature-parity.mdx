Use this page to check whether Permit Nexus PDP, a self-hosted policy decision point (PDP), supports the endpoints and capabilities your application uses before you choose Nexus PDP or move to it. The page compares Nexus PDP (`permitio/nexus-pdp`) with the [container PDP](/concepts/pdp/overview#run-an-edge-pdp-with-docker), the Edge PDP image `permitio/pdp-v2`.

:::info Nexus PDP support changes between releases
This comparison describes Nexus PDP as of November 2026. The set of supported capabilities changes between releases, so check this page before you upgrade.
:::

## Nexus PDP compatibility with container PDP endpoints

Nexus PDP accepts the same paths, request bodies, and response bodies as the container PDP on the endpoints that Nexus PDP implements. SDK calls to those endpoints work without other code changes when you set the SDK's PDP URL to a Nexus PDP and its `token` to the Nexus PDP API key.

Nexus PDP implements a subset of the container PDP's endpoints. Its capabilities match those of the managed [Cloud PDP](/concepts/pdp/cloud-pdp-capabilities), running in your own network.

## Notes on specific rows

### Data filtering on Nexus PDP \{#data-filtering}

Nexus PDP supports [`/user-permissions`](/how-to/enforce-permissions/user-permissions) and [`/authorized_users`](/how-to/enforce-permissions/authorized-users), which answer most "which resources can this user see?" questions on both PDP types. For other approaches, see [Data filtering](/how-to/enforce-permissions/data-filtering).

### AuthZen search on Nexus PDP \{#authzen-search}

Nexus PDP answers all three AuthZen search endpoints the way the container PDP does. Both PDPs share these limits:

- Neither PDP paginates search results. A search returns all its results in one response, and `page.next_token` is always empty.
- On both PDPs, resource search doesn't filter by the requested action. It returns every resource of the requested type on which the subject has any permission.

Action search differs in one way. Nexus PDP matches a `tenant` set in the resource's `properties` and returns that tenant's actions. The container PDP doesn't match it yet, so on the container PDP a search that sets one returns no actions.

### Health and readiness on Nexus PDP \{#health-and-readiness}

The container PDP serves `GET /health`, `GET /healthy`, and `GET /ready` on port `7000`. On Nexus PDP, port `7000` serves `GET /health` and `GET /healthy`, which always return `200`, and has no `/ready`. Readiness is `GET /health/ready` on the management port, `7001`. Point every probe at port `7001`. See [Health and readiness](/concepts/pdp/nexus-pdp-deployment#health-and-readiness).

### Booting without the control plane on Nexus PDP \{#offline-boot}

Nexus PDP signs up with the control plane every time it starts, not only on its first boot. A Nexus PDP that cannot reach the control plane when it starts does not start.

A running Nexus PDP that loses the control plane keeps answering on port `7000` from its local copy. Its readiness endpoint, `GET /health/ready` on port `7001`, returns `503` within about 30 seconds, so Kubernetes stops sending it traffic through its Service.

### ABAC policies on Nexus PDP \{#abac}

:::warning ABAC checks on Nexus PDP return a deny
A check against a policy that uses condition sets, user sets, or resource sets returns a deny on Nexus PDP, not an error. If your policies use ABAC, run the container PDP, or users lose access that the policy grants.
:::

### Cross-origin requests on Nexus PDP \{#cors}

Nexus PDP serves your backend services, not browsers, so it sends no cross-origin resource sharing (CORS) headers. A browser calling a PDP directly would have to hold the environment's Nexus PDP API key, which every user of the page could then read. Call Nexus PDP from your backend, and have your backend answer the browser.

The container PDP allows cross-origin requests from any origin by default. If your frontend calls the container PDP directly today, move those calls to your backend before you switch to Nexus PDP.
