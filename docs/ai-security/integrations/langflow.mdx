Build a flight booking assistant in Langflow that checks Permit.io policies before it searches flights, answers policy questions, or books a ticket. This tutorial is for AI agent builders who design flows in the Langflow visual editor. It applies the [Four-Perimeter Framework](/ai-security/framework) with three Permit components for Langflow: **JWT Validator**, **Permissions Check**, and **Data Protection**.

You build three flows:

| Flow | What it enforces | Perimeter |
| --- | --- | --- |
| Flight Search | Only users allowed to `search` on `flight` reach the agent and the flight database | Prompt filtering |
| Flight Information | Only users allowed to `info` on `flight` get baggage and service policy answers | Secure external access |
| Flight Booking | Only users allowed to `create` on `booking` can call the booking API | Secure external access, response enforcement |

## Prerequisites and tech stack \{#prerequisites-and-tech-stack}

- A [Permit.io account](https://app.permit.io/) and your environment API key. See [Get your API key](/overview/get-api-key).
- Docker, to run an Edge policy decision point (PDP). The policies in this tutorial use attribute-based access control (ABAC), which the Cloud PDP doesn't evaluate. See [Cloud PDP capabilities](/concepts/pdp/cloud-pdp-capabilities).
- A Langflow instance. See the [Langflow installation guide](https://docs.langflow.org/get-started-installation).
- The Permit components for Langflow. Langflow doesn't include them. Get the component files from the [permit-langflow-framework repository](https://github.com/permitio/permit-langflow-framework) and add them to Langflow as custom components. See [Custom components](https://docs.langflow.org/components-custom-components) in the Langflow docs. The `permit-langflow` 0.1.0 package on PyPI pins `langflow==1.1.4.post1`, so check the pin against your Langflow version.
- A JSON Web Key Set (JWKS) endpoint and RS256-signed test JSON Web Tokens (JWTs). Each JWT header needs a `kid` that matches a key in the JWKS, and the payload needs a `sub` claim with the user key.
- An OpenAI API key for the agent components, and an [Astra DB](https://www.datastax.com/products/datastax-astra) database with a `flights` collection for the Flight Search flow.

### Tools and services \{#tools--services}

| Tool | Role in this tutorial |
| --- | --- |
| [Langflow](https://www.langflow.org/) | Visual editor for the three flows |
| [Permit.io](https://app.permit.io/) | Stores the policy and evaluates checks on the PDP |
| [OpenAI](https://platform.openai.com/docs) | Model for the agent components |

```bash
PERMIT_API_KEY=your_api_key
PERMIT_PDP_URL=http://localhost:7766
JWKS_URL=https://your-domain/.well-known/jwks.json
OPENAI_API_KEY=sk-...
```

| Variable | Used in |
| --- | --- |
| `PERMIT_API_KEY` | **API Key** field of Permissions Check and Data Protection |
| `PERMIT_PDP_URL` | **PDP URL** field of Permissions Check and Data Protection. Use your Edge PDP, not the Cloud PDP. |
| `JWKS_URL` | **JWKS URL** field of JWT Validator |
| `OPENAI_API_KEY` | The agent and OpenAI components |

## Plan the access model \{#planning-our-policies}

The assistant searches flights, answers questions about flight policies, and books tickets. User attributes decide what each user can do.

### Resources and actions \{#resources--actions}

| Resource | Actions | Attributes |
| --- | --- | --- |
| `flight` | `search`, `info`, `viewprice`, `viewavailability` | `type` (String): the operation type (`info`, `search`, `booking`). `sensitivity` (String): `public`, `protected`, or `private`. |
| `booking` | `create`, `modify`, `cancel`, `view` | `type` (String): the booking operation type. `sensitivity` (String): the sensitivity of the booking data. |

### User attributes

| Attribute | Type | Values |
| --- | --- | --- |
| `membership_tier` | Array | For example `basic`, `premium` |
| `region` | String | `domestic`, `international` |
| `verified` | Boolean | `true` when the user's identity is confirmed |

### Condition sets

| User set | Condition |
| --- | --- |
| Membership Tier Access | `user.verified == true` |
| Regional Restrictions | `user.region == "domestic"` |
| Sensitive Data Access | `user.membership_tier` equals `premium` |

## Configure the policy in Permit \{#permit-schema-setup}

Create the schema in the [Permit dashboard](https://app.permit.io/).

### 1. Create the resources \{#define-resources}

Open **Policy > Resources** and create a `flight` resource for flight information and search:

```json
{
  "actions": ["search", "info", "viewprice", "viewavailability"],
  "attributes": {
    "type": "String",
    "sensitivity": "String"
  }
}
```

![Create Resource form for the flight resource with its actions and attributes](/img/ai-security/integrations/langflow/2.jpg)

Create a `booking` resource for flight bookings:

```json
{
  "actions": ["create", "modify", "cancel", "view"],
  "attributes": {
    "type": "String",
    "sensitivity": "String"
  }
}
```

![Create Resource form for the booking resource with its actions and attributes](/img/ai-security/integrations/langflow/3.jpg)

The JSON blocks list the values to enter in the form.

### 2. Define user attributes \{#define-user-attributes}

Open **Directory > Users > Settings** and add these user attributes:

```json
{
  "membership_tier": "Array",
  "region": "String",
  "verified": "Boolean"
}
```

![User attribute settings with membership_tier, region, and verified](/img/ai-security/integrations/langflow/4.jpg)

### 3. Create the ABAC user sets \{#create-condition-sets}

Open **Policy > ABAC Rules**, click **ABAC User Sets**, and create three user sets.

**Membership Tier Access:**

```text
user.verified == true
```

**Regional Restrictions:**

```text
user.region == "domestic"
```

![User set form for regional restrictions with the region equals domestic condition](/img/ai-security/integrations/langflow/6.jpg)

**Sensitive Data Access:**

```text
user.membership_tier equals premium
```

![User set form for sensitive data access with the membership_tier equals premium condition](/img/ai-security/integrations/langflow/7.jpg)

### 4. Grant permissions in the Policy Editor \{#grant-permissions-in-the-policy-editor}

Open the **Policy Editor**. The columns are your user sets and the rows are resource actions. Each checked box grants that action to users in that user set.

| Action | Membership Tier Access | Regional Restrictions | Sensitive Data Access |
| --- | --- | --- | --- |
| `booking:create` | Yes | Yes | Yes |
| `booking:modify` | Yes | No | Yes |
| `booking:cancel`, `booking:view` | Yes | No | No |
| `flight:search` | No | Yes | No |
| `flight:info` | No | Yes | No |
| `flight:viewavailability` | Yes | No | No |
| `flight:viewprice` | Yes | No | Yes |

### 5. Add test users \{#add-test-users}

The JWT Validator component reads only the `sub` claim from the token. The Permissions Check component sends that user key to the PDP without attributes, so the PDP uses the attributes stored on the user in Permit. In the **Directory** screen, create a user for each test JWT `sub` and set the user's attributes. See [Sync users](/how-to/sync-users).

**Fully authorized premium user:**

```json
{
  "key": "user-001",
  "attributes": {
    "membership_tier": ["premium"],
    "region": "domestic",
    "verified": true
  }
}
```

**Limited basic user:**

```json
{
  "key": "user-002",
  "attributes": {
    "membership_tier": ["basic"],
    "region": "international",
    "verified": false
  }
}
```

The JWT for each user needs only a `sub` claim that matches the user key.

## Create the test JWTs and the JWKS endpoint \{#create-the-test-jwts-and-the-jwks-endpoint}

1. Install the signing libraries:

   ```bash
   pip install "pyjwt[crypto]"
   ```

2. Save this script as `make_test_jwt.py`:

   ```python
   import json

   import jwt
   from cryptography.hazmat.primitives.asymmetric import rsa
   from jwt.algorithms import RSAAlgorithm

   KEY_ID = "flight-demo-key"
   USER_KEYS = ["user-001", "user-002"]

   private_key = rsa.generate_private_key(public_exponent=65537, key_size=2048)

   jwk = json.loads(RSAAlgorithm.to_jwk(private_key.public_key()))
   jwk.update({"kid": KEY_ID, "alg": "RS256", "use": "sig"})
   with open("jwks.json", "w", encoding="utf-8") as handle:
       json.dump({"keys": [jwk]}, handle, indent=2)

   for user_key in USER_KEYS:
       token = jwt.encode(
           {"sub": user_key},
           private_key,
           algorithm="RS256",
           headers={"kid": KEY_ID},
       )
       print(f"{user_key}: {token}")
   ```

3. Run the script. It writes `jwks.json` next to itself and prints one token per user:

   ```bash
   python make_test_jwt.py
   ```

4. Serve `jwks.json` over HTTP from the folder that holds it:

   ```bash
   python -m http.server 8080
   ```

5. Verify that the JWKS endpoint answers:

   ```bash
   curl -s http://localhost:8080/jwks.json
   ```

## Run the Edge PDP locally \{#running-the-permit-pdp-locally}

The Permissions Check and Data Protection components send checks to the PDP. Run an Edge PDP in Docker:

1. Pull the PDP image:

   ```bash
   docker pull permitio/pdp-v2:latest
   ```

2. Start the PDP container. Replace `<YOUR_API_KEY>` with your environment API key.

   ```bash
   docker run -it -p 7766:7000 \
     --env PDP_DEBUG=True \
     --env PDP_API_KEY=<YOUR_API_KEY> \
     permitio/pdp-v2:latest
   ```

3. Verify that the PDP is up:

   ```bash
   curl -s http://localhost:7766/healthy
   ```

For more deployment options, see the [PDP overview](/concepts/pdp/overview).

## Build the flows \{#building-the-flows}

Each flow starts with the same two identity components: a **Text Input** for the JWT and a **JWT Validator** that turns the JWT into a user key. The **User ID** output of JWT Validator connects to the **User ID** input of Permissions Check.

## Flight Search flow \{#flight-search-flow}

The Flight Search flow applies prompt filtering. The flow checks `search` on `flight` before the agent or the database receives the user's query.

### Flight Search components \{#overview-of-flow-components}

Add these components to the canvas:

| Component | Purpose |
| --- | --- |
| Text Input | Receives the JWT |
| Chat Input | Receives the flight search query |
| JWT Validator | Verifies the JWT and outputs the user key |
| Permissions Check | Checks `search` on `flight` for the user |
| If-Else | Routes the query based on the permission result |
| Astra Assistant Agent | Extracts and validates the departure and arrival cities |
| Astra DB | Retrieves flight data |
| Parse DataFrame | Formats the results |
| Two Chat Outputs | Show the allowed response or the denial |

### Flight Search component configuration \{#component-configuration}

**JWT Validator**
- **JWT Token**: connected from Text Input
- **JWKS URL**: your JWKS endpoint

**Permissions Check**

```text
PDP URL: http://localhost:7766
API Key: your Permit environment API key
Resource: flight
Action: search
```

**Astra Assistant Agent**
- **Agent Instructions:**

```text
You are a flight search assistant. Your job is to:
1. Extract departure and arrival cities from user queries
2. Validate that these are real cities with airports
3. Format the search request for our database
4. Handle cases where cities are unclear or invalid
```

**Astra DB**
- **Collection**: `flights`
- **Database**: your Astra DB database, for example `flight_db`

**Parse DataFrame** template:

```text
Flight {row_number}: {departure_city} to {arrival_city}
Departure: {departure_time}
Airline: {airline}
Flight Number: {flight_number}
Price: ${price}
Available Seats: {seats}
```

![Langflow canvas with the Flight Search flow components connected](/img/ai-security/integrations/langflow/9.jpg)

### Connect the Flight Search flow \{#flow-logic}

1. Connect **Text Input** to **JWT Validator**.
2. Connect **JWT Validator** to **Permissions Check**.
3. Connect **Permissions Check** to **If-Else**.
   - True path: Astra Assistant Agent, Astra DB, Parse DataFrame, then the allowed Chat Output.
   - False path: the denied Chat Output.
4. Connect **Chat Input** to **If-Else**.

With these connections, a query reaches the agent and Astra DB only when the JWT is valid and the PDP allows `search` on `flight`.

### Flight Search results \{#example-behavior}

| User | Query | Result |
| --- | --- | --- |
| Allowed user | "Find flights from NYC to Paris next week" | A formatted list of flights |
| Denied user | Any query | The denied Chat Output, before the agent or the database runs |

## Flight Information flow \{#flight-information-flow}

The Flight Information flow answers questions about travel policies, baggage allowances, and services. It applies secure external access: the flow checks `info` on `flight` before the agent fetches data from external policy URLs.

### Flight Information components \{#overview-of-flow-components-1}

| Component | Purpose |
| --- | --- |
| Text Input | Receives the JWT |
| Chat Input | Receives the policy question |
| JWT Validator | Verifies the JWT and outputs the user key |
| Permissions Check | Checks `info` on `flight` for the user |
| If-Else | Routes the question based on the permission result |
| Astra Assistant Agent | Answers the policy question |
| URL | Loads policy content from your policy pages |
| Parse DataFrame | Formats the policy content |
| Two Chat Outputs | Show the allowed response or the denial |

### Flight Information component configuration \{#component-configuration-1}

**JWT Validator**
- **JWKS URL**: your JWKS endpoint

**Permissions Check**

```text
PDP URL: http://localhost:7766
API Key: your Permit environment API key
Resource: flight
Action: info
```

**Astra Assistant Agent**
- **Model:** `gpt-4o-mini`
- **Agent Instructions:**

```text
You are a knowledgeable Local Expert that provides accurate flight policy and service information. You should:
1. Answer questions about baggage policies
2. Explain flight rules and restrictions
3. Provide information about services and amenities
4. Always maintain privacy by not revealing sensitive pricing or route details without authorization
```

**URL**
- **URLs**: the pages that hold your baggage and service policies, for example `https://<your-policy-site>/baggage` and `https://<your-policy-site>/services`
- **Output Format**: `Text`

**Parse DataFrame** template:

```text
Policy Information:
------------------
{policy_title}

Details:
{policy_details}

Additional Information:
{additional_info}
------------------
```

![Langflow canvas with the Flight Information flow: If-Else, Astra Assistant Agent, URL, Parse DataFrame, JWT Validator, and Permissions Check with the info action on flight](/img/ai-security/integrations/langflow/10.png)

### Connect the Flight Information flow \{#flow-logic-1}

1. Connect **Text Input** to **JWT Validator**.
2. Connect **JWT Validator** to **Permissions Check**.
3. Connect **Chat Input** to **If-Else**.
4. Route on the Permissions Check result:
   - Allowed: Astra Assistant Agent, URL, Parse DataFrame, then the allowed Chat Output.
   - Denied: the denied Chat Output.

### Flight Information results \{#example-behavior-1}

Example questions:

- "What's the baggage allowance for international flights?"
- "What are the rules for pet travel?"

| User | Result |
| --- | --- |
| Matches a user set with `info` on `flight` | The agent answers from the policy content |
| Doesn't match | The denied Chat Output |

## Flight Booking flow \{#flight-booking-flow}

The Flight Booking flow completes a booking, which changes data in an external system. The flow applies two perimeters:

- **Secure external access:** Permissions Check allows the booking API call only when the PDP allows `create` on `booking`.
- **Response enforcement:** Data Protection outputs the `booking` resource IDs the user can `create`, and Filter Data limits the booking data in the response to those IDs.

### Flight Booking components \{#components-used}

| Component | Purpose |
| --- | --- |
| Text Input | Receives the JWT |
| Chat Input | Receives the booking request |
| JWT Validator | Verifies the JWT and outputs the user key |
| Permissions Check | Checks `create` on `booking` for the user |
| Data Protection | Outputs the IDs of `booking` resources the user can `create` |
| If-Else | Routes the request based on the permission result |
| API Request | Calls your booking API |
| Astra Assistant Agent | Processes the booking request |
| Filter Data | Shapes the final output |
| Chat Output | Shows the booking result |

### Flight Booking component configuration \{#component-configuration-2}

**JWT Validator**
- **JWKS URL**: your JWKS endpoint

**Permissions Check**

```text
PDP URL: http://localhost:7766
API Key: your Permit environment API key
Resource: booking
Action: create
```

**Data Protection**
- **Resource Type**: `booking`
- **Action**: `create`
- **PDP URL** and **API Key**: the same values as Permissions Check

**API Request**
- **URL**: your booking API endpoint, for example `https://<your-booking-api>/v1/bookings`. Use a mock endpoint while you test.
- **Method**: `POST`

**Astra Assistant Agent**
- **Model:** `gpt-4o-mini`
- **Agent Instructions:**

```text
You are a booking assistant that helps process flight booking requests.
Always ensure the user is authorized before confirming anything.
```

### Connect the Flight Booking flow \{#flow-connections}

1. Connect **Text Input** to **JWT Validator**.
2. Connect the **User ID** output of **JWT Validator** to both **Permissions Check** and **Data Protection**.
3. Connect **Chat Input** to **Permissions Check**, and **Permissions Check** to **If-Else**.
4. Allowed path: API Request, Astra Assistant Agent, then Chat Output.
5. Denied path: the denied Chat Output.
6. Connect **Data Protection** to **Filter Data**, then format the result and send it to Chat Output.

A user the PDP denies can't reach the booking API.

### Flight Booking results \{#example-scenario}

Request: "Book me a flight from NYC to LA for next Monday."

| User | Result |
| --- | --- |
| `user-001` (`membership_tier: ["premium"]`, `region: domestic`, `verified: true`) | The PDP allows `create`. The API Request runs and the agent confirms the booking. |
| `user-002` (`membership_tier: ["basic"]`, `region: international`, `verified: false`) | The PDP denies `create`. The flow returns the denied Chat Output before the API call. |

## Run the flows and verify access \{#running-the-demo--verifying-behavior}

1. Start the Edge PDP. Replace `<YOUR_API_KEY>` with your environment API key:

   ```bash
   docker run -it -p 7766:7000 \
     --env PDP_DEBUG=True \
     --env PDP_API_KEY=<YOUR_API_KEY> \
     permitio/pdp-v2:latest
   ```

2. Install and start Langflow. For other installation options, see the [Langflow installation guide](https://docs.langflow.org/get-started-installation):

   ```bash
   uv pip install langflow
   uv run langflow run
   ```

3. Check that the Permit component settings use these values:

   ```text
   PERMIT_API_KEY=...
   PERMIT_PDP_URL=http://localhost:7766
   JWKS_URL=http://localhost:8080/jwks.json
   ```

4. Paste the JWT for `user-001` or `user-002` into the Text Input of each flow.

### View decisions in the audit logs \{#where-to-view-permissions--logs}

Open [audit logs](/how-to/use-audit-logs/types-and-filtering) in the Permit dashboard to see each check and why the PDP allowed or denied it. When you change a condition in the Policy Editor, the PDP receives the updated policy and the next check uses it.
