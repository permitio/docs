Classify a user's free-text prompt into a structured access request with OpenAI, then check that request with `permit.check()` before your app answers. This tutorial is for AI agent builders who write Node.js and need to decide whether a chat user can see what they ask for. It applies the prompt filtering perimeter of the [Four-Perimeter Framework](/ai-security/framework).

A chat interface receives open-ended requests like these:

```
- “What’s the IATA rate for this hotel?”
- “Help me diversify my investment portfolio”
- “Show me my financial data for Q1”
```

Some of these requests are fine for every user, and some need a specific role. A prompt has no endpoint or parameter that a rule can match, so the app first turns it into a resource type, a resource key, attributes, and an action.

## What you build \{#what-youll-build}

A Node.js module that:

1. Sends the prompt to OpenAI with a system prompt that returns JSON: `resourceType`, `resourceKey`, `attributes`, and `action`.
2. Builds a Permit resource from that JSON.
3. Calls `permit.check()` on a policy decision point (PDP) and allows or denies the request.

The example covers two domains:

| Domain | Resource types | Rule |
| --- | --- | --- |
| Hotel rates | `HotelType` with the `rateType` attribute (`IATA`, `premium`, `public`) | Users see public rates. `premium_user` also sees premium rates, and `iata_agent` also sees IATA rates. |
| Financial advice | `FinancialAdvice`, `FinancialData` | `viewer` sees financial data. Only `ai_advisor` receives AI-generated financial advice. |

The full source is in the [permit-prompt-filtering repository](https://github.com/permitio/permit-prompt-filtering).

## How prompt filtering works

A role check needs structured input: a user, an action, and a resource. A chat prompt is unstructured text. Prompt filtering puts a classifier between the two. The classifier maps the prompt to a resource type and attributes, and the PDP evaluates that structured request against your policy before the app processes the prompt.

![Flow diagram: a user prompt goes to the OpenAI classifier, which returns a structured request that Permit checks before the app responds](/img/ai-security/integrations/openai/1.png)

### Why classify prompts with an LLM \{#why-is-ai-classification-important}

- **No keyword lists:** the classifier maps different phrasings of the same request to the same resource type, without regular expressions.
- **Defaults for missing details:** the system prompt tells the classifier which value to use when the prompt doesn't name one, for example `rateType: "public"`.
- **One classifier, several domains:** you configure the resource type and attributes per classifier instance.

An LLM classifier can return a wrong resource type or attribute. Your policy decides the result for whatever the classifier returns, so write the system prompt to default to the least privileged value.

## Configure the policy in Permit \{#defining-policies-with-permitio}

Create the roles, resources, resource sets, and rules in the **Policy** screen of the [Permit dashboard](https://app.permit.io/).

### 1. Create the roles \{#create-the-roles}

Open **Policy > Roles** and add these roles:

| Role | Can access |
| --- | --- |
| `iata_agent` | IATA hotel rates |
| `premium_user` | Premium hotel rates |
| `ai_advisor` | AI-generated financial advice |
| `viewer` | Public data |

![Roles tab listing the editor, admin, viewer, iata_agent, premium_user, and ai_advisor roles](/img/ai-security/integrations/openai/2.png)

### 2. Create the resources \{#create-the-resources}

Open **Policy > Resources** and create:

| Resource | Action | Attributes |
| --- | --- | --- |
| `HotelType` | `read` | `rateType` (String): `IATA`, `premium`, or `public` |
| `FinancialData` | `read` | None |
| `FinancialAdvice` | `read` | None |

![Resources tab of the Policy screen, used to create the HotelType, FinancialData, and FinancialAdvice resources](/img/ai-security/integrations/openai/3.png)
![Resource form with the attribute settings for the rateType attribute](/img/ai-security/integrations/openai/4.png)

### 3. Create the resource sets \{#create-the-resource-sets}

Open **Policy > ABAC Rules** and create three ABAC resource sets on `HotelType`:

| Resource set | Condition |
| --- | --- |
| `iata_rates` | `resource.rateType == "IATA"` |
| `premium_rates` | `resource.rateType == "premium"` |
| `public_rates` | `resource.rateType == "public"` |

`FinancialAdvice` and `FinancialData` don't need resource sets. The rules reference them directly.

![ABAC Rules tab with a resource set on HotelType defined by a rateType condition](/img/ai-security/integrations/openai/5.png)

### 4. Grant permissions \{#grant-permissions}

In the **Policy Editor**, check `read` for these role and resource pairs:

| Role | `read` on |
| --- | --- |
| `viewer` | `public_rates`, `FinancialData` |
| `premium_user` | `premium_rates`, `public_rates` |
| `iata_agent` | `iata_rates`, `public_rates` |
| `ai_advisor` | `FinancialAdvice` |

![Policy Editor with read checked for each role on its resources and resource sets](/img/ai-security/integrations/openai/6.png)

### 5. Create test users \{#create-test-users}

In the **Directory** screen, create the users that the test code checks and assign each user a role in the `default` tenant. See [Sync users](/how-to/sync-users).

| User key | Role |
| --- | --- |
| `premium_user_001` | `premium_user` |
| `regular_user_1` | `viewer` |

If a user key doesn't exist in Permit, the PDP denies every check for that user.

## Run the PDP \{#running-the-pdp}

1. Pull the PDP image:

   ```bash
   docker pull permitio/pdp-v2:latest
   ```

2. Run the PDP container. Replace `<YOUR_API_KEY>` with your environment API key:

   ```bash
   docker run -it -p 7766:7000 \
     --env PDP_DEBUG=True \
     --env PDP_API_KEY=<YOUR_API_KEY> \
     permitio/pdp-v2:latest
   ```

3. Connect the Permit SDK to the PDP. Import the SDK with `const { Permit } = require('permitio');` and create the client:

   ```js
   const permit = new Permit({
     token: process.env.PERMIT_API_KEY,
     pdp: process.env.PDP_URL
   });
   ```

4. Check that the container is running:

   ```bash
   docker ps
   ```

   Read the PDP logs. Replace `<container_id>` with the ID from `docker ps`:

   ```bash
   docker logs <container_id>
   ```

### Why this tutorial uses an Edge PDP

The resource sets `iata_rates`, `premium_rates`, and `public_rates` match on a resource attribute, which is attribute-based access control (ABAC). The [Cloud PDP](/concepts/pdp/overview#managed-cloud-pdp) evaluates role-based access control (RBAC) and relationship-based access control (ReBAC), but not ABAC, so hotel rate checks on the Cloud PDP don't return the results in this tutorial. See [Cloud PDP capabilities](/concepts/pdp/cloud-pdp-capabilities). A local container PDP also lets you develop without a network round trip to the Cloud PDP.

## Build the OpenAI classifier \{#implementing-the-openai-powered-classifier}

The `AccessClassifier` class turns a prompt into a structured request.

### What the classifier does \{#classifier-core-responsibilities}

- Reads a natural language request, such as "What's the price of Hilton Budapest?"
- Infers the resource type and attributes, such as `resourceType: HotelType` and `rateType: public`
- Returns a JSON object that the permission check uses

![Diagram of the classifier turning a hotel price question into resourceType, resourceKey, attributes, and action](/img/ai-security/integrations/openai/7.png)

### Configure a classifier instance \{#classifier-setup}

The constructor takes an optional resource type and a list of attributes to look for. The class adds them to the system prompt it sends to OpenAI:

```js
// The classifier adapts based on what you pass:
const hotelClassifier = new AccessClassifier('HotelType', ['rateType']); // For hotel rate requests
const financeClassifier = new AccessClassifier('FinancialAdvice'); // For financial requests
const genericClassifier = new AccessClassifier(null, ['sensitivity']); // For generic attribute checking
```

The system prompt defines the output format and gives example classifications. This outline of the class shows the constructor, the system prompt builder, and the `classify()` method:

```js
const OpenAI = require('openai');

class AccessClassifier {
    constructor(resourceType = null, attributes = []) {
        this.openai = new OpenAI({
            apiKey: process.env.OPENAI_API_KEY
        });
        
        this.resourceType = resourceType;
        this.attributes = attributes;
        this.systemPrompt = this.buildSystemPrompt();
    }

    buildSystemPrompt() {
        // Base prompt explaining the classifier's job
        let prompt = `You are a request classifier that understands user intent.
Your job is to analyze requests and determine:
1. The type of resource being requested
2. Any relevant attributes of that resource
3. The intent behind the request (data access vs advisory)

Output format:
{
    "resourceType": "determined from context",
    "resourceKey": "specific identifier",
    "attributes": "relevant attributes if any",
    "action": "usually read"
}`;

        // Add configuration-specific instructions
        if (this.resourceType) {
            prompt += `\n\nClassify requests specifically for: ${this.resourceType}`;
        }

        if (this.attributes.length) {
            prompt += `\n\nLook for these attributes: ${this.attributes.join(', ')}`;
        }

        // Examples showing the classifier's flexibility
        prompt += `\n\nExample classifications:
[Request]: "Show me the data"
[Output]: {
    "resourceType": "determined by context",
    "resourceKey": "data",
    "attributes": {},
    "action": "read"
}

[Request]: "I need access to X with Y permission"
[Output]: {
    "resourceType": "X",
    "resourceKey": "identifier",
    "attributes": {"permission": "Y"},
    "action": "read"
}`;

        return prompt;
    }

    async classify(userPrompt) {
        const response = await this.openai.chat.completions.create({
            model: "gpt-4",
            messages: [
                { role: "system", content: this.systemPrompt },
                { role: "user", content: userPrompt }
            ],
            temperature: 0
        });

        return JSON.parse(response.choices[0].message.content.trim());
    }
}
```

`classify(userPrompt)` sends the system prompt and the user prompt to the OpenAI chat completions API with `temperature: 0`, and returns the parsed JSON from the response. The complete class is in [`src/classifier.js`](https://github.com/permitio/permit-prompt-filtering/blob/main/src/classifier.js) in the example repository.

### Classifier output

For a hotel classifier, `classify()` returns an object like the one in this block:

```js
// The classifier adapts based on configuration
const classifier = new AccessClassifier('HotelType', ['rateType']);

// Example usage with output
const result = await classifier.classify("What's the price for Hilton?");
// result:
// {
//     resourceType: "HotelType",
//     resourceKey: "hilton",
//     attributes: { rateType: "public" },
//     action: "read"
// }
```

## Check permissions on the classified request \{#permission-check-implementation}

After the classifier returns a structured request, `checkAccess` builds a Permit resource from it and calls `permit.check()`.

![Diagram of the permission check: the classified request becomes a Permit resource and the PDP returns allow or deny](/img/ai-security/integrations/openai/8.png)

The calling code creates one classifier per domain, classifies the prompt, and checks the result for a user:

```js
// First, create our domain-specific classifiers
const hotelClassifier = new AccessClassifier('HotelType', ['rateType']);
const financeClassifier = new AccessClassifier('FinancialAdvice');

// Example requests
const request = "Show me my current portfolio value";
const classification = await financeClassifier.classify(request);
const allowed = await checkAccess('regular_user_1', classification);
```

### The checkAccess function \{#the-checkaccess-function}

`checkAccess` takes a user key and the classified request. It builds a resource with `type` and `key`, adds `attributes` when the classifier returned any, and calls `permit.check()`. When the PDP denies the request, the function logs a reason based on the resource type. The function uses the `permit` client from [Run the PDP](#running-the-pdp).

```js
async function checkAccess(userId, parsedRequest) {
  try {
    console.log('\n🔒 Checking Permission:');
    console.log(`👤 User: ${userId}`);
    console.log(`📑 Resource Type: ${parsedRequest.resourceType}`);
    console.log(`🎯 Action: ${parsedRequest.action}`);

    let resource = {
      type: parsedRequest.resourceType,
      key: parsedRequest.resourceKey
    };

    // Add attributes only if they exist
    if (Object.keys(parsedRequest.attributes || {}).length > 0) {
      resource.attributes = parsedRequest.attributes;
      console.log('📋 Attributes:', parsedRequest.attributes);
    }

    try {
      const permitted = await permit.check(
        userId,
        parsedRequest.action,
        resource
      );

      if (permitted) {
        console.log('✅ Access Granted');
      } else {
        // Log specific denial reason
        if (parsedRequest.resourceType === 'HotelType') {
          console.log('❌ Access Denied - Insufficient rate type permissions');
        } else if (parsedRequest.resourceType === 'FinancialAdvice') {
          console.log('❌ Access Denied - User not authorized for financial advice');
        } else {
          console.log('❌ Access Denied - Insufficient permissions');
        }
      }

      return permitted;
    } catch (checkError) {
      if (checkError.message.includes('role')) {
        console.error('❌ Role-based permission check failed:', checkError.message);
      } else if (checkError.message.includes('attribute')) {
        console.error('❌ Attribute-based permission check failed:', checkError.message);
      } else {
        console.error('❌ Permission check failed:', checkError.message);
      }
      throw checkError;
    }
  } catch (err) {
    console.error("❌ Permission check failed:", err);
    throw err;
  }
}
```

## Test the classifier and the policy \{#testing-the-system}

Run each example inside an `async` function.

### Test a premium hotel rate request \{#example-classifying-and-enforcing-access}

```js
const hotelClassifier = new AccessClassifier("HotelType", ["rateType"]);
const request = "Show me the premium rate for Hilton";

const classification = await hotelClassifier.classify(request);
const allowed = await checkAccess("premium_user_001", classification);
```

The classifier returns `rateType: "premium"`. `premium_user_001` has the `premium_user` role, so `checkAccess` logs `✅ Access Granted` and returns `true`. For a user without `premium_user`, such as `regular_user_1`, it logs `❌ Access Denied - Insufficient rate type permissions` and returns `false`.

### Test a financial advice request \{#example-financial-advice-check}

```js
const financeClassifier = new AccessClassifier("FinancialAdvice");
const adviceRequest = "How should I diversify my investments?";

const classification = await financeClassifier.classify(adviceRequest);
const allowed = await checkAccess("regular_user_2", classification);
```

`regular_user_2` has the `viewer` role, not `ai_advisor`, so `checkAccess` logs `❌ Access Denied - User not authorized for financial advice` and returns `false`. Assign `ai_advisor` to `regular_user_2` and run the check again to see `✅ Access Granted`.

## View decisions in the audit logs \{#logs--observability}

Open [audit logs](/how-to/use-audit-logs/types-and-filtering) in the Permit dashboard to see each check. Each entry shows the user, action, resource, and whether the PDP allowed or denied the request. Use the audit logs to find out why a classified request was denied, for example when the classifier returned an unexpected `rateType`.
