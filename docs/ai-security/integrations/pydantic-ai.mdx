Add Permit.io permission checks to the tools of a PydanticAI financial advisor agent. This tutorial is for AI agent builders who use [PydanticAI](https://github.com/pydantic/pydantic-ai) and want each tool call to respect the user's permissions. It applies all four perimeters of the [Four-Perimeter Framework](/ai-security/framework), and the source is in [permitio/Permit-PydanticAI](https://github.com/permitio/Permit-PydanticAI).

| Perimeter | Agent tool | Permit call |
| --- | --- | --- |
| Prompt filtering | `validate_financial_query` | `permit.check()` for `receive` on `financial_advice` |
| RAG data protection | `access_financial_knowledge` | `permit.filter_objects()` for `read` on `financial_document` |
| Secure external access | `check_action_permissions` | `permit.check()` on `portfolio` |
| Response enforcement | `validate_financial_response` | `permit.check()` for `requires_disclaimer` on `financial_response` |

## Prerequisites and tech stack \{#prerequisites-and-tech-stack}

| Tool or service | Purpose |
| --- | --- |
| [PydanticAI](https://github.com/pydantic/pydantic-ai) | Agent framework with typed tools and results |
| [Permit.io account](https://app.permit.io/) and an environment API key ([Get your API key](/overview/get-api-key)) | Stores the policy |
| An [Anthropic](https://www.anthropic.com/) API key | The example agent uses the `anthropic:claude-3-5-sonnet-latest` model. PydanticAI reads the key from `ANTHROPIC_API_KEY`. To use [OpenAI](https://openai.com/), change the model string in `example/main.py`. |
| [Docker](https://www.docker.com/) | Runs the Edge policy decision point (PDP). The policy uses attribute-based access control (ABAC), which the Cloud PDP doesn't evaluate. See [Cloud PDP capabilities](/concepts/pdp/cloud-pdp-capabilities). |
| [Python 3.9 or later](https://www.python.org/) | Runs the agent |
| [uv](https://docs.astral.sh/uv/) | Installs the example's dependencies |

:::note PydanticAI versions
The example requires `pydantic-ai>=0.0.20` and uses the `result_type` argument and `result.data`. Later PydanticAI releases renamed some of these APIs. If the agent fails to start, check the [PydanticAI changelog](https://github.com/pydantic/pydantic-ai/releases) against the installed version.
:::

## Plan the access model \{#planning-our-policies}

The financial advisor agent follows four rules:

| Perimeter | Rule |
| --- | --- |
| Prompt filtering | Give AI-generated advice only to users who opted in |
| RAG data protection | Show confidential documents only to users with high clearance |
| Secure external access | Allow portfolio actions only for premium users |
| Response enforcement | Add a disclaimer to responses that contain advice |

### Resources \{#defining-resources}

`example/config.py` creates these resources:

| Resource | Actions | Attributes |
| --- | --- | --- |
| `financial_advice` | `receive` | `is_ai_generated` (bool), `risk_level` (string) |
| `financial_document` | `read` | `doc_type`, `classification` (`public`, `restricted`, `confidential`), `clearance_required` |
| `portfolio` | `update`, `read`, `analyze` | `owner_id`, `value_tier` |
| `financial_response` | `requires_disclaimer` | `contains_advice` (bool), `risk_level` (string) |

### User attributes \{#defining-user-attributes}

| Attribute | Type | Description |
| --- | --- | --- |
| `clearance_level` | string | The user's clearance: `low` or `high` |
| `ai_advice_opted_in` | bool | Whether the user accepted AI-generated financial advice |

### Condition sets \{#defining-condition-sets}

`example/config.py` creates two user sets and two resource sets:

| Set | Type | Condition |
| --- | --- | --- |
| `opted_in_users` | User set | `user.ai_advice_opted_in` equals `true` |
| `high_clearance_users` | User set | `user.clearance_level` equals `"high"` |
| `confidential_docs` | Resource set on `financial_document` | `resource.classification` equals `"confidential"` |
| `finance_advice` | Resource set on `financial_advice` | `resource.is_ai_generated` equals `true` |

The design this example is based on also describes these conditions. Only the first matches an attribute that `config.py` creates, and there under the name `ai_advice_opted_in`:

- AI advice consent:

  ```hcl
  user.opted_in == true
  ```

- Document clearance match. A user set condition can't compare a user attribute to a resource attribute, so `config.py` uses `high_clearance_users` and `confidential_docs` instead:

  ```hcl
  user.clearance_level == resource.classification
  ```

- Sensitive portfolio access. `role` isn't a user attribute in `config.py`; the example grants portfolio actions through the `premium_user` role:

  ```hcl
  user.role == "premium_user"
  ```

- Response disclaimer required. `config.py` defines the `contains_advice` attribute but no resource set on it:

  ```hcl
  resource.contains_advice == true
  ```

### Roles and rules \{#defining-roles--user-sets}

| Role | Permissions created by `config.py` |
| --- | --- |
| `premium_user` | `financial_advice:receive`, `financial_document:read`, `portfolio:update`, `portfolio:read`, `portfolio:analyze` |
| `restricted_user` | None |

The example defines two condition set rules: `opted_in_users` can `receive` on `finance_advice`, and `high_clearance_users` can `read` on `confidential_docs`. `config.py` lists these rules but doesn't create them, so grant them in the Policy Editor.

No role or rule in `config.py` grants `requires_disclaimer` on `financial_response`. The response enforcement tool adds a disclaimer only when that check is allowed, so grant `requires_disclaimer` to `premium_user` in the Policy Editor.

## Perimeter 1: Filter prompts \{#prompt-filtering}

Prompt filtering rejects a request before the agent acts on it. The `validate_financial_query` tool classifies whether the question asks for advice, then checks `receive` on `financial_advice` with `is_ai_generated` set to the classification result.

### How prompt filtering works \{#how-it-works}

1. `classify_prompt_for_advice` detects whether the question asks for financial advice.
2. `permit.check()` asks the PDP whether the user can `receive` `financial_advice` with that `is_ai_generated` value. The `opted_in_users` rule on `finance_advice` allows opted-in users.
3. When the PDP denies the check, the tool returns a denial message to the agent. When it allows the check, the tool returns `True`.

```python
@financial_agent.tool
async def validate_financial_query(
    ctx: RunContext[PermitDeps],
    query: FinancialQuery,
) -> Union[bool, str]:
    """SECURITY PERIMETER 1: Prompt Filtering
    Validates whether users have explicitly consented to receive AI-generated financial advice.
    """
    try:
        # Classify the user's intent
        is_seeking_advice = classify_prompt_for_advice(query.question)

        # Perform the permission check with Permit.io
        permitted = await ctx.deps.permit.check(
            {"key": ctx.deps.user_id},
            "receive",
            {
                "type": "financial_advice",
                "attributes": {
                    "is_ai_generated": is_seeking_advice,
                },
            },
        )

        if not permitted:
            return (
                "User has not opted in to receive AI-generated financial advice."
                if is_seeking_advice
                else "User is not authorized for this type of query."
            )

        return True

    except PermitApiError as e:
        raise SecurityError(f"Prompt permission check failed: {str(e)}")
```

### Classify financial prompts \{#classifying-financial-prompts}

The example classifies prompts with a keyword list:

```python
def classify_prompt_for_advice(question: str) -> bool:
    advice_keywords = [
        "should I", "recommend", "advice", "suggest",
        "what's the best", "help me choose", "better option"
    ]
    question_lower = question.lower()
    return any(keyword in question_lower for keyword in advice_keywords)
```

The function lowercases the question but not the keywords, so the keyword `"should I"` never matches. Use lowercase keywords, or replace the keyword list with an intent classifier.

### Expected prompt filtering results \{#expected-behavior}

| User | Prompt | Result |
| --- | --- | --- |
| `user@example.com` (opted in) | "Can you recommend a bond fund?" | Allowed |
| `restricted@example.com` (not opted in) | "Can you recommend a bond fund?" | Denied: "User has not opted in to receive AI-generated financial advice." |

## Perimeter 2: Filter documents \{#data-protection}

RAG data protection limits the documents the agent can use to the ones the user can `read`. The `access_financial_knowledge` tool sends every candidate document, with its `classification` and `doc_type` attributes, to `permit.filter_objects()`. The tool returns the content of the allowed documents only.

### How document filtering works \{#how-it-works-1}

1. The query includes a list of candidate documents.
2. `filter_objects` runs one check per document for `read` on `financial_document`, with the document's attributes.
3. The tool keeps the documents the PDP allows and passes their content to the agent.

```python
@financial_agent.tool
async def access_financial_knowledge(
    ctx: RunContext[PermitDeps],
    query: FinancialQuery
) -> List[str]:
    """SECURITY PERIMETER 2: Data Protection
    Filters knowledge base access based on document classification and user clearance.
    """
    try:
        resources = [
            {
                "id": doc.id,
                "type": "financial_document",
                "attributes": {
                    "doc_type": doc.type,
                    "classification": doc.classification,
                },
            }
            for doc in query.documents
        ]

        # Use Permit to filter accessible documents
        allowed_docs = await ctx.deps.permit.filter_objects(
            ctx.deps.user_id,
            "read",
            {},
            resources
        )

        allowed_ids = {doc["id"] for doc in allowed_docs}
        return [doc.content for doc in query.documents if doc.id in allowed_ids]

    except PermitApiError as e:
        raise SecurityError(f"Failed to filter documents: {str(e)}")
```

### Document model and classifications \{#document-model--classifications}

Each document has a classification:

```python
class FinancialDocument(BaseModel):
    id: str
    type: str  # e.g., "report", "chart", "transcript"
    classification: str  # "public", "restricted", "confidential"
    content: str
```

The PDP evaluates the `classification` attribute against the `confidential_docs` resource set and the user's `clearance_level`.

### Expected document filtering results \{#expected-behavior-1}

| User | Document classification | Result |
| --- | --- | --- |
| `user@example.com` (`premium_user`, `clearance_level: high`) | `confidential` | Allowed |
| `restricted@example.com` (`restricted_user`, `clearance_level: low`) | `confidential` | Denied |

## Perimeter 3: Authorize external actions \{#secure-external-access}

Secure external access checks permission before the agent changes data in another system, such as updating a portfolio, moving money, or calling a webhook. The `check_action_permissions` tool checks the requested action on `portfolio`:

```python
@financial_agent.tool
async def check_action_permissions(
    ctx: RunContext[PermitDeps],
    action: str,
    context: UserContext
) -> bool:
    """SECURITY PERIMETER 3: Secure External Access
    Controls permissions for sensitive financial operations, such as modifying a portfolio.
    """
    try:
        return await ctx.deps.permit.check(
            ctx.deps.user_id,
            action,
            {"type": "portfolio"}
        )
    except PermitApiError as e:
        raise SecurityError(f"Failed to check portfolio update permission: {str(e)}")
```

The check runs before the agent calls the external system. In `example/main.py`, the tool always checks the `update` action.

### Expected portfolio results \{#real-world-scenarios}

| User | Action | Result |
| --- | --- | --- |
| `user@example.com` (`premium_user`) | `update` on `portfolio` | Allowed |
| `restricted@example.com` (`restricted_user`) | `update` on `portfolio` | Denied |

### Call an external API after the check \{#combining-with-external-apis}

Call the external API only when the check returns `True`:

```python
if await check_action_permissions(...):
    # Proceed to call API
    result = await client.put("/portfolios/123", json=payload)
else:
    raise SecurityError("Unauthorized portfolio update attempt.")
```

## Perimeter 4: Enforce the response \{#response-enforcement}

Response enforcement checks the final answer before the user sees it. The `validate_financial_response` tool classifies whether the answer contains advice, checks `requires_disclaimer` on `financial_response`, and appends a disclaimer when the answer contains advice and the check allows it:

```python
@financial_agent.tool
async def validate_financial_response(
    ctx: RunContext[PermitDeps],
    response: FinancialResponse
) -> FinancialResponse:
    """SECURITY PERIMETER 4: Response Enforcement
    Ensures all financial advice responses meet regulatory requirements
    and include necessary disclaimers.
    """
    try:
        contains_advice = classify_response_for_advice(response.answer)

        permitted = await ctx.deps.permit.check(
            ctx.deps.user_id,
            "requires_disclaimer",
            {
                "type": "financial_response",
                "attributes": {"contains_advice": str(contains_advice)},
            },
        )

        if contains_advice and permitted:
            disclaimer = (
                "\n\nIMPORTANT DISCLAIMER: This is AI-generated financial advice. "
                "This information is for educational purposes only and should not be "
                "considered professional financial advice. Always consult a qualified advisor."
            )
            response.answer += disclaimer
            response.disclaimer_added = True
            response.includes_advice = True

        return response

    except PermitApiError as e:
        raise SecurityError(f"Failed to check response content: {str(e)}")
```

The tool sends `contains_advice` as the string `"True"` or `"False"`, while `config.py` defines the attribute as a boolean. A condition that compares `contains_advice` to the boolean `true` doesn't match the string value.

### Classify responses \{#response-classification}

The example detects advice in a response with a keyword list:

```python
def classify_response_for_advice(response_text: str) -> bool:
    advice_indicators = [
        "recommend", "should", "consider", "advise",
        "suggest", "best option", "strategy", "allocation"
    ]
    return any(keyword in response_text.lower() for keyword in advice_indicators)
```

In production, replace the keyword list with an intent classifier or a moderation API.
