Plan your Permit.io rollout and fit it into your software development lifecycle (SDLC). This page is for engineering leads and architects who own the authorization rollout. None of these practices is required, and each one saves rework later.

## Define the project scope \{#project-scope}

- Before you integrate anything, write down your use case and user stories. For example: "a support agent can read a customer's tickets, but only in the customer's tenant". The stories show the priorities, scale, and data volume your authorization layer needs to handle.
- Decide which policy authoring interface each stakeholder needs. Developers can use the API, SDKs, or policy as code. Product managers and security teams can use the Policy Editor. End users can use Permit Elements.

## Model your policies \{#modeling-your-policies}

After you know what your authorization layer needs to do and who operates it, model the policies:

- Start with the policy model closest to your existing authorization logic, and extend it from there.
- If you're not sure where to start, pick a simpler model: [multi-tenant](/concepts/multi-tenant-authorization) [role-based access control (RBAC)](/how-to/build-policies/rbac/overview), or [relationship-based access control (ReBAC)](/how-to/build-policies/rebac/overview) with a single-level hierarchy or direct [ownership](/how-to/ownership).

:::tip Map your authorization layer
Follow the step-by-step guide to [planning an RBAC implementation](https://www.permit.io/blog/planning-app-rbac) to map roles, resources, and actions before you build.
:::

## Start with a small proof of concept \{#aim-for-a-quick-poc}

- After you pick a model, apply Permit to one part of your application first, such as a single service. That part gets fine-grained enforcement while the rest of your setup stays the same.
- If you already have an in-house authorization system, run Permit alongside it. For example, call `permit.check()` next to your existing check, log both decisions, and compare them before you switch enforcement to Permit.
- Run the first proof of concept in a development or staging environment before you deploy to a larger part of your application.

## Map deployments to projects, environments, and tenants \{#deployment-and-silos}

### Projects and environments \{#consider-projects-and-environments}

Use [projects](/manage-your-account/projects-and-env#projects) and [environments](/manage-your-account/projects-and-env#environments) to keep deployments separate. Each environment has its own policy, data, and API key.

:::tip Example mapping
Create one Permit project for each application or major service. Inside the project, create one environment for each deployment stage: development, staging, user acceptance testing (UAT), and production.
:::

### Tenants

Use [tenants](/concepts/multi-tenant-authorization/#tenants-in-permitio) to isolate users and resources that belong together. Role assignments are scoped to a tenant, so a role in one tenant grants nothing in another tenant.

:::tip Tenants for B2B accounts
In a B2B application, create one tenant for each customer account.
:::

### Policy decision points (PDPs) \{#policy-decision-points-pdps}

- [Policy decision points (PDPs)](/overview/how-does-it-work#the-policy-decision-point-pdp) answer permission checks. Teams usually start by running PDPs as sidecars, or as load-balanced containers on services such as AWS Fargate, Google Cloud Run, or Kubernetes (for example Amazon EKS). See [Deploy Permit to production](/how-to/deploy/deploy-to-production).
- Start each PDP with the [API key](/manage-your-account/workspace-settings#api-keys) of the environment it serves. A PDP started with the staging API key answers checks with the staging policy, even when production traffic reaches it.

## Manage policy changes in your SDLC and CI/CD \{#managing-policy-sdlc-and-cicd}

### Control who changes policy at each stage \{#sdlc}

Use [project and environment member roles](/manage-your-account/workspace-settings#member-management) to control who can change policy at each deployment stage. For example, a product manager can edit policy in the staging environment, while only a developer or DevOps engineer can edit the production environment.

### Automate environments in CI/CD \{#cicd-integration}

- Call the [create environment API](https://api.permit.io/v2/redoc#tag/Environments/operation/create_environment) from your CI/CD pipeline to create a preview environment for each pull request. Limit access to the preview environment during review, for example to the developer who opened the pull request.
- Call the [copy environment API](https://api.permit.io/v2/redoc#tag/Environments/operation/copy_environment) to promote changes from one environment to another, so environments stay consistent. See [Copy and merge environments](/manage-your-account/creating-environments).
- Use the [Permit Terraform provider](/integrations/infra-as-code/terraform-provider/) to manage environment baselines and policy changes as code.
- Use [GitOps](/integrations/gitops/overview) to review, merge, and roll out policy changes the same way you manage code.

## Give each stakeholder the right interface \{#the-right-interfaces-for-the-right-people}

- Grant [Policy Editor access](/manage-your-account/workspace-settings#member-management) to stakeholders based on their role, so non-technical staff can make the policy changes they own without a code release.
- Give the broader developer team access to the Permit API and the Terraform provider for day-to-day operations.
- Limit GitOps and direct policy-as-code access to the developers who own the policy code.
- Use [Permit Elements](/embeddable-uis/overview), embeddable UI components, to let your end users manage users and approve access requests in their own tenant.
