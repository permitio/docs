Build a relationship-based access control (ReBAC) policy in the Permit.io dashboard, then test it with a permission check. This walkthrough is for developers who have built a role-based access control (RBAC) policy and need permissions that follow relationships between objects. You model dashboards that contain widgets, so a role on a dashboard gives a role on every widget in it.

## Prerequisites

- A Permit.io account with a project and environment ([Configure your first RBAC policy](/overview/configure-your-first-rbac-policy))
- The ReBAC concepts of resource roles, relations, and role derivations ([ReBAC overview](/how-to/build-policies/rebac/overview), [Policy basics](/how-to/build-policies/policy-basics))
- To run the test check: an initialized Permit SDK connected to a policy decision point (PDP) ([Use the Permit API and SDK](/overview/use-the-permit-api-and-sdk))

## Part 1: Define the policy schema \{#defining-our-rebac-policy---schema}

The example is a dashboarding system with two resource types. `Dashboard` is the parent. `Widget` is the child. Each resource has its own roles: Owner, Viewer, and Analyst on dashboards, and Owner, Viewer, and Editor on widgets. A role on a dashboard gives a matching role on every widget in that dashboard.

<img
  src="/ui-videos/walkthroughs/rebac/project-diagram-rebac.png"
  alt="Diagram of the Dashboard and Widget resources: Dashboard is parent of Widget, each has three resource roles, and Dashboard Owner and Viewer derive Widget Editor and Viewer"
  data-zoomable
/>

The schema has four parts: resources with their roles, the relation between the resources, role derivations, and permissions.

## Step 5: Add data and test the policy \{#step-1-testing-our-policy}

<TimelineWrapper>
<TimelineStep>

### Create users \{#create-users}

In **Directory**, click **Add user** and create two users. Don't give them top-level roles. You assign an instance role in a later step.

| User | Key | Email |
|---|---|---|
| John Smith | `johnsmith` | `john@smith.com` |
| Anna Smith | `annasmith` | `anna@smith.com` |

<Video src={"/ui-videos/walkthroughs/rebac/creating-users-rebac.mp4"} controls autoPlay={false} />

</TimelineStep>
<TimelineStep>

### Create resource instances and their relationship \{#create-resource-instances-and-their-relationship-tuples}

Create a Widget instance, `data_consumption`, under a Dashboard instance, `data`.

1. In **Directory**, open the **Instances** tab and click **Add Instance**.
2. In **Resource Type**, select `Dashboard`.
3. In **Instance Key**, enter `data`.
4. In **Tenant**, select **Default Tenant**.
5. Under **Relationships**, click **Add Relationship** and set `Dashboard` `data` **is parent of** `Widget` `data_consumption`.
6. Click **Save**.

The Instances tab lists `Widget` `data_consumption` and `Dashboard` `data`, each with one relationship. Permit creates the `data_consumption` Widget instance from the relationship.

<Video
  src={"/ui-videos/walkthroughs/rebac/create-resource-instances-rebac.mp4"}
  controls
  autoPlay={false}
/>

</TimelineStep>
<TimelineStep>

### Assign an instance role \{#assign-roles}

Make John Smith `Owner` of the `data_consumption` widget.

1. In **Directory**, open the **Users** tab, click the three-dot menu of John Smith, and select **Edit**.
2. Under **Instance Access**, click **Add Instance Access**.
3. Select `Widget`, enter the instance `data_consumption`, and select the role `Owner`.
4. Click **Save**.

John Smith's row shows `Widget:data_consumption#Owner` under **Instance Access**.

<Video
  src={"/ui-videos/walkthroughs/rebac/assign-instance-roles-rebac.mp4"}
  controls
  autoPlay={false}
/>

</TimelineStep>
<TimelineStep>

### Test the policy with a permission check \{#test-the-policy}

Call `permit.check()` with a user key, an action, and a resource instance. This is the shape of the call:

```js
await permit.check(userId, action, {
  type: "Widget",
  key: "someKey",
  tenant: "someTenant",
});
```

For this policy, use these values:

| Argument | Value for this walkthrough |
|---|---|
| `userId` | `johnsmith` |
| `action` | `edit` |
| `type` | `Widget` |
| `key` | `data_consumption` |
| `tenant` | `default` |

The check returns `true`, because John Smith is Owner of the `data_consumption` widget, and a Widget Owner can `edit`. The same check for `annasmith` returns `false`, because Anna Smith has no role on the widget or its dashboard. Each decision also appears on the **Audit Log** screen of the Permit dashboard.

</TimelineStep>
</TimelineWrapper>
