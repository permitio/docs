Move an application from the deprecated Permit.io v1 API, v1 policy decision point (PDP), and v1 SDKs to v2. This page is for maintainers of code that calls the v1 API or runs a v1 PDP. It explains what changed in v2 and the order to migrate in.

## Who needs to migrate \{#who-is-this-guide-for}

Migrate if your code does any of the following:

- Calls the Permit REST API at a v1 path.
- Runs a v1 PDP container.
- Uses a v1 SDK.

The v1 API and v1 PDPs are deprecated. Features added in v2, such as attribute-based access control (ABAC) condition sets, are available only in the v2 API.

## What changed in v2 \{#tldr---what-changed}

| Area | v1 | v2 |
| --- | --- | --- |
| Object hierarchy | Objects could live at the organization level | Organizations contain projects, projects contain environments, and environments contain almost every other object. See [v2 object hierarchy](#new-object-hierarchy). |
| API roots | Mixed | General objects at `/v2/orgs` and `/v2/projects`, schema objects under `/v2/schema`, and facts objects under `/v2/facts` |
| Identifiers | Slugs, `custom_id` values, and keys in different places | Keys everywhere. Every path accepts either the key or the Permit ID of an object. See [Keys](#keys). |
| Organization-scoped schema objects | Supported | Not supported. Move them into an environment. See [Move off organization-scoped objects](#migrating-off-organization-scoped-objects). |
| SDK write calls | v1 write API | A different write API. Code that writes through the SDK must change. See [Upgrade the PDP and SDKs](#migrating-the-pdp-and-sdk). |
| `permit.check()` and SDK initialization | v1 calls | Same calls as v1 |

The v1 and v2 APIs read and write the same data, so you can use both during the migration. The two APIs make different assumptions about the structure of data, so a v1 call can behave differently from the v2 call for the same object.

## v2 object hierarchy \{#new-object-hierarchy}

v2 objects nest in a strict hierarchy:

| Level | Represents | Example |
| --- | --- | --- |
| Organization | Your company | Acme Corp |
| Project | One product of your company. Projects share little with each other. | `billing`, `crm` |
| Environment | One deployment stage of a project, such as production or staging | `prod`, `staging` |

Environments are self-contained. A change in the staging environment does not affect the production environment. To copy policy from one environment to another, see [Create, copy, and merge environments](/manage-your-account/creating-environments).

### Object types \{#types-of-objects}

Objects inside an environment are either schema objects or facts objects:

| Type | What it defines | Objects | API root |
| --- | --- | --- | --- |
| Schema objects | What can exist and what is allowed: the rules of your policy | Resources (with their actions and attributes), roles (with their permissions), condition sets | `/v2/schema` |
| Facts objects | What exists: the data your policy runs on | Tenants, users, role assignments, condition set rules | `/v2/facts` |

Organizations, projects, and environments are general objects.

### General object paths \{#general-objects}

| Object | Path |
| --- | --- |
| Organizations | `/v2/orgs` |
| Projects | `/v2/projects` |
| Environments | `/v2/projects/{project_id}/envs` |

Projects are not nested under organizations in the path. Each API key belongs to a single organization, so the organization is implicit in every call. `GET /v2/orgs` returns the organization the API key belongs to.

### Schema object paths \{#schema-objects}

| Object | Path |
| --- | --- |
| Resources | `/v2/schema/{proj_id}/{env_id}/resources` |
| Resource actions | `/v2/schema/{proj_id}/{env_id}/resources/{resource_id}/actions` |
| Resource attributes | `/v2/schema/{proj_id}/{env_id}/resources/{resource_id}/attributes` |
| Roles | `/v2/schema/{proj_id}/{env_id}/roles` |
| Condition sets | `/v2/schema/{proj_id}/{env_id}/condition_sets` |

### Facts object paths \{#facts-objects}

| Object | Path |
| --- | --- |
| Users | `/v2/facts/{proj_id}/{env_id}/users` |
| Tenants | `/v2/facts/{proj_id}/{env_id}/tenants` |
| Tenant-user associations | `/v2/facts/{proj_id}/{env_id}/tenants/{tenant_id}/users` |
| Role assignments | `/v2/facts/{proj_id}/{env_id}/role_assignments` |
| Condition set rules | `/v2/facts/{proj_id}/{env_id}/set_rules` |

### HTTP methods \{#object-paths-and-conventions}

Nested objects, such as tenant-user associations, live under the path of their parent object. v2 paths follow REST conventions:

| Request | Effect |
| --- | --- |
| `GET` on an object type | Lists the objects |
| `GET` on one object | Returns the object |
| `POST` on an object type | Creates an object |
| `PATCH` on one object | Changes only the fields in the request body |
| `PUT` on one object | Replaces the object. Fields missing from the request body reset to their defaults. |
| `DELETE` on one object | Deletes the object |
| `POST` on a sub-path of an object | Runs an action on the object, for example `POST /v2/pdps/{proj_id}/{env_id}/configs/{pdp_id}/rotate-api-key` rotates the API key of a PDP |

v2 API calls authenticate with an API key in the same way as v1 calls.

### Keys \{#keys}

In v2, keys replace the v1 slugs and `custom_id` values. Every primary schema object and facts object has a key, and the key is required.

- A key can be any string of the characters `a-z`, `A-Z`, `0-9`, `_`, and `-`, including a UUID from your own system.
- A key can't change after you create the object.
- A key is unique per object type within its namespace. For most objects the namespace is the environment. For an environment it is the project, and for a project it is the organization.
- Permit uses a key only to look up the object and to check uniqueness. Wherever a path takes a Permit ID, it also accepts the key.

For example, one environment can hold a resource with the key `john` and a role with the key `john`, and two environments can each hold a resource with the key `john`. One environment can't hold two resources with the key `john`. Likewise, two projects can each have an environment with the key `prod`, but one project can't have two.

### Example paths \{#examples}

| Object | Path |
| --- | --- |
| The `document` resource in the `prod` environment of the `billing` project, by key | `/v2/schema/billing/prod/resources/document` |
| The same resource, by ID | `/v2/schema/billing/prod/resources/9014f244-9034-49a9-81ff-053a65f67ff1` |
| The `staging` environment of the `crm` project, by key | `/v2/projects/crm/envs/staging` |
| The same environment, by ID | `/v2/projects/crm/envs/1e9472f5-24d7-4b3b-b49b-39d2e8843913` |
| The same environment, by project ID and environment ID | `/v2/projects/541e3523-2cdb-468a-8ca8-e7e8ccdb415d/envs/1e9472f5-24d7-4b3b-b49b-39d2e8843913` |

## Migration order \{#migration-order}

1. **Move off organization-scoped objects**, if you have any. Do this first, because v2 PDPs ignore organization-scoped objects.
2. **Upgrade the PDP and SDKs together.** v2 SDKs work only with v2 PDPs, and v1 SDKs work only with v1 PDPs.
3. **Update REST API calls** at any point. The v1 and v2 APIs share data, so each call can move to v2 on its own schedule.

## 1. Move off organization-scoped objects \{#migrating-off-organization-scoped-objects}

v2 does not support organization-scoped schema objects. An environment depends only on its own objects, so a change in one environment can't break another. In v1, only users and roles can be organization-scoped.

The v1 API and v1 PDPs keep using organization-scoped objects. The v2 API and the Permit dashboard show them in a compatibility environment, `v2_global_env`, in the project `v1_global_project`. v2 PDPs ignore the objects in the compatibility environment.

1. Check whether you have organization-scoped objects. With an organization API key, send GET requests to these URLs:

```
https://api.permit.io/v2/schema/v1_global_project/v2_global_env/roles
https://api.permit.io/v2/facts/v1_global_project/v2_global_env/users
```

   A 404 response means the compatibility environment does not exist, so you have no organization-scoped objects. Skip to [Upgrade the PDP and SDKs](#migrating-the-pdp-and-sdk).

2. Recreate each role and user from the compatibility environment in every environment that uses it. v1 PDPs also use environment-scoped objects, so you can make this change before you upgrade to v2.
3. Verify the move: run a `permit.check()` call against a v2 PDP for a user and role you recreated. The check returns the same decision it returned on v1.
4. Delete the `v2_global_env` environment and the `v1_global_project` project.

## 2. Upgrade the PDP and SDKs \{#migrating-the-pdp-and-sdk}

You can run several PDPs for the same environment without extra configuration. Run a v2 PDP next to your v1 PDP, and point each service at the v2 PDP when you upgrade its SDK.

1. Start a v2 PDP. Use the command you use for the v1 PDP, with the image changed to `permitio/pdp-v2`. In this example, replace `permit_key_abcdefghijklmnopqrstuvwxyz` with your environment API key:

```bash
docker run -p 7766:7000 \
  --env PDP_API_KEY=permit_key_abcdefghijklmnopqrstuvwxyz \
  --env PDP_DEBUG=True \
  permitio/pdp-v2:latest
```

2. Upgrade each service to the v2 SDK, and point the SDK at the v2 PDP. SDK initialization and `permit.check()` calls don't change.
3. If the service writes data through the SDK, rewrite those calls for the v2 write API. See [Rewrite SDK write calls](#rewrite-sdk-write-calls).
4. Verify the service: run a `permit.check()` call through the v2 PDP, and confirm it returns the expected decision. See [Run the PDP](/overview/run-pdp) for how to check that the PDP container is running.
5. When every service uses the v2 SDK, stop the v1 PDP.

### Rewrite SDK write calls \{#rewrite-sdk-write-calls}

The v2 SDK write API is not compatible with the v1 write API. For example, in the Python SDK, a v1 user sync looks like this:

```python
await permit.write(permit.api.sync_user(
  user.customId,
  user.first_name,
  user.last_name,
  user.email,
  ))
```

In v2, the same sync is one call:

```python
await permit.api.sync_user(user)
```

`user` is a dict with the same fields as a user in the REST API. Only `key` is required. Also pass `email`, or `first_name` and `last_name`, so decision logs show a readable user name. In current versions of the Python SDK, `permit.api.sync_user()` is deprecated in favor of `permit.api.users.sync()`, which takes the same argument.

For the full SDK API, see the [Node.js SDK quickstart](/sdk/nodejs/quickstart-nodejs) and the [Python SDK quickstart](/sdk/python/quickstart-python).

## 3. Update REST API calls \{#how-to-migrate}

Change each v1 API call to the matching v2 path from the [object path tables](#new-object-hierarchy). Replace slugs and `custom_id` values with keys. For every v2 endpoint, see the [Permit API reference](https://api.permit.io/v2/redoc).
